# Паттерн обработки ошибок: Return-код (enum/int) + out-параметры

__Дата:__ "2026-10-30"  
__Версия:__ "1.0.0.5"  
__Стандарты:__ "C11 (ISO/IEC 9899:2011); C17 (ISO/IEC 9899:2018); C23 (ISO/IEC 9899:2024)"

__Предварительные требования:__

- Управление временем жизни объектов (Object Lifetime): четкое понимание разницы между инициализацией, занулением (safe state) и освобождением памяти в Си.
- Двухканальная передача данных: понимание разделения потока управления (`return` для статуса) и потока данных (разыменование `out`-указателей).
- Знакомство с альтернативными контрактами возврата. Паттерн 01 является одним из пяти синхронных контрактов; его выбор осознан только при понимании границ применимости соседей:
  - [Паттерн 02 (Sentinel + errno)](02_sentinel_errno.md) — естественный контракт POSIX-границы. Понимание, почему `errno` не подходит для публичного API доменной библиотеки.
  - [Паттерн 03 (Return value + err_t*)](03_return_val_param_err_t.md) — двухканальный контракт для скаляров, когда out-параметр для `int` избыточен.
  - [Паттерн 04 (Result / Tagged Union)](04_result_struct.md) — функциональная альтернатива, где статус и данные упакованы в одну структуру. Понимание, почему копирование Result дороже, чем запись в out-параметр.
  - [Паттерн 05 (Bool Success)](05_bool_success.md) — сужение контракта до предиката, когда детализация ошибок избыточна.
  - [Паттерн 08 (State/EOF Marker)](08_state_stream_marker.md) — разделение естественного конца данных и ошибки среды. Понимание, почему маркеры не должны смешиваться с кодами ошибок.
- Знакомство с [Паттерном 17: Compiler-Enforced Return Checking](17_compiler_enforced_return_checking.md) — механизмами принуждения вызывающей стороны к валидации возвращаемых кодов на этапе компиляции.
- Знакомство с [Каталогом паттернов](00_pattern_catalog.md).

__Цель:__

- Сформулировать стандарт проектирования синхронного API на языке Си с использованием раздельных каналов статуса (`err_t`) и данных (`out`-параметры).
- Зафиксировать инвариант детерминизма (принудительное зануление выходных каналов при сбоях) для предотвращения неопределенного поведения (UB) и утечек данных из стека.
- Обозначить ограничение паттерна в сценариях с множественными ресурсами и указать на необходимость специализированных механизмов очистки (см. Паттерны [10 (Goto-цепочки)](10_goto_cleanup.md) и [12 (Scope Guards)](12_raii_emulation_with_scope_guard.md)).
- Показать связь с другими паттернами: контекст ошибок (06), принудительная проверка (17), очистка ресурсов (10, 12).

__Теория:__

Когда мы пишем на C, у нас нет роскоши в виде высокоуровневых абстракций, автоматического управления памятью или встроенных механизмов обработки исключений. Каждый проектируемый интерфейс должен быть хирургически точным.
В идеальном мире проектирования систем любая доменная функция — это чистое математическое отображение:

$$f(x) = y$$

Где:

- $x \in X$ — это область определения (входные аргументы, предусловия, инварианты).
- $y \in Y$ — это область значений (результат работы, постусловия).

В контексте С-разработки эта идеальная модель сталкивается с суровой реальностью: память конечна, указатели могут быть NULL, а состояние железа — нестабильно. Поэтому реальная функция в C всегда возвращает не просто $y$. Она возвращает кортеж:

$$f(x) \rightarrow \langle Y_{result} \cup Y_{error}, \Delta S \rangle$$

Где $Y_{error}$ — это подмножество непредвиденных или предвиденных сбоев, а $\Delta S$ — изменение состояния (side-effects). И вот здесь рождается транзакционная природа функции.
.

Разработчик должен смотреть на вызов любой функции как на микротранзакцию. У нее есть два фундаментальных исхода с точки зрения теории автоматов и транзакций:

1. Счастливый путь (Happy Path / Основной канал): Функция успешно переводит систему из состояния \(S_{0}\) в состояние \(S_{1}\), возвращая валидный \(Y_{result}\).
2. Путь сбоя (Failure Path / Исключительный канал): Происходит нарушение предусловий или внешняя ошибка. Функция обязана либо сделать Rollback (откатить состояние к \(S_{0}\), как будто ничего не было), либо гарантировать Safe Failure (перевести систему в строго детерминированное безопасное состояние сбоя).

Если ваш контракт спроектирован неверно, то при возникновении ошибки состояние системы становится неопределенным (Undefined Behavior / Corrupted State).

В языках с поддержкой множественного возврата (Python, Go, Rust) это решается тривиально:

```python
# Python: множественный возврат
status, config = read_config("app.ini")
```

Функция возвращает кортеж, и вызывающая сторона деструктурирует его в две переменные. Элегантно, читаемо, безопасно. В С такой роскоши нет.

Главный определяющий фактор при инженерном __выборе__ паттерна `Return-код + out-параметры` сродни философскому — __что важнее: статус или данные__.
Если ответ на ключевой инженерный вопрос звучит как: "проверка статуса и природы ошибки обязательна, данные используются только если статус говорит, что они валидны", то выбор паттерна `Return-код + out-параметры` становится очевидным. Если же возврат данных идет через несколько out-параметров, то выбор фактически безальтернативен.

__Низкоуровневая механика и ABI (Application Binary Interface)__
На уровне ассемблера и регистров CPU (например, в System V AMD64 ABI) это разделение имеет строгое физическое воплощение:

- __Канал статуса (`return`):__ Регистр `RAX` полностью резервируется под возврат целочисленного значения `enum err_t`. Компилятор оптимизирует проверку этого регистра, генерируя быстрые условные переходы (`test rax, rax; jnz error_handler`).
- __Канал данных (`out`-параметры):__ Адреса out-переменных передаются через стандартные регистры аргументов (например, `RDI`, `RSI`, `RDX`). Сами полезные данные пишутся функцией напрямую в память, выделенную вызывающей стороной (на ее стеке или в куче).

## 1. Описание и условия применения

### 1.1. Формальное описание и контракт

В языке C существует два устоявшихся способа определения доменных кодов ошибок. Выбор между ними зависит от требований к типобезопасности, размера бинарного файла и целевой платформы.

> [!CAUTION]
> __ВАЖНО__
> Из-за отсутствия пространств имен в C, __имя самого типа и все его константы обязаны иметь уникальный префикс проекта__ (например, `myproj_`), чтобы избежать конфликтов переопределения (ODR-нарушений) при статической линковке с другими библиотеками.

__Способ А: Именованное перечисление (`enum`) — предпочтительный современный подход__
Обеспечивает семантическую типизацию, улучшает отображение значений в отладчике и в C23 позволяет применять атрибут `[[nodiscard]]` непосредственно к типу.

```c
// Префикс проекта (myproj_) обязателен для типа и всех констант
typedef enum {
    MYPROJ_ERR_OK = 0,
    MYPROJ_ERR_INVALID_ARG,
    MYPROJ_ERR_IO,
    MYPROJ_ERR_NO_MEM
} myproj_err_t;

// Сигнатура функции
// C23: [[nodiscard]]
// GCC/Clang: __attribute__((warn_unused_result))
// MSVC: _Check_return_
myproj_err_t func_name(arg1_t arg1, out_t *out_result);
```

__Способ Б: Макросы препроцессора (`#define`) — классический/строгий подход__
Оправдан в строгом embedded (где требуется строгий контроль над размером типа, например, приведение к int8_t для экономии памяти), в legacy-коде, или когда коды ошибок должны строго совпадать с аппаратными/OS-константами без неявных приведений типов.

```c
// Префикс проекта обязателен для всех макросов
#define MYPROJ_ERR_OK          0
#define MYPROJ_ERR_INVALID_ARG 1
#define MYPROJ_ERR_IO          2
#define MYPROJ_ERR_NO_MEM      3

// Сигнатура функции возвращает базовый целочисленный тип или префиксированный typedef
typedef int myproj_err_t;
myproj_err_t func_name(arg1_t arg1, out_t *out_result);
```

__Жесткий контракт (Инварианты):__
Независимо от способа определения кодов, функция обязана соблюдать следующие инварианты:

1. __Инвариант успеха:__ При возвращении `ERR_OK` (или `0`) все `out`-параметры находятся в определенном, корректном и пригодном для использования состоянии.
2. __Инвариант детерминизма при сбое:__ При возвращении любого кода, отличного от `ERR_OK`, все `out`-параметры __обязаны__ быть приведены в безопасное состояние. Рекомендуется обнулять их в самой первой строке функции (через `memset` для структур или присваивание `NULL`/`0` для скаляров). Это гарантирует, что вызывающий код, случайно прочитавший данные до проверки статуса, не получит мусор из стека (предотвращение Undefined Behavior и утечек информации, CWE-226).
3. __Инвариант проверки:__ Что бы паттерн не превратился  в декорацию, вызывающий код обязан проверять возвращаемый статус перед использованием `out`-параметров. Компилятор должен принуждать к этому (см. [Паттерн 17](17_compiler_enforced_return_checking.md)).

### 1.2. Когда паттерн уместен

Паттерн 01 является базовым контрактом возврата для синхронных API. Его применимость определяется следующими осями:

__Уровень кода (Layer):__

- __LOW (Системный):__ ⚠️ Применяется с оговорками. На границе с POSIX/stdlib естественным контрактом является [Паттерн 02 (`errno` + sentinel)](02_sentinel_errno.md). Паттерн 01 оправдан, если требуется строгий контроль типов или кроссплатформенность, но errno не должен "протекать" в публичное API.
- __MID (Доменный):__ ✅ Применяется. Архитектурный стандарт для синхронных API библиотек среднего уровня.
- __HIGH (Прикладной):__ ✅ Применяется. Для приложений, принимающих доменные коды от библиотек и реагирующих на них.

__Модель выполнения (Execution Model):__

- __Sync (Синхронная):__ ✅ Применяется. Стандартный сценарий — статус и данные передаются через стек вызовов.
- __Async (Асинхронная):__ ❌ Не применяется. В event-loop серверах стек вызовов разрушен, возврат через `return` физически невозможен. Используйте [Паттерн 15](15_async_event_error_transfer.md).

__Природа ошибки (Error Nature):__

- __Environment (Среда):__ ✅ Применяется. Ошибки I/O, сети, памяти. Доменные коды (`ERR_IO`, `ERR_NO_MEM`) маппятся из `errno` внутри реализации.
- __Domain (Доменная):__ ✅ Применяется. Бизнес-логические ошибки (валидация, парсинг). Прямое использование доменных кодов.
- __Invariant (Инвариант):__ ❌ Не применяется. Нарушение инвариантов кода — это баг, а не штатная ошибка. Используйте [Паттерн 13](13_fail_fast_assert.md).

__Длительность жизни объекта (Object Lifetime):__

- __Stateless (Без состояния):__ ✅ Применяется. Для одноразовых функций (парсеры, конвертеры, валидаторы).
- __Stateful (С состоянием):__ ✅ Применяется. Для методов долгоживущих объектов (соединения с БД, файловые потоки). В комбинации с [Паттерном 09](09_latched_error_state.md) для фатальных сбоев.

__Критичность к производительности (Performance Criticality):__
Паттерн 01 применим во всех сценариях — от Hard Real-Time до Non-Real-Time. Нулевой runtime-overhead обеспечивается передачей статуса через регистр `RAX` и прямой записью данных в память вызывающей стороны.

__Архитектурный вывод:__ Паттерн 01 является базовым контрактом для синхронных API. Его применение отсекается асинхронной моделью выполнения и нарушениями инвариантов кода.

Данный паттерн применим при соблюдении следующих условий:

__Множественность состояний ошибки.__ Функция имеет более одного способа завершиться неудачей, и вызывающей стороне критически важно различать эти причины для принятия решений. Если причина не важна — используйте [Паттерн 05](05_bool_success.md). Если нужно вернуть скаляр с опциональной детализацией — рассмотрите [Паттерн 03](03_return_val_param_err_t.md). Если нужно вернуть одно значение с обязательной причиной — используйте [Паттерн 04](04_result_struct.md).

__Сложность возвращаемых данных.__ Результат функции логически «сложный» (структуры, несколько выходных значений), что делает использование sentinel-значений ([Паттерн 02](02_sentinel_errno.md), например `NULL` или `-1`) неудобным, невозможным или семантически некорректным.

__Требование изоляции от глобального состояния.__ Разрабатываемая библиотека должна быть строго независима от глобального `errno`. Это критично для многопоточных приложений, асинхронных рантаймов и кроссплатформенных API, где `errno` может быть перезаписан внутренними вызовами до того, как его прочитает пользователь.

__Выбор способа определения кодов:__

- Используйте `enum`, если приоритетом является читаемость, типобезопасность и современные стандарты (C11/C23).
- Используйте `#define`, если приоритетом является строгий контроль над размером типа (например, приведение к `int8_t` в embedded), совместимость с устаревшим ABI или прямой маппинг на специфичные константы ОС без кастинга.

## 2. Плюсы и минусы

### 2.1. Плюсы

- __Явность контракта.__ Наличие `err_t` в сигнатуре делает факт возможной ошибки очевидным.
- __Расширяемость.__ Добавить новый тип ошибки можно, расширив `enum`, не меняя сигнатуры функций.
- __Независимость от errno.__ Облегчает многопоточность и тестирование (можно мокать ошибки).

### 2.2. Минусы и риски

- __Громоздкость сигнатур.__ При наличии нескольких выходных значений количество out-параметров растет.
- __Риск игнорирования ошибок.__ Статус можно проигнорировать.
  - *Решение:* Использование атрибутов `[[nodiscard]]` (C23) или `__attribute__((warn_unused_result))` (GCC/Clang). См. [Паттерн 17](17_compiler_enforced_return_checking.md).
- __Дублирование кода очистки.__ Если функция захватывает несколько ресурсов, код освобождения при ошибках начинает дублироваться.
  - *Решение:* Применяется [Паттерн 10: Goto-цепочки для централизованной очистки](10_goto_cleanup.md).

## 3. Сравнение с альтернативами

| Критерий | Паттерн 01 (`err_t` + out) | Паттерн 02 (Sentinel + `errno`) | Паттерн 04 (Result Struct) |
| :--- | :--- | :--- | :--- |
| __Потокобезопасность__ | Полная (Реэнтрантная по определению) | Требует TLS (Thread-Local Storage) | Полная |
| __Низкоуровневый Overhead__ | Нулевой (Регистровый ABI-оптимальный) | Накладные расходы на обращение к TLS | Копирование структуры через стек / регистры |
| __Изоляция модулей__ | Абсолютная (Внутренние коды маппятся в доменные) | Глобальное грязное состояние `errno` | Абсолютная |
| __Защита от UB__ | Гарантируется инвариантом детерминизма | Легко забыть проверить и прочитать `-1` / `NULL` | Конструктивная (Данные заблокированы в Union) |

Этот паттерн незаменим на стыке системных слоев (компоненты ОС, драйверы, SDK библиотек), где использование глобального состояния `errno` недопустимо из-за риска межмодульного загрязнения кодов ошибок, а накладные расходы на копирование тяжелых монадических структур Result (Паттерн 04) не проходят по жестким требованиям жесткого реального времени (Hard Real-Time).

### 4. Простой пример

### 4.1. Задача и код

```c
#include <stdio.h>
#include <stdlib.h>

typedef enum {
    ERR_OK = 0,
    ERR_INVALID_ARG,
    ERR_IO,
    ERR_PARSE
} err_t;

// Принудительная проверка возврата (Паттерн 17)
__attribute__((warn_unused_result))
err_t read_int(const char *path, int *out_value) {
    // 1. Детерминизм: обнуляем out-параметр сразу
    if (out_value) *out_value = 0;

    if (path == NULL || out_value == NULL) {
        return ERR_INVALID_ARG;
    }

    FILE *f = fopen(path, "r");
    if (!f) {
        return ERR_IO; // Здесь мы теряем детали errno, но сохраняем контракт
    }

    int tmp = 0;
    if (fscanf(f, "%d", &tmp) != 1) {
        fclose(f);
        return ERR_PARSE;
    }
    
    fclose(f);
    *out_value = tmp;
    return ERR_OK;
}
```

## 4. Развернутый пример: мини-библиотека конфигурации

### 4.1. Интерфейс

```c
typedef enum {
    ERR_OK = 0,
    ERR_CONFIG_INVALID_ARG,
    ERR_CONFIG_IO,
    ERR_CONFIG_PARSE,
    ERR_CONFIG_NO_MEM,
    ERR_CONFIG_NOT_FOUND
} err_t;

typedef struct config config_t;

__attribute__((warn_unused_result))
err_t config_load(const char *path, config_t **out_cfg);

void config_free(config_t *cfg);
```

### 4.2. Реализация (с безопасным аллокатором)

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

struct config_entry { char *key; char *value; };
struct config { struct config_entry *entries; size_t count; };

// Безопасный дубликатор строки (чистый C11, без утечек)
static char *safe_strdup(const char *s) {
    if (!s) return NULL;
    size_t len = strlen(s) + 1;
    char *dup = malloc(len);
    if (dup) memcpy(dup, s, len);
    return dup;
}

static err_t config_add_entry(config_t *cfg, const char *key, const char *value) {
    struct config_entry *new_entries = realloc(cfg->entries, (cfg->count + 1) * sizeof(*new_entries));
    if (!new_entries) return ERR_CONFIG_NO_MEM;
    cfg->entries = new_entries;

    // Безопасное выделение: если value упадет, мы освободим key
    char *k = safe_strdup(key);
    char *v = safe_strdup(value);
    if (!k || !v) {
        free(k); 
        free(v); 
        return ERR_CONFIG_NO_MEM;
    }

    cfg->entries[cfg->count].key = k;
    cfg->entries[cfg->count].value = v;
    cfg->count++;
    return ERR_OK;
}

err_t config_load(const char *path, config_t **out_cfg) {
    // 1. Детерминизм: обнуляем указатель
    if (out_cfg) *out_cfg = NULL; 
    
    if (!path || !out_cfg) return ERR_CONFIG_INVALID_ARG;

    FILE *f = fopen(path, "r");
    if (!f) return ERR_CONFIG_IO;

    config_t *cfg = calloc(1, sizeof(*cfg)); // calloc обнуляет поля
    if (!cfg) { fclose(f); return ERR_CONFIG_NO_MEM; }

    char line[256]; // Буфер достаточного размера
    while (fgets(line, sizeof(line), f)) {
        char *eq = strchr(line, '=');
        if (!eq) { fclose(f); config_free(cfg); return ERR_CONFIG_PARSE; }
        
        *eq = '\0';
        char *key = line;
        char *value = eq + 1;
        
        char *nl = strchr(value, '\n');
        if (nl) *nl = '\0';

        err_t err = config_add_entry(cfg, key, value);
        if (err != ERR_OK) {
            fclose(f); config_free(cfg); return err;
        }
    }
    fclose(f);
    
    *out_cfg = cfg;
    return ERR_OK;
}

void config_free(config_t *cfg) {
    if (!cfg) return;
    for (size_t i = 0; i < cfg->count; ++i) {
        free(cfg->entries[i].key);
        free(cfg->entries[i].value);
    }
    free(cfg->entries);
    free(cfg);
}
```

### 4.3. Анализ дизайна и «Мостик» к следующему паттерну

Внешний API полностью построен на `err_t`; `errno` нигде не «торчит» наружу. Низкоуровневые ошибки немедленно преобразуются в доменные коды.

__Внимание на код очистки:__
Посмотрите на функцию `config_load`. В ней __трижды__ встречается связка:
`fclose(f); config_free(cfg); return err;`

Если бы у нас было 5 ресурсов (файл, 3 аллокации, мьютекс), код очистки превратился бы в «лапшу», где легко забыть освободить ресурс.
Именно для решения этой проблемы в C был канонизирован __[Паттерн 10: Goto-цепочки для централизованной очистки (Cleanup)](10_goto_cleanup.md)__, который позволяет избавиться от дублирования `free`/`close` и сделать поток освобождения ресурсов математически строгим.

## 5. Практические рекомендации (Best Practices)

1. __Принудительная проверка:__ Всегда помечайте функции, возвращающие `err_t`, атрибутом `__attribute__((warn_unused_result))` или `[[nodiscard]]` ([Паттерн 17](17_compiler_enforced_return_checking.md)).
2. __Детерминизм out-параметров:__ Обнуляйте out-параметры (`memset` или `= NULL`) в первой строке функции. Это защитит от UB и уязвимостей.
3. __Изоляция пространства имен (Namespace Isolation):__ При проектировании кодов ошибок необходимо использовать строгий префикс проекта или библиотеки __не только для констант, но и для имени самого типа__ (например, `myproj_err_t` вместо общего `err_t`). Это предотвращает коллизии идентификаторов (ODR-нарушения или конфликты макросов) при статической линковке или включении заголовков сторонних библиотек. Дополнительно группируйте коды по внутренним доменам (`MYPROJ_ERR_CONFIG_...`, `MYPROJ_ERR_NET_...`). Резервируйте `0` для успеха и предоставляйте функцию `myproj_err_to_string()` для логирования.
4. __Маппинг `errno`:__ Если вам нужна диагностика ошибок среды (например, отличить `ENOENT` от `EACCES`), перед возвратом `ERR_IO` логируйте значение `errno` ([Паттерн 02](02_sentinel_errno.md)) или сохраняйте его во внутреннем [контексте библиотеки](06_error_context.md).
