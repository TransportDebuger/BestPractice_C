# Паттерн обработки ошибок: Goto-цепочки для централизованной очистки (Cleanup)

title: "Паттерн обработки ошибок: Goto-цепочки для централизованной очистки (Cleanup)"\
date: "2026-07-01"\
version: "v1.0"\
standards: "C11 (базовый); GCC/Clang extensions (warn_unused_result); C23 ([[nodiscard]])"\
prerequisites:

- Уверенное владение C (функции, указатели, работа с ресурсами, время жизни объектов).
- Понимание базовых схем обработки ошибок ([Паттерн 01: err_t](01_return_code_out_params.md), [Паттерн 02: sentinel+errno](02_sentinel_errno.md)).
- Знакомство с [Каталогом паттернов](00_pattern_catalog.md).

objective:

- Описать паттерн `goto-cleanup` как математически строгий механизм централизованной очистки ресурсов.
- Сформулировать инварианты инициализации, порядка освобождения (LIFO) и передачи владения.
- Показать, как избежать дублирования кода `free`/`close` без использования нестандартных расширений.
- Разобрать взаимодействие с `errno` и контекстами ошибок.

theory:
  В строгом ISO C нет автоматического разрушения объектов при выходе из области видимости (нет RAII и деструкторов). Ресурсы (память, файловые дескрипторы, мьютексы) нужно освобождать явно.\
  При наличии нескольких ресурсов и точек возможного сбоя наивная стратегия «освобождать перед каждым `return`» приводит к дублированию кода и риску утечек.\
  Паттерн `goto-cleanup` предлагает:

  1. Объявить все ресурсы в начале функции и инициализировать их безопасными sentinel-значениями (`NULL`, `-1`).
  2. При ошибке выполнять `goto` на единственную метку очистки (например, `cleanup:`) в конце функции.
  3. В блоке `cleanup` последовательно освобождать ресурсы, проверяя их на sentinel-значения.

  Ключевой философский принцип: **`goto` используется не для «спагетти-кода», а как ограниченный инструмент для линейного сворачивания стека ресурсов в обратном порядке (LIFO).**

## 1. Описание и строгий контракт

### 1.1. Типичный каркас

```c
__attribute__((warn_unused_result)) // Паттерн 17
err_t process_data(const char *path) {
    // 1. Инициализация ресурсов безопасными значениями
    FILE *f = NULL;
    char *buf = NULL;
    err_t err = ERR_OK;

    // 2. Ранний выход до захвата ресурсов (допустим и предпочтителен)
    if (!path) return ERR_INVALID_ARG;

    // 3. Последовательный захват с проверкой
    f = fopen(path, "r");
    if (!f) {
        err = ERR_IO;
        goto cleanup;
    }

    buf = malloc(1024);
    if (!buf) {
        err = ERR_NO_MEM;
        goto cleanup;
    }

    /* ... основная работа с f и buf ... */

cleanup:
    // 4. Централизованная очистка в обратном порядке (LIFO)
    free(buf);        // free(NULL) безопасен по стандарту
    if (f) fclose(f);
    
    return err;
}
```

### 1.2. Жесткие контракты и инварианты

1. **Инвариант безопасной инициализации.** Каждый ресурс обязан быть инициализирован sentinel-значением (`NULL` для указателей, `-1` для дескрипторов) *в момент объявления*. Блок `cleanup` не должен гадать, был ли ресурс захвачен; он полагается на проверку `if (res != SENTINEL)`.
2. **Правило LIFO (Обратный порядок).** Ресурсы освобождаются в порядке, обратном порядку их захвата. Это критично, если ресурсы зависят друг от друга (например, `buf` аллоцирован из кастомного аллокатора `f`, который нужно закрыть позже).
3. **Инвариант передачи владения (Disarm Pattern).** Если функция завершается успешно и передает владение ресурсом вызывающему коду (через out-параметр), локальный указатель **обязан** быть обнулен до прыжка в `cleanup` (или до `return`). Иначе `cleanup` освободит чужой ресурс (double-free).
4. **Ограничение переходов.** `goto` направлен **только вперед**, только к метке очистки в пределах той же функции.

## 2. Области применения

Паттерн является абсолютным стандартом де-факто для:

- **Системного программирования и ядра ОС:** Ядро Linux полностью построено на этой идиоме (см. Linux Kernel Coding Style, раздел 4).
- **Драйверов и embedded-систем:** Где захватывается множество аппаратных ресурсов (регистры, DMA-буферы, прерывания).
- **Сложных инициализационных функций:** Где создается объект, открываются файлы, захватываются мьютексы, и любой сбой требует отката.

## 3. Плюсы и минусы

### 3.1. Плюсы

- **Математическая строгость.** Весь код освобождения ресурсов собран в одном месте. Невозможно «забыть» освободить ресурс при добавлении новой ветки ошибки.
- **Отсутствие дублирования.** Код `free`/`close` пишется один раз, а не копируется в 5 разных веток `if`.
- **Переносимость.** Это строгий ISO C. Работает везде, в отличие от RAII-эмуляций (Паттерн 12).
- **Читаемость.** Поток «счастливого пути» (happy path) не загроможден мусором обработки ошибок.

#### 3.2. Минусы и риски

- **Требует дисциплины.** Разработчик обязан помнить о правиле LIFO и инициализации sentinel-значениями.
- **Плохая репутация `goto`.** Junior-разработчики могут злоупотребить `goto` для произвольных прыжков, превратив код в «спагетти».
- **Длина функций.** Если функция разрастается, блок `cleanup` может оказаться слишком далеко от точки захвата ресурса (решается декомпозицией функции).

## 4. Развёрнутый пример: Загрузка конфигурации с передачей владения

Покажем, как правильно передать владение динамической памятью вызывающему коду, не спровоцировав `double-free` в блоке `cleanup`.

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>

typedef enum {
    ERR_OK = 0, ERR_INVALID_ARG, ERR_IO, ERR_PARSE, ERR_NO_MEM
} err_t;

typedef struct config config_t;

__attribute__((warn_unused_result))
err_t config_load(const char *path, config_t **out_cfg) {
    FILE *f = NULL;
    config_t *cfg = NULL;
    err_t err = ERR_OK;
    char line[256];

    // Детерминизм out-параметра (Паттерн 01)
    if (out_cfg) *out_cfg = NULL; 
    if (!path || !out_cfg) return ERR_INVALID_ARG;

    f = fopen(path, "r");
    if (!f) { err = ERR_IO; goto cleanup; }

    cfg = calloc(1, sizeof(*cfg));
    if (!cfg) { err = ERR_NO_MEM; goto cleanup; }

    while (fgets(line, sizeof(line), f)) {
        /* ... парсинг строки и наполнение cfg ... */
        if (/* ошибка парсинга */) {
            err = ERR_PARSE;
            goto cleanup;
        }
    }

    if (ferror(f)) {
        err = ERR_IO;
        goto cleanup;
    }

    // УСПЕХ. Передаем владение вызывающему коду.
    *out_cfg = cfg;
    
    // ИНВАРИАНТ ПЕРЕДАЧИ ВЛАДЕНИЯ (DISARM):
    // Обнуляем локальный указатель, чтобы блок cleanup ниже НЕ освободил его.
    cfg = NULL; 
    err = ERR_OK;

cleanup:
    // Если cfg != NULL, значит произошла ошибка, и мы должны его освободить.
    // Если cfg == NULL (мы его обнулили при успехе), free(NULL) безопасен.
    if (cfg) config_free(cfg); 
    
    // Аналогично с файлом: если мы успешно дошли до конца, fclose все равно нужен.
    if (f) fclose(f);
    
    return err;
}
```

## 5. Критические нюансы (Must Read)

### 5.1. Проблема сохранения `errno` при очистке

Если вы используете `goto-cleanup` в обертках над POSIX ([Паттерн 02](02_sentinel_errno.md)), помните: системные вызовы в блоке `cleanup` (например, `close()`, `pthread_mutex_unlock()`) могут теоретически затереть `errno`, если они сами завершатся с ошибкой.\
**Правило:** Если вам нужно вернуть `errno` наверх или сохранить его в контекст ([Паттерн 06](06_error_context.md)), делайте это **до** прыжка в `cleanup`:

```c
if (read(fd, buf, size) < 0) {
    const int saved_errno = errno; // Сохраняем СРАЗУ
    err = ERR_IO;
    goto cleanup; // В cleanup вызываем close(fd), который может поменять errno
}
```

### 5.2. Ранний `return` до захвата ресурсов

Не используйте `goto cleanup` для проверок аргументов (например, `if (!ptr) goto cleanup;`), если вы еще не захватили ни одного ресурса. Прямой `return ERR_INVALID_ARG;` в прологе функции чище и безопаснее. `goto` нужен только тогда, когда есть что освобождать.

### 5.3. Ошибки в самом `cleanup`

Что делать, если `fclose(f)` вернул ошибку? В большинстве случаев (чтение файлов, освобождение памяти) ею можно пренебречь (`(void)fclose(f);`), так как у нас уже есть первичная ошибка `err`, которую мы должны вернуть. Перезаписывать первичную ошибку вторичной из `cleanup` — плохая практика, она скрывает истинную причину сбоя.

## 6. Взаимодействие с другими паттернами

### 6.1. Синергия с `err_t` и Контекстом ошибок

В блоке `cleanup` удобно фиксировать итоговую ошибку в контексте библиотеки ([Паттерн 06](06_error_context.md)) или переводить объект в залипающее состояние ([Паттерн 09](09_latched_error_state.md)):

```c
cleanup:
    if (err != ERR_OK && ctx) {
        lib_set_error(ctx, err, "Operation failed during cleanup");
    }
    free(buf);
    return err;
```

### 6.2. Эволюция: Scope Guards ([Паттерн 12](12_raii_emulation_with_scope_guard.md))

Если ваш компилятор поддерживает GCC/Clang, вы можете заменить явные `goto cleanup` на атрибут `__attribute__((cleanup))`. Это делает код линейным, но требует отказа от строгой переносимости ISO C. В ядре Linux используют `goto`, в современном `systemd` — `cleanup`. Выбор зависит от целевой платформы.

---

### 7. Практические рекомендации (Best Practices)

1. **Инициализируйте всё сразу.** `int fd = -1;`, `FILE *f = NULL;`. Никогда не оставляйте локальные переменные ресурсов неинициализированными.
2. **Соблюдайте LIFO.** Ресурсы освобождаются в порядке, обратном их созданию. Это защищает от зависимостей и deadlock-ов (если речь о мьютексах).
3. **Используйте `free(NULL)` и `fclose(NULL)` безопасно.** `free(NULL)` гарантированно безопасен по стандарту C. Для `FILE*` и дескрипторов всегда пишите `if (f) fclose(f);`.
4. **Не прячьте логику в `cleanup`.** Блок очистки должен содержать **только** освобождение ресурсов. Никаких сложных вычислений, аллокаций или логирования с `malloc`.
5. **Согласуйте имена меток.** Используйте `cleanup:`, `out:` или `error:`. Главное — единообразие во всем проекте.
