# Каталог паттернов обработки ошибок в C

__Дата:__ "2026-10-30"  
__Версия:__ "1.0.0.10"  
__Стандарты:__ "C11 (ISO/IEC 9899:2011); C17 (ISO/IEC 9899:2018); C23 (ISO/IEC 9899:2024); POSIX.1-2017; GCC/Clang/MSVC Extensions"

__Предварительные требования:__

- Базовое знание языка C (стандарт C11).
- Понимание концепций: стек/куча, указатели, время жизни объектов.
- Знакомство с многопоточностью и атомарными операциями.

__Цель:__

- Предоставить исчерпывающую таксономию паттернов обработки ошибок в C.
- Четко разграничить семантику: ошибки среды, естественное завершение, баги программиста.
- Указать строгие требования к стандарту языка или компилятора для каждого паттерна.
- Задать архитектурный фундамент для проектирования API от embedded до высоконагруженных user-space систем.

__Теория:__

В языке C отсутствует скрытый поток управления. Здесь нет встроенного механизма исключений, концепции RAII или автоматических деструкторов. Каждая инструкция выполняется ровно там, где она написана, а обработка ошибок — это всегда явное, детерминированное управление состоянием вычислительной машины и жизненным циклом ресурсов.

Представьте, что вы пишете функцию, которая открывает файл, читает данные и записывает результат в другой файл. В C вы не можете просто написать `try { ... } catch { ... }`. Вы обязаны явно проверить каждый шаг: открылся ли файл? Удалось ли прочитать данные? Записались ли они корректно? Если что-то пошло не так — кто освободит ресурсы? Кто сообщит пользователю о причине сбоя?

Этот пуризм дает разработчику полный контроль над железом и тактами, но накладывает колоссальную когнитивную нагрузку. В C ответственность за консистентность системы при сбоях полностью переложена на плечи программиста. Поскольку язык не предлагает единого синтаксического стандарта для обработки нештатных ситуаций, архитектура обработки ошибок превращается в самостоятельную дисциплину проектирования.

За десятилетия индустрия выработала набор паттернов — устоявшихся решений для типичных сценариев. Каждый паттерн ищет компромисс между тремя метриками: читаемостью кода, накладными расходами (overhead) и гарантиями безопасности.

Выбор конкретного паттерна всегда диктуется «стоимостью ошибки» (Cost of Failure), доменом разработки и целевым стандартом:

- __Низкоуровневый системный код и драйверы__ полагаются на классический POSIX-стиль (`errno`, отрицательные коды) и ручной раскрут стека через локальные переходы.
- __Средний прикладной слой и библиотеки__ мигрируют в сторону более строгой типизации — явных перечислений (`err_t`) или эмуляции алгебраических типов данных (`Result<T, E>`).
- __Верхний уровень абстракции и системы реального времени (RTOS)__ завязываются на жесткие политики восстановления, глобальные контексты или стратегии аварийного останова (fail-fast).

В основе любого успешного решения в C лежит фундаментальный принцип: __«Данные и метаданные об ошибках должны быть строго разделены. Ошибка не имеет права маскироваться под валидный результат, а штатное поведение не должно приводить к ложноположительным сбоям»__.

Этот каталог представляет собой практическую таксономию паттернов обработки ошибок в C. Мы разберем их анатомию, область применения, влияние на итоговый ассемблерный код и компромиссы, на которые приходится идти ради достижения отказоустойчивости.

## I. Паттерны возврата статуса и данных (Return & Data)

### Паттерн 01. [Return-код (enum/int) + out-параметры](01_return_code_out_params.md)

__Требуемый стандарт:__ C11 (базовый)

__Идея:__ Функция возвращает код ошибки (обычно `int` или `enum`) через `return`, а полезные данные записывает через указатели-параметры (`out`-параметры). Это классический двухканальный контракт: статус и данные живут в разных каналах связи.

__Краткий пример сигнатуры:__

```c
typedef enum {
    ERR_OK = 0,
    ERR_INVALID_ARG,
    ERR_IO,
    ERR_NO_MEM
} err_t;

err_t read_config(const char *path, config_t *out_cfg);
```

__Области применения:__

- Библиотеки и модульные API, где требуется явное и детализированное представление ошибок
- Системный код, драйверы, SDK
- Сценарии с множественными выходными значениями (структуры, несколько параметров)

### Паттерн 02. [Специальное значение (sentinel) + errno (Ошибки среды)](02_sentinel_errno.md)

__Требуемый стандарт:__ C11 + POSIX.1 (для `errno`)

__Идея:__ Функция возвращает тип результата, но одно значение зарезервировано как признак сбоя среды (`NULL`, `-1`), а дополнительные сведения даются через глобальную переменную `errno`. Это стандарт де-факто для POSIX-оберток.

__Краткий пример сигнатуры:__

```c
// POSIX-стиль
FILE *fopen(const char *path, const char *mode);  // возвращает NULL при ошибке

ssize_t read(int fd, void *buf, size_t count);    // возвращает -1 при ошибке
```

__Области применения:__

- Обертки вокруг стандартной библиотеки C
- POSIX-API, системный код
- Низкоуровневые драйверы и взаимодействие с ядром ОС

### Паттерн 03. [Return полезного значения + статус через аргумент](03_return_val_param_err_t.md)

__Требуемый стандарт:__ C11 (базовый)

__Идея:__ Функция возвращает полезное значение через `return`, а статус ошибки — через дополнительный параметр (указатель на `err_t`). Это двухканальный контракт для скалярных операций, где основное значение — это результат, а статус — вторичен.

__Краткий пример сигнатуры:__

```c
int safe_divide(int a, int b, err_t *err);
```

__Области применения:__

- Функции, где ошибки редки
- Скалярные операции (числа, указатели), где для читаемости удобно видеть результат как `return`
- Парсеры и конвертеры

### Паттерн 04. [Struct Result / Tagged Union (Структура результата)](04_result_struct.md)

__Требуемый стандарт:__ C11 (базовый), C23 (атрибут `[[nodiscard]]` к типу)

__Идея:__ Функция возвращает структуру, содержащую тег (дискриминатор) и объединение (`union`) полезной нагрузки и кода ошибки. Это функциональный стиль в C, эмулирующий алгебраические типы данных `Result<T, E>` из Rust/Haskell.

__Краткий пример сигнатуры:__

```c
// Именованный тег структуры для соответствия MISRA C:2012 Rule 2.4
// и поддержки опережающих объявлений (forward declarations)
struct result_int_impl {
  bool is_ok;
  union { int value; err_t err; } data;
};
typedef struct result_int_impl result_int_t;

result_int_t parse_int(const char *s);
```

__Области применения:__

- Парсеры, конвертеры, функциональные обертки
- Операции с владеющими указателями (где игнорирование ведет к утечке памяти)
- Современные C-библиотеки с строгой типобезопасностью

### Паттерн 05. [Простое булево «успех/неуспех»](05_bool_success.md)

__Требуемый стандарт:__ C99/C11 (`<stdbool.h>`)

__Идея:__ Функция возвращает `bool` как флаг успеха/неуспеха, данные — через out-параметры. Это упрощенный контракт, когда детализация ошибки избыточна и важна только информация "сработало / не сработало".

__Краткий пример сигнатуры:__

```c
bool parse_line(const char *line, entry_t *out_entry);
```

__Области применения:__

- Внутренние вспомогательные функции
- Фильтрация, простые проверки
- Предикаты валидации (где причина ошибки не важна)

## II. Паттерны состояния, контекста и потоков (State, Context & Flow)

### Паттерн 06. [Глобальный/контекстный объект состояния ошибок](06_error_context.md)

__Требуемый стандарт:__ C11 (базовый)

__Идея:__ Состояние ошибки привязывается к конкретному экземпляру библиотеки (контексту `lib_ctx_t`), а не к глобальной переменной `errno`. Контекст хранит код ошибки и человекочитаемое сообщение, что позволяет изолировать диагностику между независимыми экземплярами и сохранять расширенную информацию о сбое.

__Краткий пример сигнатуры:__

```c
// Именованный тег структуры для соответствия MISRA C:2012 Rule 2.4 
// и поддержки опережающих объявлений (forward declarations)
struct error_state_impl {
    err_t code;
    char  message[128]; // Фиксированный буфер: строгая защита от OOM
};
typedef struct error_state_impl error_state_t;

typedef struct {
    error_state_t err;
    /* ... другие поля состояния библиотеки ... */
} lib_ctx_t;

err_t db_query(lib_ctx_t *ctx, const char *sql, result_t *out_res);
const error_state_t *db_last_error(const lib_ctx_t *ctx);
```

__Области применения:__

- Библиотеки с несколькими независимыми экземплярами (соединения с БД, HTTP-клиенты)
- Сценарии, требующие расширенной человекочитаемой диагностики
- Восстановимые операции, где объект продолжает работать после ошибки

### Паттерн 07. [Callback-обработчики ошибок](07_error_callback.md)

__Требуемый стандарт:__ C11 (базовый)

__Идея:__ Библиотека принимает от пользователя функцию-обработчик ошибок (callback) и указатель на пользовательские данные (`user_data`). При возникновении ошибки библиотека вызывает этот callback, передавая код ошибки и контекст. Это позволяет пользователю реализовать собственную стратегию обработки (логирование, алертинг, восстановление) без модификации библиотеки.

__Краткий пример сигнатуры:__

```c
typedef void (*error_handler_t)(err_t code, const char *msg, void *user_data);

typedef struct {
    error_handler_t on_error;
    void           *user_data;
} lib_config_t;

err_t lib_init(const lib_config_t *cfg, lib_ctx_t **out_ctx);
```

__Области применения:__

- Библиотеки с гибкой политикой обработки ошибок
- Фреймворки, где стратегия обработки определяется пользователем
- Сценарии с логированием, алертингом, метриками

### Паттерн 08. [Маркеры состояния и конца потока (State/EOF Marker)](08_state_stream_marker.md)

__Требуемый стандарт:__ C11 (базовый)

__Идея:__ Функция возвращает специальный маркер (например, `EOF`, `NULL` для конца списка), который означает не ошибку, а естественное завершение потока данных. Это позволяет разделить два семантически разных события: «я не смог это сделать» (ошибка среды) и «я сделал, но данных больше нет» (норма). Смешивание этих состояний приводит к ложноположительным сбоям.

__Краткий пример сигнатуры:__

```c
// EOF — конец файла, не ошибка
int fgetc(FILE *stream);  // возвращает EOF при конце файла

// NULL — конец списка, не ошибка
node_t *list_get_next(list_t *list);

// Использование:
int c;
while ((c = fgetc(f)) != EOF) {
    process_char(c);
}
// После цикла: ferror(f) для разделения EOF и реальной ошибки
```

__Области применения:__

- Потоковое чтение данных (файлы, сокеты, каналы)
- Итераторы и обход структур данных (списки, деревья)
- Парсеры с естественным концом входных данных

### Паттерн 09. [Latched Error State (Залипающее состояние ошибки)](09_latched_error_state.md)

__Требуемый стандарт:__ C11 (базовый)

__Идея:__ Долгоживущий объект переводится в перманентно ошибочное состояние (`FAILED`) после первой фатальной ошибки. Все последующие вызовы методов объекта мгновенно возвращают стандартный код `ERR_STREAM_FAILED`, не обращаясь к системным ресурсам. Первая ошибка (Root Cause) консервируется в контексте и не может быть перезаписана последующими вызовами (инвариант Latch-Once). Это реализует принцип Circuit Breaker (предохранителя), защищая систему от каскадных сбоев и работы с поврежденным состоянием.

__Краткий пример сигнатуры:__

```c
typedef struct {
    int   failed;   // 0 = Ready, 1 = Failed
    error_state_t err;      // Зафиксированный Root Cause
    FILE         *f;        // Управляемый ресурс
} safe_file_t;

err_t safe_file_write(safe_file_t *sf, const void *buf, size_t len);
// Если sf->failed == 1, мгновенно возвращает ERR_STREAM_FAILED

const error_state_t *safe_file_last_error(const safe_file_t *sf);
// Возвращает снимок оригинального сбоя (или NULL, если объект жив)
```

__Области применения:__

- Долгоживущие объекты с фатальными ошибками (разрыв соединения, отказ диска)
- Сетевые сокеты, файловые потоки, клиенты СУБД
- Embedded-системы с аппаратными шинами (I2C, SPI, CAN)
- Сценарии, где работа с поврежденным состоянием опасна (use-after-fail)

## III. Паттерны управления потоком и ресурсами (Control Flow & Resources)

### Паттерн 10. [Goto-цепочки для централизованной очистки (Cleanup)](10_goto_cleanup.md)

__Требуемый стандарт:__ C11 (базовый)

__Идея:__ Использование `goto` и меток для детерминированного освобождения ресурсов в обратном порядке их захвата. Это единственный математически строгий способ избежать дублирования кода очистки в базовом C без привлечения расширений компилятора.

__Краткий пример сигнатуры:__

```c
err_t process_resources(const char *path) {
    err_t err = ERR_OK;
    
    FILE *f = fopen(path, "r");
    if (!f) return ERR_IO;
    
    void *buf = malloc(1024);
    if (!buf) { err = ERR_NO_MEM; goto cleanup_file; }
    
    // ... работа с ресурсами ...
    
cleanup_buf:
    free(buf);
cleanup_file:
    fclose(f);
    return err;
}
```

__Области применения:__

- Любые функции, захватывающие более одного ресурса (файлы, память, мьютексы, дескрипторы)
- Эталон для ядра Linux и встраиваемых систем
- Строгий ISO C без расширений компилятора

### Паттерн 11. [setjmp/longjmp (Нелокальные переходы)](11_setjmp_longjmp.md)

__Требуемый стандарт:__ C11 (базовый, `<setjmp.h>`)

__Идея:__ Сохранение контекста стека в точке `setjmp` и «размотка» стека к этой точке через `longjmp` при возникновении фатальной ошибки в глубокой рекурсии. Это механизм аварийного выхода из глубоко вложенного кода без передачи кода ошибки через все уровни.

__Краткий пример сигнатуры:__

```c
#include <setjmp.h>

static jmp_buf parse_env;

err_t parse_deep_structure(const char *input) {
    if (setjmp(parse_env) != 0) {
        // Сюда попадает управление при longjmp из глубины
        return ERR_PARSE_FAILED;
    }
    
    parse_recursive(input);  // Внутри — longjmp(parse_env, 1) при ошибке
    return ERR_OK;
}
```

__Области применения:__

- Парсеры с глубоким рекурсивным спуском (без захвата ресурсов)
- Реализация сопрограмт (coroutines) и кооперативной многозадачности
- Сценарии, где передача кода ошибки через десятки уровней вложенности непрактична

### Паттерн 12. [Эмуляция RAII через Scope Guards](12_raii_emulation_with_scope_guard.md)

__Требуемый стандарт:__ GCC/Clang Extension (`__attribute__((cleanup))`)

__Идея:__ Использование атрибута `cleanup` для автоматического вызова функции очистки при выходе переменной из области видимости (scope). Это эмуляция RAII из C++ на чистом C, делающая код линейным и исключающая утечки при ранних возвратах.

__Краткий пример сигнатуры:__

```c
// Функция очистки, привязанная к типу. 
// ВАЖНО: Проверка >= 0 безопасна ТОЛЬКО при строгой инициализации переменной значением -1.
// Если инициализировать fd = 0, функция закроет стандартный ввод (stdin) процесса!
static void cleanup_fd(int *fd) {
    if (*fd >= 0) close(*fd);
}

err_t do_work(const char *path) {
    // Строгая инициализация невалидным дескриптором обязательна
    int fd __attribute__((cleanup(cleanup_fd))) = -1;
    
    fd = open(path, O_RDONLY);
    if (fd < 0) return ERR_IO;
    
    // ... работа с fd, любые ранние return ...
    // При выходе из scope компилятор автоматически вызовет cleanup_fd(&fd)
    
    return ERR_OK;
}
```

__Области применения:__

- Современные user-space демоны (systemd, сетевые сервисы)
- Код на GCC/Clang, где `goto cleanup` становится слишком громоздким
- Сценарии с множественными точками раннего возврата из функции

## IV. Паттерны фатальных сбоев и инвариантов (Fatal Failures & Invariants)

### Паттерн 13. [Fail-Fast (инварианты, assert, аварийный выход)](13_fail_fast_assert.md)

__Требуемый стандарт:__ C11 (базовый, `<assert.h>`)

__Идея:__ При обнаружении нарушения внутренних инвариантов программы (багов программиста, а не ошибок среды) функция не пытается вернуть код ошибки, а немедленно прерывает выполнение процесса через `assert()` или явный `abort()`. Это философия «падай рано, падай громко» — лучше аварийный останов с полным core dump, чем тихая работа в неконсистентном состоянии, ведущая к повреждению данных или уязвимостям безопасности. Также данный паттерн известен как "Принцип Самурая".

__Краткий пример сигнатуры:__

```c
#include <assert.h>

// Макрос для production-сборок, где NDEBUG может отключить assert
#ifdef NDEBUG
    #define ASSERT_OR_CRASH(cond) \
        do { if (!(cond)) { abort(); } } while (0)
#else
    #define ASSERT_OR_CRASH(cond) assert(cond)
#endif

void process_buffer(uint8_t *buf, size_t len) {
    // Проверка предусловия: буфер не должен быть NULL
    ASSERT_OR_CRASH(buf != NULL);
    
    // Проверка инварианта: длина не должна превышать максимум
    ASSERT_OR_CRASH(len <= MAX_BUFFER_SIZE);
    
    // Если дошли сюда — инварианты соблюдены, можно работать
    for (size_t i = 0; i < len; i++) {
        buf[i] = transform(buf[i]);
    }
}
```

__Области применения:__

- Проверка предусловий/постусловий функций (контрактное программирование)
- Валидация внутренних инвариантов структуры данных (не внешних входных данных)
- Debug-сборки для раннего обнаружения багов разработчика
- Safety-critical системы с политикой fail-fast (авионика, медицинское оборудование)
- Сценарии, где продолжение работы в неконсистентном состоянии опаснее аварийного останова

## V. Продвинутые архитектурные паттерны (Advanced Architectural)

### Паттерн 14. [Error Context / Wrapping (Обогащение контекстом)](14_error_context_wrapping.md)

__Требуемый стандарт:__ C11 (базовый)

__Идея:__ При передаче ошибки вверх по стеку вызовов она не просто пробрасывается, а «оборачивается» дополнительным контекстом текущего уровня абстракции. Это позволяет сохранить оригинальную первопричину (Root Cause), но добавить к ней доменное понимание того, что именно пыталась сделать система в момент сбоя.

__Краткий пример сигнатуры:__

```c
typedef struct {
    err_t root_cause;
    const char *layer_context;
    const char *action_description;
} wrapped_error_t;

wrapped_error_t db_connect_and_query(const char *uri) {
    err_t err = network_connect(uri);
    if (err != ERR_OK) {
        return (wrapped_error_t){ 
            .root_cause = err, 
            .layer_context = "DatabaseModule",
            .action_description = "Failed to establish initial connection"
        };
    }
    // ...
}
```

__Области применения:__

- Многоуровневые архитектуры (сетевой слой → бизнес-логика → UI)
- Библиотеки, которые должны предоставлять понятные сообщения об ошибках, не теряя технические детали
- Системы расширенного логирования и трассировки (tracing)

### Паттерн 15. [Асинхронная / Событийная передача ошибок](15_async_event_error_transfer.md)

__Требуемый стандарт:__ C11 (базовый), POSIX (epoll/kqueue) или фреймворки (libuv, io_uring)

__Идея:__ В асинхронных моделях выполнения функция не блокирует поток и не возвращает ошибку немедленно. Вместо этого статус операции (успех или конкретный код ошибки) прикрепляется к объекту события, future-промісу или передается в callback завершения. Потребитель обязан проверить статус при обработке события.

__Краткий пример сигнатуры:__

```c
typedef struct {
    void *user_data;
    err_t status;
    size_t bytes_transferred;
} async_result_t;

typedef void (*async_callback_t)(const async_result_t *result);

// Операция инициируется, но результат придет позже через callback
err_t async_read_file(const char *path, async_callback_t cb, void *user_data);
```

__Области применения:__

- Event-loop серверы и высоконагруженные сетевые приложения
- Асинхронный ввод-вывод (AIO, io_uring, libuv)
- GUI-приложения и фоновые задачи, где блокировка потока недопустима

### Паттерн 16. [Типобезопасные Tagged Unions через `_Generic`](16_type_safety_tagged_union.md)

__Требуемый стандарт:__ C11 (ключевое слово `_Generic`)

__Идея:__ Использование механизма выбора типа `_Generic` для создания полиморфных макросов, которые безопасно извлекают данные или обрабатывают ошибки из обобщенных структур (Tagged Union) без явного приведения типов. Это предотвращает ошибки несоответствия типов на этапе компиляции, эмулируя перегрузку функций.

__Краткий пример сигнатуры:__

```c
typedef struct {
    bool is_error;
    union {
        int int_val;
        double double_val;
        err_t err_code;
    } data;
} generic_result_t;

// Макрос безопасно извлекает значение нужного типа или обрабатывает ошибку
#define GET_RESULT(res, type) _Generic((res).data, \
    int: (res).is_error ? handle_err((res).data.err_code) : (res).data.int_val, \
    double: (res).is_error ? handle_err((res).data.err_code) : (res).data.double_val \
)

// Использование:
generic_result_t res = parse_value(input);
int val = GET_RESULT(res, int);
```

__Области применения:__

- Обобщенные (generic) библиотеки и коллекции данных
- Математические или парсинговые функции, работающие с несколькими типами данных
- API, требующие строгой типобезопасности без дублирования кода для каждого типа

## VI. Паттерны контрактного программирования и принуждения (Enforcement)

### Паттерн 17. [Compiler-Enforced Return Checking (Принудительная проверка возврата)](17_compiler_enforced_return_checking.md)

__Требуемый стандарт:__ C23 (`[[nodiscard]]`) или GCC/Clang Extensions (`__attribute__((warn_unused_result))`)

__Идея:__ Использование атрибутов компилятора для генерации предупреждения или ошибки сборки, если возвращаемое значение функции (статус ошибки, владеющий указатель или результат валидации) было проигнорировано вызывающим кодом. Это переносит контроль ошибок из плоскости человеческой дисциплины в плоскость статического анализа на этапе компиляции.

__Краткий пример сигнатуры:__

```c
// C23 (стандартный переносимый подход)
[[nodiscard]] err_t init_system(void);

// GCC/Clang (расширение для C11/C17)
__attribute__((warn_unused_result)) err_t init_system(void);
```

__Области применения:__

- Любые API, где игнорирование статуса ведёт к неопределённому поведению (UB) или утечкам ресурсов.
- Функции, возвращающие владеющие указатели или результаты аллокации памяти.
- Функции валидации, проверки криптографических подписей и выхода за границы буфера (security-critical).
- Методы долгоживущих объектов, находящихся в «залипшем» состоянии (синергия с Паттерном 09).
