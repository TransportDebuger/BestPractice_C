- Понимание различий между ошибками среды/ввода и ошибками разработки (инвариантов).
- Базовое знание `assert.h` и функций аварийного завершения (`abort`, `exit`).

objective:

- Описать философию Fail-Fast в контексте C: когда и зачем программа должна падать, а не «лечить» ошибку.
- Жестко разграничить ошибки среды (13.2) и ошибки инвариантов (13.1).
- Разобрать концепцию «сохранения места преступления» (Core Dumps) и использование атрибутов `_Noreturn`.
- Предотвратить критическую ошибку «NDEBUG-ловушки» при работе с памятью.

theory:
  Принцип Fail-Fast: «об ошибках нужно узнавать как можно раньше и как можно громче». Программа должна немедленно завершаться при нарушении внутренних инвариантов, вместо того чтобы продолжать работу в потенциально некорректном состоянии.\
  В C, в отсутствие исключений и RAII, попытка «проглотить» ошибку инварианта (вернуть `err_t` и продолжить работу) почти гарантированно ведет к тихой порче данных, уязвимостям безопасности или катастрофическим сбоям гораздо позже по стеку вызовов.\
  Важно разделять два класса фатальных сбоев:

  1. __Ошибки инвариантов/логики (13.1):__ Баги в коде. Нарушение контрактов. Они не должны происходить в корректной программе. Лечатся только исправлением кода.
  2. __Невосстановимые средовые ошибки (13.2):__ Крах среды (OOM, переполнение стека). Продолжение работы невозможно или опасно.
  Для обоих классов оправдано использование немедленного аварийного завершения (`abort()`), но инструменты и философский контекст их применения различаются.

## 1. Философия Fail-Fast и «Сохранение места преступления»

### 1.1. Почему мы должны падать?

Если функция обнаруживает, что переданный указатель `NULL` (хотя контракт требует `non-NULL`), или что внутренняя связность списка нарушена — это не «ошибка пользователя», это __баг разработки__.
Если мы вернем `ERR_INVALID_ARG` (как описано в [Паттерне 01](01_return_code_out_params.md)), стек вызовов свернется. К моменту, когда ошибка достигнет `main()` и будет залогирована, мы уже не будем знать, *кто именно* и на каком кадре стека испортил данные.

Если же мы вызовем `abort()`, операционная система сгенерирует __Core Dump__. Разработчик откроет его в `gdb` и увидит точный кадр стека, где инвариант был нарушен. Это главное преимущество Fail-Fast: __сохранение места преступления для отладчика__.

### 1.2. Инструменты Fail-Fast в C

- __`assert(condition)`__ из `<assert.h>`: в отладочной сборке (без `NDEBUG`) при невыполнении условия печатает сообщение и завершает программу (через `abort`).
- __Явные проверки с `abort()`__: используются для проверок, которые должны работать *всегда*, включая Release-сборки (например, для средовых ошибок или критичных предусловий публичного API).
- __Атрибуты `_Noreturn` (C11) / `__attribute__((noreturn))`__: указывают компилятору, что функция не возвращает управление, что улучшает оптимизацию и устраняет ложные предупреждения.

## 2. 13.1. Defensive Programming (Ошибки инвариантов)

### 2.1. Что относится к инвариантам

- Указатель, помеченный как `non-NULL` в контракте, оказался `NULL` внутри функции.
- Внутренние структуры данных имеют нарушенную связность (например, `size > 0`, но `head == NULL`).
- Индекс массива выходит за допустимые пределы, хотя логика выше должна была это исключить.

### 2.2. Использование `assert` и кастомных макросов

Стандартный `assert` хорош для тяжелых проверок в Debug-сборках. Но для критичных предусловий API (которые должны защищать библиотеку даже в Release) используют кастомные макросы, работающие всегда.

```c
#include <stdio.h>
#include <stdlib.h>

// Используем _Noreturn (C11) для подсказки компилятору
_Noreturn void fatal_error(const char *msg, const char *file, int line) {
    fprintf(stderr, "FATAL [%s:%d]: %s\n", file, line, msg);
    abort(); // Генерирует Core Dump
}

#define REQUIRE(cond, msg) \
    do { \
        if (!(cond)) { \
            fatal_error("Precondition failed: " msg, __FILE__, __LINE__); \
        } \
    } while (0)

#define ENSURE(cond, msg) \
    do { \
        if (!(cond)) { \
            fatal_error("Postcondition failed: " msg, __FILE__, __LINE__); \
        } \
    } while (0)
```

__Использование:__

```c
void list_push_front(list_t *list, int value) {
    REQUIRE(list != NULL, "list must not be NULL");
    REQUIRE(list->size == 0 || list->head != NULL, "internal invariant violated");
    
    // ... логика ...
    
    ENSURE(list->size > 0, "size must be positive after push");
}
```

## 3. 13.2. Невосстановимые средовые ошибки (Environmental Collapse)

### 3.1. Когда среда умирает

Ситуации, когда продолжение работы невозможно или опасно:

- __Out Of Memory (OOM):__ `malloc` вернул `NULL`.
- __Переполнение стека:__ Рекурсия ушла в бесконечность.
- __Критический сбой драйвера/ОС:__ Невозможно восстановить файловый дескриптор или сокет.

### 3.2. Политика проекта: OOM

В классическом C `OOM` считается ошибкой среды (возвращаем `ERR_NO_MEM` через [Паттерн 01](01_return_code_out_params.md)). Однако в современных высоконагруженных и safety-critical системах (включая ядро Linux) `OOM` часто трактуется как __фатальная ошибка__, потому что восстановление после частичной аллокации слишком сложно и ведет к уязвимостям.
Если политика проекта считает OOM фатальным, мы используем явный `abort()`, а не `assert()`.

## 4. Критическая ловушка: «NDEBUG-ловушка» (Must Read)

Это самая частая и катастрофическая ошибка разработчиков, пришедших из других языков или читающих устаревшие туториалы.

__Антипаттерн:__

```c
node_t *n = malloc(sizeof(*n));
assert(n != NULL); // <--- КРИТИЧЕСКАЯ ОШИБКА
n->value = value;
```

__Почему это катастрофа:__
Стандартный `assert` __полностью вырезается компилятором__, если определен макрос `NDEBUG` (а в Release-сборках он определяется всегда).
В Release-сборке при нехватке памяти `malloc` вернет `NULL`. `assert` проигнорируется, и следующая строка `n->value = value;` приведет к __Segmentation Fault__ (разыменованию NULL) или, что хуже, к тихой порче памяти по нулевому адресу.

__Правильный подход:__
Результат `malloc` (и других системных вызовов) __никогда__ не проверяется через `assert`. Это ошибка среды, а не инвариант.

```c
node_t *n = malloc(sizeof(*n));
if (!n) {
    // OOM — это ошибка среды. 
    // Если политика проекта требует fail-fast при OOM:
    fprintf(stderr, "FATAL: Out of memory in list_push_front\n");
    abort(); 
    
    // ИЛИ: return ERR_NO_MEM; (если среда позволяет восстановление и очистку через goto/Паттерн 10)
}
n->value = value;
```

## 5. Подсказки компилятору и оптимизация

### 5.1. Атрибут `_Noreturn`

Если вы пишете кастомный `fatal_error` или `panic`, помечайте его как `_Noreturn` (C11). Это помогает компилятору не выдавать ложных предупреждений (например, «missing return statement») и лучше оптимизировать стек.

```c
_Noreturn void my_panic(const char *msg) {
    log_fatal(msg);
    abort();
}
```

### 5.2. `__builtin_unreachable()`

Если мы проверили инвариант и вызвали `abort()`, мы можем сказать компилятору, что код после этой точки недостижим. Это позволяет убрать лишние проверки (например, bounds checking в `switch`) и сгенерировать более эффективный код.

```c
err_t lib_process(lib_ctx_t *ctx, const char *input) {
    REQUIRE(ctx != NULL, "ctx must not be NULL");
    
    switch (ctx->mode) {
        case MODE_A: return do_a(ctx, input);
        case MODE_B: return do_b(ctx, input);
        default: 
            fatal_error("Unknown mode", __FILE__, __LINE__);
            __builtin_unreachable(); // Подсказка GCC/Clang
    }
}
```

## 6. Fail-Fast vs Обработка ошибок среды (Резюме)

| Характеристика | Ошибки среды/ввода (Паттерны 01-12) | Ошибки инвариантов / Сбой среды (Паттерн 13) |
| :--- | :--- | :--- |
| __Природа__ | Нормальны, ожидаемы (файл не найден, нет сети, `ENOMEM`). | Баги (нарушение контрактов) или крах ОС (`OOM`, `Stack Overflow`). |
| __Действие__ | Обработать мягко: retry, fallback, лог, возврат `err_t`. | Немедленное падение (`abort()`). |
| __Инструмент__ | `err_t`, `Result`, `errno`, `goto cleanup`, Scope Guards. | `assert()`, `REQUIRE()`, `abort()`, `exit()`. |
| __Цель__ | Восстановить работу, сохранить данные. | Сохранить Core Dump, предотвратить порчу данных. |

## 7. Практические рекомендации (Best Practices)

1. __Никогда не используйте `assert` для проверки результатов системных вызовов.__ `malloc`, `fopen`, `socket`, `pthread_create` могут легально вернуть ошибку из-за состояния среды. Используйте явные проверки `if (!ptr)`.
2. __Используйте `_Noreturn` для функций аварийного завершения.__ Если вы пишете кастомный `fatal_error`, помечайте его как `_Noreturn`.
3. __Разделяйте Debug и Release политики.__ Стандартный `assert` хорош для тяжелых проверок инвариантов в Debug-сборках. Но для критичных предусловий публичного API используйте макросы вроде `REQUIRE`, которые работают и в Release, чтобы защитить библиотеку от некорректного использования внешним кодом.
4. __Настройте сбор Core Dumps.__ Fail-Fast имеет смысл только тогда, когда вы можете проанализировать падение. Убедитесь, что в вашей ОС и окружении (Docker, systemd) настроено сохранение core-дампов (`ulimit -c unlimited`, `core_pattern`).
5. __Не маскируйте баги.__ Если вы поймали себя на том, что возвращаете `ERR_INTERNAL` вместо `abort()` из-за `NULL`-указателя, который *не может* быть `NULL` по логике выше — остановитесь и исправьте код. Вы создаете «зомби-состояние».
