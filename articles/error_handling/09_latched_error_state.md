# Паттерн обработки ошибок: Latched Error State (залипающее состояние ошибки)

__Дата:__ "2026-10-28"\
__Версия:__ "v1.0"\
__Стандарты:__ "C11 (ISO/IEC 9899:2011, `_Atomic`); GCC/Clang Extensions (`__attribute__((warn_unused_result))`); C23 (ISO/IEC 9899:2024, атрибут `[[nodiscard]]`)"

__Предварительные требования__:

- Понимание базовых контрактов возврата: [Паттерн 01](01_return_code_out_params.md) (`err_t` + out-параметры), [Паттерн 02](02_sentinel_errno.md) (Sentinel + `errno`), [Паттерн 03](03_return_val_param_err_t.md) (Return value + `err_t *`), [Паттерн 04](04_result_struct.md) (Struct Result / Tagged Union). Latched State является ортогональной надстройкой и совместим с любым из этих контрактов.
- Знакомство с [Паттерном 06: Контекст ошибок](06_error_context.md) — базой, на которую накладывается конечный автомат latched state.
- Знакомство с [Паттерном 17: Compiler-Enforced Return Checking](17_compiler_enforced_return_checking.md) — механизмами принудительной проверки возврата (`[[nodiscard]]`, `warn_unused_result`).
- Опыт работы с объектами/контекстами, имеющими жизненный цикл (init/use/destroy).
- Базовое понимание многопоточности и атомарных операций C11 (`_Atomic`, `atomic_compare_exchange_strong`).
- Знакомство с [Каталогом паттернов](00_pattern_catalog.md).

__Цель:__

- Описать паттерн Latched Error State как инструмент перевода долгоживущих контекстов в необратимое состояние отказа (Circuit Breaker) для защиты системы от работы с поврежденными инвариантами (сценарии Use-After-Fail).
- Сформулировать инвариант «однократной записи» (Latch-Once) и доказать его необходимость для гарантированной консервации первопричины сбоя (Root Cause) и предотвращения каскадного размытия логов.
- Разбрать системные риски параллельного исполнения: показать, как наивная реализация автоматов состояния приводит к состояниям гонки (Data Races), и предоставить безопасные шаблоны синхронизации на базе атомарных примитивов стандарта C11.
- Продемонстрировать паттерны взаимодействия клиентского кода с «мертвым» объектом для безопасного извлечения посмертной диагностики и принятия решений о программном сбросе или утилизации ресурса.

__Теория__:

Обычные функции в языке Си работают как одноразовые транзакции: вызвали, получили результат (или ошибку) и забыли. Но когда мы работаем с долгоживущими объектами — например, открытым файлом, сетевым сокетом или контекстом библиотеки — ситуация меняется. У таких объектов появляется «память» и свой жизненный цикл.

__Проблема: Эффект домино (Каскадный сбой)__
Представьте, что вы пишете программу, которая записывает данные в файл. В середине процесса на диске внезапно закончилось место. Функция записи честно вернет вам ошибку. Но язык Си устроен так, что компилятор технически не может запретить вам (или вашему коллеге) вызвать функцию записи для этого файла еще раз, и еще раз, и еще раз.

Это приводит к двум серьезным проблемам:

1. __Размытие настоящей причины (Root Cause):__ Первый вызов упал, потому что «диск полон». Второй вызов упадет с ошибкой «сломался указатель». Третий — «память повреждена». В итоге в системных логах начнется хаос, и вы потратите часы, пытаясь понять, какая именно ошибка была самой первой и сломала систему.
2. __Тихая порча данных:__ Продолжая вызывать методы уже «сломанного» объекта, программа начинает работать с непредсказуемым внутренним состоянием. Это классический путь к трудноловимым багам и уязвимостям.

__Решение: Принцип предохранителя (Circuit Breaker)__
Паттерн `Latched Error State` (Залипающее состояние ошибки) превращает объект в умный предохранитель. Мы встраиваем внутрь объекта простейший конечный автомат (переключатель), у которого есть три состояния:

1. __Init (Инициализирован):__ Объект только что создан.
2. __Ready (Готов к работе):__ Объект исправно выполняет команды.
3. __Failed (Залип в ошибке):__ Объект встретил критический сбой и «умер».

Смысл паттерна в том, что переход в состояние __FAILED__ является __билетом в один конец__. Как только объект ломается, он «защелкивается» (latch).

Ключевой философский принцип: __объект, перешедший в состояние FAILED, больше не имеет права изменять свою диагностику__. Первая ошибка, убившая объект, должна быть сохранена навсегда, так как все последующие ошибки будут лишь ее следствием (симптомами, а не причиной).

Внедрение этого переключателя дает разработчику три важнейшие гарантии:

- __Защита от каскадных сбоев:__ Если объект перешел в состояние `FAILED`, все последующие вызовы любых его методов будут мгновенно возвращать стандартный код `ERR_STREAM_FAILED`. Объект отказывается выполнять команды, защищая систему от работы с непредсказуемым внутренним состоянием (use-after-fail).
- __Консервация первой ошибки:__ Первая ошибка, которая «убила» объект, записывается в его память навсегда. Все последующие вызовы не имеют права перезаписать это сообщение. Благодаря этому вы всегда точно знаете оригинальный диагноз «смерти» объекта, сколько бы вызовов после этого ни произошло.
- __Упрощение обработки ошибок:__ После первого сбоя все последующие вызовы возвращают один и тот же код `ERR_STREAM_FAILED`. Вызывающему коду не нужно анализировать каждый новый код ошибки — он уже знает, что объект мертв, и может сосредоточиться на одной задаче: чтении root cause и принятии решения о восстановлении или отказе.

## 1. Описание паттерна и строгий контракт

### 1.1. Формальное описание и контракт

Структура `error_state_t` реализует [Паттерн 06 (Контекст ошибок)](06_error_context.md) — базовый механизм хранения кода ошибки и строкового сообщения. Паттерн Latched State является надстройкой над этим контекстом, добавляя конечный автомат состояния.

Интерфейсная часть модуля (заголовочный файл `safe_file.h`):

```c
#ifndef SAFE_FILE_H
#define SAFE_FILE_H

#include <stdio.h>
#include <stdatomic.h>
#include "compiler_attrs.h" // Проектный заголовок с макросом NODISCARD (см. Паттерн 17)
// или #include <sal.h> — если используется MSVC и нужна проверка использования возврата без проектного заголовка

typedef enum {
    ERR_OK = 0,
    ERR_INVALID_ARG,
    ERR_IO,
    ERR_STREAM_FAILED
} err_t;

typedef struct {
    err_t code;
    char  message[128]; // Фиксированный буфер: жесткая защита от OOM при обработке ошибок
} error_state_t;

struct safe_file_impl {
    _Atomic int failed;      // C11: Атомарный флаг состояния автомата (0 - Ready, 1 - Failed)
    error_state_t err;       // Зафиксированный снимок первоначальной ошибки (Root Cause)
    FILE *f;                 // Управляемый низкоуровневый системный ресурс
};
typedef safe_file_impl safe_file_t;

/*
 * Выполняет упорядоченную запись буфера в поток.
 * Обеспечивает статическую проверку возвращаемого значения на уровне компилятора.
 * Вместо NODISCARD проектного заголовка, можно использовать:
 *  - C23: [[nodiscard]]
 *  - GCC/Clang: __attribute__((warn_unused_result))
 *  - MSVC: _Check_return_ //Не забудьте #include <sal.h>
 */
NODISCARD
err_t safe_file_write(safe_file_t *sf, const void *buf, size_t len);

/*
 * Возвращает указатель на неизменяемый контекст залипшей ошибки.
 * Если объект исправен (failed == 0), возвращает NULL.
 */
const error_state_t *safe_file_last_error(const safe_file_t *sf);

#endif /* SAFE_FILE_H */
```

__Жесткие контракты и архитектурные инварианты:__

1. __Инвариант «Latch-Once» (Однократная фиксация):__ Как только внутренний флаг `failed` переходит в состояние `1`, диагностическое поле `err` становится __read-only__ (строго неизменяемым). Любые попытки повторной записи или каскадные сбои операционной среды полностью игнорируются подсистемой логирования. Клиент защищен от получения вторичных симптомов сбоя.
2. __Инвариант сквозного детерминизма out-параметров:__ Если методы «мертвого» объекта (находящегося в состоянии `FAILED`) предполагают возврат данных через `out`-указатели согласно [Паттерну 01](01_return_code_out_params.md), эти указатели __обязаны быть обнулены__ до возврата кода `ERR_STREAM_FAILED`. Быстрый аварийный выход из функции не освобождает разработчика от зануления внешних каналов данных.
3. __Детерминизм строкового сообщения:__ Поле `err.message` гарантированно содержит нуль-терминатор `\0` на любой позиции буфера. Прямое копирование через небезопасный `strncpy` или `strcpy` запрещено; фиксация строки производится исключительно через `snprintf`, контролирующий размер приемника.
4. __Атомарность транзакции автомата:__ Чтение флага `failed` и его перевод в аварийное состояние должны происходить в рамках единой неделимой операции (атомарный барьер памяти), исключающей состояние гонки (Data Race) между параллельными потоками управления (подробнее см. Раздел 5).

### 1.2. Когда паттерн уместен

Паттерн 09 является аддитивной надстройкой над контрактами возврата и контекстом ошибок. Его применимость определяется следующими осями:

__Уровень кода (Layer):__

- __LOW (Системный):__ ✅ Применяется. Драйверы устройств, embedded-системы, взаимодействие с аппаратными шинами (I2C, SPI, CAN). При аппаратном сбое периферийный контекст защёлкивается до физического сброса.
- __MID (Доменный):__ ✅ Применяется. Библиотеки среднего уровня с долгоживущими объектами (соединения с БД, файловые потоки, сетевые сокеты). При фатальном сбое объект переходит в `FAILED`, все последующие вызовы мгновенно отклоняются.
- __HIGH (Прикладной):__ ⚠️ Применяется редко. Только для долгоживущих объектов (например, HTTP-клиент с пулом соединений). Для одноразовых операций избыточен.

__Модель выполнения (Execution Model):__

- __Sync (Синхронная):__ ✅ Применяется. Стандартный сценарий — объект защёлкивается после первой фатальной ошибки.
- __Async (Асинхронная):__ ✅ Применяется. В event-loop серверах каждый сокет — долгоживущий объект. При разрыве соединения сокет переходит в `FAILED`, все последующие сабмиты мгновенно отклоняются с кодом `ERR_STREAM_FAILED`.

__Природа ошибки (Error Nature):__

- __Environment (Среда):__ ✅ Применяется. Разрыв соединения (`EPIPE`, `ECONNRESET`), потеря связи с диском, аппаратный сбой. Объект переводится в `FAILED`.
- __Domain (Доменная):__ ⚠️ Применяется осторожно. Только если доменная ошибка необратимо повреждает внутреннее состояние объекта (например, нарушение протокола, повреждение буфера). Восстановимые доменные ошибки (валидация входных данных) не должны «убивать» объект.
- __Invariant (Инвариант):__ ❌ Не применяется. Нарушение инвариантов кода — это баг, а не состояние объекта. Используйте Паттерн 13 (Fail-Fast).

__Длительность жизни объекта (Object Lifetime):__

- __Stateless (Без состояния):__ ❌ Не применяется. У объекта нет «памяти» и жизненного цикла. Latched State избыточен.
- __Stateful (С состоянием):__ ✅ Применяется. Критически важен для долгоживущих объектов, где фатальная ошибка делает последующие операции бессмысленными или опасными.

__Критичность к производительности (Performance Criticality):__

- __Hard Real-Time:__ ⚠️ Применяется осторожно. Атомарные операции (`atomic_compare_exchange_strong`) могут быть дороги на некоторых платформах. Если объект не используется из нескольких потоков, можно использовать неатомарный флаг с документацией однопоточности.
- __Soft Real-Time:__ ✅ Применяется.
- __Non-Real-Time:__ ✅ Применяется.

__Архитектурный вывод:__ Паттерн 09 применим __только для долгоживущих объектов (Stateful)__, где фатальная ошибка необратимо повреждает внутреннее состояние. Для одноразовых функций или восстановимых ошибок используйте стандартные контракты возврата.

#### Прикладные сценарии применения

При выборе использовать данный паттерн или нет необходимо ответить на __Ключевой инженерный вопрос для принятия решения:__
> *"Если этот долгоживущий объект встретит данную ошибку, будет ли его внутреннее состояние необратимо повреждено, делая любые последующие операции бессмысленными или опасными?"*

Если ответ — __"Да, повреждено и опасно"__, применяйте Latched State. Если ответ — __"Нет, можно повторить транзакцию или исправить параметры"__ — используйте стандартные контракты возврата ошибок.

Чтобы сделать оси осязаемыми, рассмотрим четыре реальных сценария, где Latched State становится незаменимым:

__1. Файловые и системные потоки вывода (I/O Streams).__
Вы пишете программу, непрерывно ведущую системный лог на диск. В середине работы диск заполняется — `fwrite()` возвращает ошибку. Без защёлкивания каждый последующий вызов функции логирования будет дёргать ядро ОС, возвращать ошибку и забивать логи каскадом вторичных сбоев (вроде «bad descriptor»). Паттерн сохраняет первопричину («disk full»), а все последующие вызовы мгновенно отсекаются на уровне приложения с кодом `ERR_STREAM_FAILED`.

__2. Сетевые интерфейсы и Stream-like API.__
При фиксации десинхронизации протокола (битый фрейм данных) или закрытии несущего сокета операционной системой (`EPIPE` / `ECONNRESET`) дальнейшие транзакции через текущие буферы бессмысленны и разрушительны для памяти. Объект переводится в состояние предохранителя, аппаратно блокируя сетевой стек от отправки некорректных данных.

__3. Транзакционные клиенты СУБД.__
При потере связи с сервером или падении пула соединений (класс ошибок `SQLSTATE 08xxx` — Connection Exception) текущий дескриптор сессии признаётся необратимо повреждённым. Автомат предотвращает отправку последующих бизнес-запросов в «зависшую» сеть, принуждая клиентский слой явно утилизировать и пересоздать хэндл.

__4. Интерфейсы драйверов и Embedded-систем.__
При фиксации аппаратного таймаута шины (`I2C`, `SPI`, `CAN`) периферийный контекст защёлкивается в состоянии ошибки. Это предохраняет управляющую логику от накопления или чтения некорректных (устаревших) показаний датчиков. Объект удерживает аварийное состояние до тех пор, пока не будет вызван явный программный или физический сброс (`Reset`).

#### Когда паттерн НЕ уместен (антипаттерны)

- __Одноразовые функции (Stateless API).__ Если функция вызывается один раз и сразу возвращает изолированный результат (например, `parse_int("42")`), Latched State избыточен — у объекта нет накопленного состояния и распределённого во времени жизненного цикла.
- __Восстановимые ошибки (Recoverable Errors).__ Если ошибка носит транзитный характер (`EAGAIN` — «попробуйте позже», `EINTR` — «вызов прерван сигналом», или сетевой таймаут с легальной возможностью повтора), объект не должен умирать. Защёлкивание автомата на таких ошибках парализует работу системы.
- __Короткоживущие объекты (локальный scope).__ Если контекст живёт исключительно в рамках выполнения одной функции (локальная структура на стеке), внедрение конечного автомата усложняет код без получения архитектурной выгоды — объект всё равно будет уничтожен при выходе из области видимости.

Подробное описание осей применимости и их комбинаций см. в [Стратегии выбора](00_strategy_and_selection.md), раздел 2.1.

## 2. Плюсы и минусы

### 2.1. Плюсы

- __Конструктивный Fail-Fast:__ Исключает риски скрытого выполнения кода в деградировавшем окружении (Use-After-Fail), предотвращая порчу данных в памяти подсистемы.
- __Стабилизация диагностического лога:__ Устраняет «эффект домино», блокируя генерацию вторичных каскадных ошибок и сохраняя снимок оригинального сбоя (Root Cause).
- __Упрощение обработки ошибок после первого сбоя:__ После того как объект перешел в состояние FAILED, все последующие вызовы возвращают один и тот же код ERR_STREAM_FAILED. Клиенту не нужно анализировать каждый новый код ошибки — он уже знает, что объект мертв, и может сосредоточиться на одной задаче: чтении root cause и принятии решения о восстановлении или отказе.
- __Изоляция потока управления:__ Упрощает написание верхнеуровневых диспетчеров задач. Мертвый объект сам декларирует свою невалидность, избавляя клиентские слои от ручного анализа внутренней консистентности контекста.

### 2.2. Минусы и риски

- __Архитектурная сложность классификации:__ На этапе проектирования API требуется жесткое разделение ошибок на транзитные (Recoverable) и терминальные (Fatal). Ошибка классификации превращает защиту в уязвимость, парализуя систему ложными блокировками.

> [!ATTENTION]
> __Критический риск:__ Если по ошибке пометить восстанавливаемую ошибку (например, `EAGAIN`, `EINTR` или кратковременный таймаут сети) как фатальную, объект «умрет» преждевременно. Это превращает защитный механизм в уязвимость, парализуя систему ложными блокировками и самоиндуцированным отказом в обслуживании (Denial of Service).

- __Требование явного управления жизненным циклом:__ Как и любой API с ресурсами, Latched State требует от клиента явного вызова деструктора (safe_file_close()) после обнаружения фатальной ошибки. Автомат защищает инварианты памяти, но не освобождает от управления дескрипторами. Это общее свойство C, а не специфика паттерна.
- __Критические риски параллелизма (Data Races):__ Небрежная (неатомарная) проверка и мутация флага состояния в многопоточной среде мгновенно разрушают инвариант однократной записи, приводя к трудноотлаживаемому Undefined Behavior.
- __Усложнение изоляции в Юнит-тестах:__ Объекты с жестким внутренним состоянием необратимости требуют полной переинициализации (или внедрения специализированных бэкдоров сброса статуса) между тестовыми сценариями, усложняя написание легковесных тестов.

## 3. Простой пример: Безопасный файловый поток

### 3.1. Реализация с инвариантом Latch-Once

Реализационная часть модуля (исходный код `safe_file.c`):

```c
#include <stdio.h>
#include <string.h>
#include <stdatomic.h>
#include "safe_file.h" // Заголовок (см. раздел 1.1)

/*
 * Вспомогательная внутренняя функция фиксации терминального состояния.
 * Реализует инвариант Latch-Once, защищая диагностические данные от перезаписи.
 */
static void safe_file_set_error(safe_file_t *sf, err_t code, const char *msg) {
    if (!sf) return;
    
    // Пытаемся атомарно захватить право на запись ошибки.
    // Если sf->failed уже равен 1, atomic_compare_exchange_strong вернет false,
    // и мы немедленно выйдем, сохранив самый первый, оригинальный Root Cause.
    int expected = 0;
    if (!atomic_compare_exchange_strong(&sf->failed, &expected, 1)) {
        return; 
    }
    
    // ВАЖНО (Потокобезопасность): 
    // atomic_compare_exchange_strong по умолчанию использует memory_order_seq_cst,
    // создавая полный барьер памяти. Это гарантирует, что записи в sf->err, 
    // выполненные НИЖЕ этого места, станут видны читающим потокам только после 
    // того, как они увидят sf->failed == 1 через atomic_load.
    sf->err.code = code;
    
    // snprintf детерминирован: гарантированно ставит '\0' и не выходит за границы буфера
    snprintf(sf->err.message, sizeof(sf->err.message), "%s", msg ? msg : "Unknown error");
}

NODISCARD
err_t safe_file_write(safe_file_t *sf, const void *buf, size_t len) {
    // Граничные проверки контракта данных (Паттерн 01)
    if (!sf || !buf) return ERR_INVALID_ARG;

    // БЫСТРЫЙ ВЫХОД (Circuit Breaker): 
    // Если автомат уже защелкнут в состоянии FAILED, мгновенно блокируем 
    // операцию без обращения к нижележащему системному ресурсу.
    if (atomic_load(&sf->failed)) {
        return ERR_STREAM_FAILED;
    }

    // Попытка выполнения системной транзакции записи
    size_t n = fwrite(buf, 1, len, sf->f);
    if (n != len) {
        // Зафиксирован критический сбой I/O среды (например, диск полон).
        // Переводим конечный автомат объекта в терминальное состояние FAILED.
        safe_file_set_error(sf, ERR_IO, "fwrite failed: disk full or broken pipe");
        
        // При ПЕРВОМ (терминальном) сбое возвращаем реальную физическую причину
        return ERR_IO; 
    }

    return ERR_OK;
}

const error_state_t *safe_file_last_error(const safe_file_t *sf) {
    if (!sf) return NULL;
    
    // Если автомат не защелкнут, возвращать «посмертную» диагностику бессмысленно
    if (atomic_load(&sf->failed) == 0) {
        return NULL;
    }
    
    return &sf->err;
}
```

## 4. Взаимодействие с клиентским кодом (Чтение Root Cause)

Главная ценность паттерна раскрывается в том, как клиентский слой взаимодействует с «мертвым» объектом, извлекая посмертную диагностику без риска разрушения логики приложения.

Исходный код клиентского приложения (`main.c`):

```c
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <stdatomic.h>
#include "safe_file.h"

int main(void) {
    // Безопасное выделение контекста на стеке вызывающей стороны
    safe_file_t sf;
    
    // Инициализация ресурсов подсистемы
    sf.f = fopen("out.bin", "wb");
    if (!sf.f) {
        perror("Фатальная ошибка открытия физического файла");
        return EXIT_FAILURE;
    }
    
    // ВАЖНО (Многопоточность): Атомарные поля типа _Atomic инициализируются 
    // исключительно через специализированную рантайм-функцию atomic_init.
    // Использование сырых назначенных инициализаторов Си для атомиков запрещено.
    atomic_init(&sf.failed, 0);
    memset(&sf.err, 0, sizeof(sf.err)); // Гарантированный детерминизм полей памяти

    char data[] = "Industrial telemetry payload";
    
    // Имитируем распределенную серию транзакций записи.
    // Если в середине первой записи диск переполнится, автомат защелкнется в FAILED.
    err_t err = safe_file_write(&sf, data, sizeof(data));
    
    // Демонстрация силы Latched State: мы можем вызвать функцию повторно, 
    // даже не проверяя результат предыдущего шага. Если объект уже "мертв", 
    // он не обратится к диску и не вызовет UB, а мгновенно вернет ERR_STREAM_FAILED.
    err = safe_file_write(&sf, data, sizeof(data)); 
    
    // Централизованная валидация терминального статуса подсистемы (проверяем один раз в конце)
    if (err != ERR_OK) {
        if (err == ERR_STREAM_FAILED) {
            // Объект перешел в состояние отказа ДО текущего вызова (или во время него).
            // Извлекаем неизменяемый снимок оригинального сбоя (Root Cause)
            const error_state_t *root_cause = safe_file_last_error(&sf);
            if (root_cause) {
                fprintf(stderr, "Критический отказ подсистемы. Первопричина: [%d] %s!\n", 
                        root_cause->code, root_cause->message);
            }
        } else {
            // Текущая транзакция зафиксировала ПЕРВЫЙ (терминальный) сбой.
            const error_state_t *root_cause = safe_file_last_error(&sf);
            if (root_cause) {
                fprintf(stderr, "Поток уничтожен текущим вызовом. Причина: [%d] %s\n", 
                        root_cause->code, root_cause->message);
            }
        }
        
        // Обязательная явная утилизация системного дескриптора (см. Раздел 2.2)
        fclose(sf.f);
        return EXIT_FAILURE;
    }
    
    // Штатное завершение жизненного цикла объекта
    fclose(sf.f);
    return EXIT_SUCCESS;
}
```

## 5. Критические риски: Многопоточность и Атомарность

### 5.1. Гонка данных (Data Race)

Если один и тот же экземпляр `safe_file_t` конкурентно используется из двух параллельных потоков без внешних мьютексов, возникает критический риск. Если хотя бы один из потоков выполняет __неатомарную__ операцию чтения или записи флага `failed` (например, `if (sf->failed)` вместо `atomic_load(&sf->failed)`), в рамках стандарта ISO C11 это классифицируется как __Гонка данных (Data Race)__.

Любая несинхронизированная гонка данных на неатомарных типах данных в Си приводит к __Неопределенному поведению (Undefined Behavior)__. Компилятор имеет право оптимизировать чтение флага через регистры CPU, что разрушит инвариант Latch-Once и приведет к чтению частично поврежденного (мусорного) контекста ошибки.

__Архитектурные решения:__

1. __Использование встроенных атомиков `_Atomic` (C11):__ Как продемонстрировано в листинге Раздела 3.1, управляющий флаг автомата обязан объявляться с квалификатором `_Atomic`. Операции проверки и мутации должны производиться исключительно через функции `atomic_load` и `atomic_compare_exchange_strong`. Это гарантирует атомарность перехода на уровне инструкций процессора. По умолчанию операции `atomic_compare_exchange_strong` и `atomic_load` используют порядок памяти `memory_order_seq_cst` (последовательная согласованность), который создает полный барьер памяти и гарантирует видимость всех предшествующих записей для других потоков. Это обеспечивает корректность без использования тяжелых системных мьютексов ОС.
2. __Условный Fallback и компиляция без атомиков:__ Стоит учитывать, что в стандарте C11 атомарные операции являются опциональными (Conditional Feature). Если компилятор определяет макрос `__STDC_NO_ATOMICS__` (проверка через `#ifdef __STDC_NO_ATOMICS__`), заголовок `<stdatomic.h>` будет недоступен. В таком сценарии вы __обязаны__ перевести модуль в однопоточный режим и жестко задокументировать контракт безопасности: *"Подсистема не является потокобезопасной. Конкурентный доступ запрещен. Каждый поток обязан владеть изолированным экземпляром safe_file_t"*.

### 5.2. Фиксированный буфер vs Динамическая память

Архитектурный выбор статического массива `char message[128]` вместо гибкого динамического указателя `char *message` с ленивым выделением через `malloc` обусловлен принципом __обработки ошибок без динамической аллокации__ (static allocation for error context).

__Системное обоснование:__
Механизм фиксации сбоя __никогда не должен зависеть от состояния кучи (Heap)__. Если исходным триггером аварии подсистемы послужило полное исчерпание оперативной памяти (сбой `ERR_CONFIG_NO_MEM`), то вызов `malloc()` внутри функции `safe_file_set_error` гарантированно вернет `NULL`. В результате приложение не сможет записать строковую диагностику, и разработчик полностью потеряет снимок первопричины (Root Cause), получив пустой лог. Статически зарезервированный буфер гарантирует консервацию сообщения при любом состоянии физической памяти устройства.

## 6. Взаимодействие с другими паттернами

### 6.1. Синергия с контрактами возврата (Паттерны 01, 03, 04)

Паттерн 09 является __ортогональной надстройкой__ над любым контрактом возврата. Конечный автомат Latched State определяет, *когда* объект умирает, а контракт возврата определяет, *как* передается статус операции. Эти два механизма не связаны жестко, и разработчик может выбрать любой контракт в зависимости от природы операций.

__С Паттерном 01 (`err_t` + out-параметры) — классический вариант:__
Наиболее идиоматичный для stream-like API (запись в файл, сокет, шину). Статус передается через `return`, данные — через out-параметры. Именно этот вариант используется в примере раздела 3.

```c
NODISCARD
err_t safe_file_write(safe_file_t *sf, const void *buf, size_t len);
// Если sf в FAILED, мгновенно возвращает ERR_STREAM_FAILED
```

__С Паттерном 03 (Return value + `err_t*`) — для скалярных операций:__
Когда основное значение — это скаляр (число, указатель), а статус — вторичен. Latched State гарантирует, что при «мертвом» объекте функция вернет безопасное значение (0, NULL) и запишет `ERR_STREAM_FAILED` в out-параметр.

```c
NODISCARD
int safe_file_read_byte(safe_file_t *sf, err_t *err);
// Если sf в FAILED: *err = ERR_STREAM_FAILED, return 0
```

__С Паттерном 04 (Result / Tagged Union) — функциональный стиль:__
Когда операция возвращает сложное значение или указатель, упакованный в `Result`. Latched State возвращает `RESULT_ERR(ERR_STREAM_FAILED)` для «мертвого» объекта.

```c
// C23: nodiscard применен к типу (раздел 1.3 Паттерна 17)
struct [[nodiscard]] result_ptr_impl {
    bool is_ok;
    union { void *ptr; err_t err; } data;
};
typedef struct result_ptr_impl result_ptr_t;

NODISCARD
result_ptr_t safe_file_read_line(safe_file_t *sf);
// Если sf в FAILED: return {.is_ok = false, .data.err = ERR_STREAM_FAILED}
```

__Архитектурная рекомендация:__ Выбор контракта возврата определяется природой операций, а не фактом использования Latched State:

- Для операций с множественными out-параметрами → Паттерн 01
- Для скалярных операций с основным значением → Паттерн 03
- Для парсеров и операций с владеющими указателями → Паттерн 04

Независимо от выбранного контракта, инвариант Latch-Once (сохранение первопричины) и атрибут `NODISCARD` (принудительная проверка) работают одинаково.

Подробное описание контрактов возврата см. в [Паттерне 01](01_return_code_out_params.md), [Паттерне 03](03_return_val_param_err_t.md) и [Паттерне 04](04_result_struct.md).

### 6.2. Синергия с Паттерном 06 (Контекст ошибок)

Паттерн 06 предоставляет базовую структуру `error_state_t` (код ошибки + строковое сообщение), на которую накладывается конечный автомат Latched State. Без Паттерна 06 у нас нет механизма хранения диагностики; без Паттерна 09 мы не можем гарантировать, что эта диагностика не будет перезаписана последующими вызовами (инвариант Latch-Once).

Подробное описание контекста ошибок см. в [Паттерне 06](06_error_context.md).

### 6.3. Синергия с Паттерном 17 (Compiler-Enforced Return Checking)

Если методы "мертвого" объекта не помечены `NODISCARD` (или `__attribute__((warn_unused_result))`), вызывающий код может молча проигнорировать возврат `ERR_STREAM_FAILED` и продолжить работу с поврежденным состоянием. Это превращает защитный механизм Latched State в декорацию.

Атрибут `[[nodiscard]]` гарантирует, что компилятор пресечет игнорирование статуса, превращая Latched State из дисциплинарного соглашения в статически проверяемое свойство программы.

Подробное описание механизмов принуждения см. в [Паттерне 17](17_compiler_enforced_return_checking.md).

### 6.4. Синергия с Паттернами 10 и 12 (Очистка ресурсов)

Когда объект переходит в состояние `FAILED`, возникает вопрос: что делать с базовым ресурсом (например, `FILE *f`, сокетом, дескриптором БД)? Паттерн 09 не решает эту проблему — он только фиксирует факт "смерти" объекта и консервирует root cause.

Для корректной очистки ресурса используются:

- __Паттерн 10 (Goto-цепочки)__ — для строгого ISO C и embedded.
- __Паттерн 12 (Scope Guards)__ — для GCC/Clang в user-space.

Подробное описание механизмов очистки см. в [Паттерне 10](10_goto_cleanup.md) и [Паттерне 12](12_raii_emulation_with_scope_guard.md).

## 7. Практические рекомендации (Best Practices)

1. __Принудительная проверка.__ Помечайте методы объекта атрибутом `__attribute__((warn_unused_result))` или `[[nodiscard]]` ([Паттерн 17](17_compiler_enforced_return_checking.md)). Игнорирование кода возврата на «мертвом» объекте ведет к тихой деградации и нарушению инварианта Circuit Breaker.

2. __Соблюдайте Latch-Once.__ Никогда не перезаписывайте `err.code` и `err.message`, если объект уже перешел в состояние `FAILED`. Первая ошибка — это диагноз, последующие — лишь симптомы. Нарушение этого инварианта превращает защитный механизм в источник ложной диагностики.

3. __Разделяйте Recoverable и Fatal ошибки.__ Не делайте объект «мертвым» из-за `EINTR` или `EAGAIN`. Latched State применяется только к фатальным сбоям (потеря связи, нарушение протокола, повреждение структур). Ошибка классификации превращает защиту в уязвимость, парализуя систему ложными блокировками.

4. __Атомарность или Документация.__ Либо используйте `_Atomic` для флага состояния, либо жестко документируйте ограничения многопоточности. Смешивание этих стратегий (например, использование `_Atomic` без документации) создает ложное ощущение потокобезопасности.

5. __Комбинируйте с другими паттернами (бандлы).__ Latched State не существует изолированно — он всегда используется в связке с другими паттернами, формируя архитектурный бандл. Наиболее распространенные комбинации:

   - __Бандл A (Async-сервер):__ Latched State + Async Passing (Паттерн 15) + Fail-Fast (Паттерн 13). Используется в event-loop серверах, где каждый сокет — долгоживущий объект. При разрыве соединения сокет переходит в `FAILED`, все последующие сабмиты мгновенно отклоняются с кодом `ERR_STREAM_FAILED`.
   - __Бандл B (Доменная библиотека):__ Latched State + `err_t` (Паттерн 01) + Goto-цепочки (Паттерн 10) + Контекст ошибок (Паттерн 06). Используется в библиотеках среднего уровня, где объекты (конфигурации, соединения с БД) живут в течение сессии. При фатальном сбое объект переходит в `FAILED`, ресурсы освобождаются через goto-цепочки, диагностика сохраняется в контексте.
   - __Бандл C (Современный Linux-демон):__ Latched State + `err_t` (Паттерн 01) + Scope Guards (Паттерн 12) + Контекст ошибок (Паттерн 06). Используется в user-space демонах для GCC/Clang. Scope Guards обеспечивают линейный код без goto, автоматическую очистку ресурсов при выходе из функции.

   Полный список канонических бандлов и матрица их совместимости описаны в [Стратегии выбора](00_strategy_and_selection.md), раздел 3.2.

6. __Явный метод сброса (опционально, редко).__ Если объект поддерживает восстановление, предоставьте метод `safe_file_reset()`, который атомарно сбрасывает `failed` в `0` и очищает `err`, но __только если базовый ресурс (например, `FILE*`) был успешно переподключен__. Этот паттерн применяется редко — в большинстве случаев «мертвый» объект утилизируется, а не восстанавливается. Если вы реализуете `reset()`, убедитесь, что он также помечен `NODISCARD`, так как ошибка переподключения должна быть обработана.
