# Паттерн обработки ошибок: Простое булево «успех/неуспех» (bool + out-параметры)

date: "2026-07-01"\

standards: "C11 (базовый, stdbool.h); GCC/Clang extensions (warn_unused_result); C23 ([[nodiscard]])"\
prerequisites:

- Базовое владение C (функции, указатели, структуры).
- Понимание разницы между «успех/неуспех» и типами ошибок среды.
- Знакомство с [Каталогом паттернов](00_pattern_catalog.md).
- Знакомство с [Паттерном 01: Return-код + out-параметры](01_return_code_out_params.md).

objective:

- Подробно описать паттерн булевого результата (успех/неуспех) с out-параметрами.
- Сформулировать строгие инварианты контракта для out-параметров и механизмы принуждения компилятора.
- Показать области применения, плюсы и минусы по сравнению с `err_t` и другими паттернами.
- Дать практические примеры и рекомендации, когда этот паттерн достаточен, а когда от него пора отказываться.

theory:
  Булевый паттерн предполагает, что функция возвращает только факт успеха или неуспеха (`bool` из `<stdbool.h>`), а данные передаются через out-параметры.
  Детализация причины неуспеха либо не нужна для вызывающего кода, либо фиксируется другими средствами (логирование, глобальный/контекстный `error_state`), но не через тип результата.
  Такой подход особенно удобен для внутренних вспомогательных функций и «фильтров», где ошибка интерпретируется как «условие не выполнено», а не как отдельное состояние системы.
  Ключевой принцип: использование `bool` требует явного подключения `<stdbool.h>`, чтобы избежать исторической путаницы с `int`, где `0` часто означает «успех».

## 1. Описание и строгий контракт

### 1.1. Сигнатура и семантика

Типичный вид:

```c
#include <stdbool.h>

// GCC/Clang: __attribute__((warn_unused_result))
// C23: [[nodiscard("Ignoring parse result leaves out_entry uninitialized")]]
__attribute__((warn_unused_result))
bool parse_line(const char *line, entry_t *out_entry);
```

**Жесткий контракт (Инварианты):**

1. **Возврат `true`** означает, что операция завершилась успешно, и out-параметры находятся в определённом корректном состоянии.
2. **Возврат `false`** означает, что операция не удалась (входные данные не соответствуют формату, нарушено предусловие и т.д.).
3. **Строгий инвариант детерминизма out-параметров:** Поведение с out-параметрами при `false` должно быть предсказуемым. В современном C рекомендуется **обнулять out-параметр в самом начале функции** (например, через `memset`). Это гарантирует, что вызывающий код, случайно прочитав структуру при `false`, не получит мусор из стека (предотвращение UB и уязвимостей).
4. **Использование `bool`.** Никогда не используйте `int` вместо `bool` для этого паттерна без явной документации. В C исторически сложилось, что `0` означает «успех». Если функция возвращает `int`, вызывающий код по инерции может проверить `if (func() == 0)`, что для булевой логики будет означать «неуспех». Использование `<stdbool.h>` обязательно.

## 2. Области применения

Булевый паттерн подходит, когда:

- Детализация типа ошибки не влияет на дальнейшую логику (если не удалось распарсить строку — просто пропустить её).
- Функция выполняет проверку условия или простую валидацию («валидна ли строка», «является ли структура консистентной»).
- Функция — внутренний помощник (`static`), не входящий в публичный API библиотеки, а служащий частью более сложной операции, которая уже возвращает `err_t` или `Result`.

## 3. Плюсы и минусы

### 3.1. Плюсы

- **Простота интерфейса.** Сигнатура и использование интуитивны: `if (func(...)) { ... }`.
- **Минимальный когнитивный overhead.** Нет необходимости проектировать систему кодов ошибок, если детализация не нужна.
- **Идеально для «мелких» функций.** Внутренние утилиты, проверки, фильтры часто не требуют ничего, кроме «да/нет».

### 3.2. Минусы и риски

- **Отсутствие информации о причине.** Невозможно отличить разные типы неуспеха.
- **Риск игнорирования возврата.** Возвращаемое значение `bool` так же легко проигнорировать, как и `int`. Если вызывающий код напишет `parse_line(line, &e);` без проверки `if`, он начнет работать с обнуленными данными.
  - *Решение:* Использование атрибутов `[[nodiscard]]` (C23) или `__attribute__((warn_unused_result))` (GCC/Clang). См. [Паттерн 17](17_compiler_enforced_return_checking.md).
- **Не годится для публичных API с требованиями к диагностике.** Клиентам библиотеки часто нужно различать «нет такого параметра», «не тот тип», «ошибка ввода-вывода».

## 4. Практический пример

### 4.1. Разбор простой пары key=value

```c
#include <stdbool.h>
#include <string.h>
#include <stdio.h>

typedef struct {
    char key[32];
    char value[64];
} entry_t;

// Принудительная проверка возврата (Паттерн 17)
__attribute__((warn_unused_result))
bool parse_simple_entry(const char *line, entry_t *out_entry) {
    // 1. Проверка предусловий
    if (!line || !out_entry) {
        return false;
    }

    // 2. Строгий инвариант: обнуляем out-параметр сразу.
    // Это защищает от чтения мусора из стека при возврате false.
    memset(out_entry, 0, sizeof(*out_entry));

    const char *eq = strchr(line, '=');
    if (!eq) {
        return false;
    }

    size_t key_len = (size_t)(eq - line);
    size_t val_len = strlen(eq + 1);

    if (key_len == 0 || key_len >= sizeof(out_entry->key)) {
        return false;
    }
    if (val_len == 0 || val_len >= sizeof(out_entry->value)) {
        return false;
    }

    // 3. Безопасное копирование
    memcpy(out_entry->key, line, key_len);
    out_entry->key[key_len] = '\0';

    // snprintf безопаснее strncpy: всегда добавляет '\0' и не читает за пределами источника
    snprintf(out_entry->value, sizeof(out_entry->value), "%s", eq + 1);

    return true;
}
```

**Использование:**

```c
entry_t e;
if (parse_simple_entry(line, &e)) {
    /* строка подходит, работаем с e */
} else {
    /* строка игнорируется или логируется как некорректная.
       Структура e гарантированно обнулена, ее можно безопасно передать в логгер. */
}
```

## 5. Взаимодействие с другими паттернами

### 5.1. Как часть более сложного API

Булевый паттерн хорошо работает как внутренняя деталь реализации функции, которая наружу возвращает `err_t` ([Паттерн 01](01_return_code_out_params.md)):

```c
static bool parse_entry_internal(const char *line, entry_t *out_entry);

__attribute__((warn_unused_result))
err_t parse_entry(const char *line, entry_t *out_entry) {
    if (!line || !out_entry) return ERR_INVALID_ARG;
    if (out_entry) *out_entry = (entry_t){0}; // Детерминизм
    
    if (!parse_entry_internal(line, out_entry)) {
        return ERR_PARSE; // Маппинг булевого неуспеха в детализированный код
    }
    return ERR_OK;
}
```

### 5.2. Сочетание с контекстом ошибок

Иногда `bool` используют как быстрый флаг, а детали ошибки пишут в контекст ([Паттерн 06](06_error_context.md)):

```c
bool validate_record(lib_ctx_t *ctx, const record_t *rec) {
    if (!rec) {
        lib_set_error(ctx, ERR_INVALID_ARG, "rec is NULL");
        return false;
    }
    if (!is_valid_id(rec->id)) {
        lib_set_error(ctx, ERR_INVALID_ID, "invalid record id");
        return false;
    }
    return true;
}
```

## 6. Когда пора отказаться от bool-паттерна

Признаки, что булевого паттерна становится недостаточно:

1. В вызывающем коде постоянно нужны разные реакции на разные причины неуспеха.
2. Появляются требования детально логировать ошибки, строить метрики по типам ошибок.
3. Функция становится частью публичного API библиотеки, которую используют сторонние команды.

В таких случаях разумно переходить на:

- `err_t + out-параметры` ([Паттерн 01](01_return_code_out_params.md)) для средних уровней и библиотек.
- `Result`-структуры ([Паттерн 04](04_result_struct.md)), если удобнее возвращать всё одним объектом.

## 7. Практические рекомендации (Best Practices)

1. **Принудительная проверка:** Всегда помечайте такие функции атрибутом `__attribute__((warn_unused_result))` или `[[nodiscard]]` ([Паттерн 17](17_compiler_enforced_return_checking.md)). Это переводит контроль из плоскости «человеческой дисциплины» в плоскость «статического анализа».
2. **Детерминизм out-параметров:** Либо обнуляйте out-параметр в начале функции (`memset`), либо строго документируйте, что его чтение при `false` запрещено. Первый вариант безопаснее.
3. **Явное использование `<stdbool.h>`:** Никогда не возвращайте «магические» `int` (0/1) для этого паттерна.
4. **Ограничьте область применения:** Используйте `bool`-паттерн во внутренних утилитарных функциях и простых фильтрах. Избегайте его в публичных API сложных модулей.
