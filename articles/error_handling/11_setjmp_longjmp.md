# Паттерн обработки ошибок: setjmp/longjmp (Нелокальные переходы)

title: "Паттерн обработки ошибок: setjmp/longjmp (Нелокальные переходы)"\
date: "2026-07-01"\
version: "v1.0"\
standards: "C11 (базовый, setjmp.h); POSIX.1-2017 (sigsetjmp/siglongjmp)"\
prerequisites:

- Глубокое понимание работы стека вызовов, стековых кадров и регистров процессора.
- Уверенное владение [Паттерном 10: Goto-цепочки](10_goto_cleanup.md) и концепцией RAII/очистки ресурсов.
- Понимание разницы между ошибками среды и ошибками инвариантов ([Паттерн 13](13_fail_fast_assert.md)).
- Знакомство с [Каталогом паттернов](00_pattern_catalog.md).

objective:

- Описать механику `setjmp`/`longjmp` как инструмента нелокального перехода.
- Жестко ограничить области применения: от «академических исключений» к индустриальным паттернам (парсеры, виртуальные машины).
- Разобрать критические ловушки: неопределенное поведение локальных переменных (`volatile`), катастрофические утечки ресурсов и работа с сигналами.
- Показать индустриальный стандарт: контекстный `jmp_buf` (The libpng way).

theory:
  Функции `setjmp` и `longjmp` из `<setjmp.h>` позволяют сохранить контекст выполнения (регистры процессора, указатель стека) и впоследствии восстановить его, осуществив «прыжок» через произвольное количество уровней стека вызовов.\
  **Философская установка:** В C это **не исключения**. В C нет деструкторов и нет механизма автоматической очистки стека (RAII). `longjmp` просто сдвигает указатель стека обратно, «уничтожая» все промежуточные стековые кадры. Любой ресурс (память, файловый дескриптор, мьютекс), захваченный между `setjmp` и `longjmp`, будет **безвозвратно утерян**, если не были приняты экстраординарные меры.\
  Поэтому `setjmp/longjmp` в современном C — это не механизм обработки бизнес-ошибок, а «аварийный люк» для специфических сценариев: глубокого рекурсивного спуска (парсеры) или реализации сопрограмт/виртуальных машин, где код *гарантированно* не захватывает ресурсов на пути прыжка.

## 1. Механика и строгий контракт

### 1.1. Базовая семантика

```c
#include <setjmp.h>

jmp_buf env;

void deep_function(void) {
    // ... какой-то код ...
    longjmp(env, 42); // Прыжок обратно в setjmp, заставляя его вернуть 42
}

int main(void) {
    int val = setjmp(env); // Сохраняет контекст, возвращает 0 при первом вызове
    if (val == 0) {
        deep_function();
    } else {
        // Сюда попадем после longjmp. val будет равен 42.
    }
    return 0;
}
```

### 1.2. Жесткие контракты и инварианты

1. **Инвариант живого стека.** Функция, в которой был вызван `setjmp`, **не должна завершиться** до вызова `longjmp`. Прыжок в уничтоженный стековый кадр — это Undefined Behavior (UB) и гарантированный Segmentation Fault.
2. **Инвариант отсутствия ресурсов.** Между `setjmp` и `longjmp` **запрещено** захватывать ресурсы, требующие ручного освобождения (`malloc`, `fopen`, `pthread_mutex_lock`). `longjmp` не вызовет `free()` или `fclose()`.
3. **Инвариант потокобезопасности.** `jmp_buf` привязан к потоку. Прыжок между разными потоками невозможен и является UB.

## 2. Области применения (Где уместно, а где — антипаттерн)

### 2.1. Где уместно (Индустриальные сценарии)

- **Глубокие рекурсивные парсеры.** Если у вас парсер с 20 уровнями вложенности (например, JSON, XML, языки программирования), и на 18-м уровне обнаружена синтаксическая ошибка, возврат `err_t` ([Паттерн 01](01_return_code_out_params.md)) через все 18 уровней засоряет код. `longjmp` позволяет мгновенно вернуться в точку инициализации парсера.
- **Виртуальные машины и интерпретаторы.** Реализация конструкций типа `try/catch` или `pcall` (как в Lua) для пользовательского кода.
- **Сопрограммы (Coroutines).** Использование `setjmp/longjmp` (или ассемблерных аналогов) для переключения контекста между задачами.

### 2.2. Где НЕ УМЕСТНО (Строгие антипаттерны)

- **Замена `err_t` + `goto-cleanup`.** Использование `setjmp` для обработки ошибок ввода-вывода, сетевых таймаутов или нехватки памяти в бизнес-логике — это катастрофа.
- **Попытка эмулировать C++ исключения.** Написание макросов `TRY/CATCH` на базе `setjmp` неизбежно приводит к утечкам памяти и блокировкам.

## 3. Индустриальный паттерн: Контекстный jmp_buf (The libpng way)

В «академических» статьях часто используют глобальную переменную `jmp_buf env`. **В индустриальном C это недопустимо** из-за проблем с многопоточностью и реентерабельностью.

Эталоном правильного использования является библиотека `libpng`. Суть паттерна: `jmp_buf` является **частью структуры контекста**, которая передается через аргументы.

### 3.1. Реализация

```c
#include <setjmp.h>
#include <stdlib.h>
#include <stdio.h>

typedef enum {
    ERR_OK = 0,
    ERR_PARSE_SYNTAX,
    ERR_PARSE_OVERFLOW
} parse_err_t;

// Контекст парсера содержит jmp_buf
typedef struct {
    jmp_buf env;
    parse_err_t error_code;
    const char *error_msg;
    // ... другие поля состояния парсера ...
} parser_ctx_t;

// Функция фатальной ошибки парсера
_Noreturn void parser_fatal(parser_ctx_t *ctx, parse_err_t code, const char *msg) {
    ctx->error_code = code;
    ctx->error_msg = msg;
    longjmp(ctx->env, (int)code); // Прыжок в контексте конкретного парсера
}

// Глубокая функция парсинга (не знает про setjmp, просто использует контекст)
void parse_complex_node(parser_ctx_t *ctx, const char *data) {
    // ... много рекурсивных вызовов ...
    if (/* синтаксическая ошибка */) {
        parser_fatal(ctx, ERR_PARSE_SYNTAX, "Unexpected token at line 42");
    }
}

int main(void) {
    parser_ctx_t ctx = {0};
    
    // Устанавливаем "ловушку" в контексте
    int err = setjmp(ctx.env);
    if (err == 0) {
        // Нормальный путь
        parse_complex_node(&ctx, "some data");
        printf("Parse successful\n");
    } else {
        // Путь ошибки: мы мгновенно вернулись сюда из глубины рекурсии
        printf("Parse failed: [%d] %s\n", ctx.error_code, ctx.error_msg);
    }
    return 0;
}
```

**Почему это правильно:**

1. **Потокобезопасность.** Каждый поток создает свой `parser_ctx_t` на стеке или в куче. Глобального состояния нет.
2. **Реентерабельность.** Можно запускать парсер рекурсивно или из callback-ов, так как каждый уровень имеет свой контекст.
3. **Инкапсуляция.** Глубокие функции парсера просто принимают `ctx` и вызывают `parser_fatal`, не заботясь о механизме прыжка.

## 4. Критические ловушки (Must Read)

### 4.1. Ловушка `volatile` и оптимизации компилятора

Это самая частая причина «магических» багов при использовании `setjmp`.\
Компилятор имеет право кешировать локальные переменные в регистрах процессора. `setjmp` сохраняет регистры. Если между `setjmp` и `longjmp` переменная изменялась, но не была объявлена как `volatile`, компилятор мог не записать её новое значение в память. После `longjmp` регистры восстановятся из `jmp_buf`, и переменная примет **старое (или мусорное) значение**.

**Правило:** Любая локальная переменная, которая была изменена после `setjmp` и должна быть прочитана после `longjmp`, **обязана** быть объявлена с квалификатором `volatile`.

```c
int main(void) {
    int normal_var = 10;
    volatile int safe_var = 10; // Правильно
    
    if (setjmp(env) == 0) {
        normal_var = 20; // Компилятор может держать 20 в регистре
        safe_var = 20;   // Компилятор обязан записать 20 в память
        longjmp(env, 1);
    } else {
        // После longjmp:
        // normal_var может быть равна 10 (или вообще чем угодно) -> UB по стандарту C!
        // safe_var гарантированно равна 20 (или 10, если longjmp произошел до присваивания).
    }
}
```

### 4.2. Катастрофа утечек ресурсов

Поскольку в C нет деструкторов, `longjmp` просто сдвигает указатель стека.

```c
void bad_function(jmp_buf env) {
    FILE *f = fopen("data.txt", "r"); // Ресурс захвачен
    if (/* error */) {
        longjmp(env, 1); // Файл НИКОГДА не будет закрыт. Утечка дескриптора.
    }
    fclose(f);
}
```

**Решение:** В коде между `setjmp` и `longjmp` либо вообще не должно быть аллокаций, либо должен использоваться [Паттерн 10: Goto-цепочки](10_goto_cleanup.md) *внутри* каждой промежуточной функции, а `longjmp` вызывается только после того, как все локальные ресурсы этой функции освобождены.

### 4.3. Сигналы и `sigsetjmp`

Если `longjmp` вызывается из обработчика сигнала (Signal Handler), использование обычного `setjmp` может привести к тому, что сигналы, которые были заблокированы на момент входа в handler, останутся заблокированными навсегда.\
Для работы с сигналами стандарт POSIX требует использовать пару **`sigsetjmp` / `siglongjmp`**, которые дополнительно сохраняют и восстанавливают маску сигналов процесса.

## 5. Антипаттерн: Макросы TRY/CATCH на базе setjmp

В интернете можно встретить попытки написать макросы для эмуляции C++ исключений:

```c
// ОПАСНЫЙ АНТИПАТТЕРН
#define TRY do { jmp_buf env; if (setjmp(env) == 0) {
#define CATCH } else {
#define END_TRY } } while(0)
```

**Почему это сломано:**

1. Переменная `jmp_buf env` является **локальной** для макроса `TRY`. Функции, вызываемые внутри блока `TRY`, **не имеют доступа** к `env` и не могут вызвать `longjmp`. (Чтобы это скомпилировалось, `env` приходится делать глобальным, что убивает многопоточность).
2. Даже если передать `env` через глобальную переменную, блок `CATCH` не выполнит очистку ресурсов, захваченных в `TRY`.

**Вывод:** Никогда не пишите макросы `TRY/CATCH` в C. Используйте явный контекстный `jmp_buf` (как в `libpng`), если вам действительно нужен нелокальный переход.

## 6. Практические рекомендации (Best Practices)

1. **Правило по умолчанию: НЕ ИСПОЛЬЗОВАТЬ.** Для 99% бизнес-логики, сетевых и файловых операций используйте `err_t` + `goto-cleanup` ([Паттерн 01](01_return_code_out_params.md) + [Паттерн 10](10_goto_cleanup.md)). `setjmp` — это инструмент для узкоспециализированных задач.
2. **Контекстный jmp_buf.** Никогда не используйте глобальные `jmp_buf`. Всегда вкладывайте `jmp_buf` в структуру контекста (`parser_ctx_t`, `vm_state_t`) и передавайте указатель на неё через аргументы функций.
3. **Запрет на аллокации.** Жестко контролируйте (например, через Code Review или статический анализ), чтобы между `setjmp` и `longjmp` не вызывались `malloc`, `fopen`, `pthread_mutex_lock` и т.д.
4. **Используйте `volatile`.** Если вам нужно передать данные из точки `longjmp` в точку `setjmp` через локальные переменные, объявляйте их как `volatile`.
5. **Помечайте функции прыжка.** Функции, внутри которых вызывается `longjmp` (например, `parser_fatal`), должны быть помечены атрибутом `_Noreturn` (C11) или `__attribute__((noreturn))`. Это поможет компилятору избежать ложных предупреждений и лучше оптимизировать код (см. [Паттерн 13](13_fail_fast_assert.md)).
