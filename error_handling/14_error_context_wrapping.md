# Паттерн обработки ошибок: Error Context / Wrapping (Обогащение контекстом)

objective:

- Описать паттерн обогащения ошибки контекстом (Error Wrapping) при её пробросе через слои абстракции.
- Показать, как сохранить «корневую причину» (root cause) и добавить доменную семантику без использования динамической памяти.
- Сформулировать строгие правила безопасности (защита от OOM при обработке OOM).
- Продемонстрировать индустриальные макросы для прозрачного логирования и обогащения.

theory:\
  В многоуровневой архитектуре (ОС -> stdlib -> доменная библиотека -> бизнес-логика) низкоуровневая ошибка (например, `ENOENT` или `ERR_IO`) теряет свою информативность при достижении верхнего уровня. Код `ERR_IO` в функции `process_user_request()` ничего не говорит о том, *какой именно файл* не удалось открыть.\
  Паттерн Error Wrapping (Обертывание/Обогащение) предполагает, что при передаче ошибки с нижнего уровня на верхний, функция не просто возвращает `err_t`, но и **обогащает контекст ошибки** ([Паттерн 06](06_error_context.md)) новой семантической информацией (имя файла, ID сессии, строка формата).
  Ключевой философский принцип: **Обработчик ошибок никогда не должен падать**. Поскольку обогащение часто требует форматирования строк, использование `malloc` или `asprintf` внутри обертки недопустимо. Мы используем фиксированные буферы и `vsnprintf`.

---

## 1. Описание и строгий контракт

### 1.1. Формальное описание

Обогащение ошибки — это процесс замены или дополнения строкового сообщения в контексте (`lib_ctx_t`) по мере выхода из функции.

```c
// Базовая функция установки ошибки с форматированием (инфраструктура Паттерна 06)
void lib_set_error_fmt(lib_ctx_t *ctx, err_t code, const char *file, int line, 
                       const char *fmt, ...);

// Макрос-обертка для прозрачного обогащения
#define WRAP_ERR(ctx, err, fmt, ...) \
    lib_set_error_fmt(ctx, err, __FILE__, __LINE__, fmt, ##__VA_ARGS__)
```

### 1.2. Жесткие контракты и инварианты

1. **Инвариант безопасности памяти (No-Malloc Rule).** Функции обогащения ошибки **категорически запрещено** использовать динамическую память (`malloc`, `strdup`, `asprintf`). Если система упала с `ERR_NO_MEM`, попытка аллоцировать буфер для строки ошибки приведет к каскадному краху. Используются только стековые буферы или поля фиксированного размера в `lib_ctx_t`.
2. **Сохранение кода, обогащение сообщения.** Числовой код (`err_t`) обычно остается неизменным (или маппится в доменный), а строковое сообщение перезаписывается более высокоуровневым контекстом.
3. **Наличие исходного кода.** В структуре `error_state_t` рекомендуется хранить не только строку, но и оригинальный код (или `errno`), чтобы UI/логгер могли ветвиться по типу ошибки, а не парсить строку.

## 2. Области применения

Паттерн критически важен, когда:

- **Многоуровневая архитектура:** Низкоуровневый парсер возвращает `ERR_PARSE`, но средний слой (загрузчик конфигов) должен сообщить: "Ошибка парсинга JSON в файле `/etc/app.conf` на строке 42".
- **Сетевые шлюзы и RPC:** Превращение внутренней ошибки `ERR_TIMEOUT` в понятный клиенту ответ "Сервис авторизации недоступен (timeout)".
- **Сложные бизнес-процессы:** Когда одна операция вызывает десяток других, и без контекста невозможно понять, на каком этапе произошел сбой.

---

## 3. Плюсы и минусы

### 3.1. Плюсы

- **Высокая диагностируемость.** Разработчик или поддержка сразу видит не просто "I/O Error", а "Failed to write to /var/log/app.log".
- **Инкапсуляция слоев.** Нижний слой не знает о существовании `/etc/app.conf`, он просто возвращает `ERR_IO`. Средний слой добавляет этот контекст, не нарушая контрактов нижнего.
- **Отсутствие утечек.** При использовании фиксированных буферов (в отличие от C++ `std::string` в исключениях) мы не создаем "ошибок при обработке ошибок".

### 3.2. Минусы и риски

- **Перерасход памяти.** Каждый `lib_ctx_t` "весит" больше (например, +256 байт на буфер сообщения).
- **Накладные расходы на CPU.** `vsnprintf` — относительно медленная операция. В hot-path (внутренних циклах) обогащение ошибок может снизить производительность.
- **Риск переполнения буфера.** Если сообщение слишком длинное, `snprintf` его обрежет. Важно проектировать буферы с запасом или использовать усечение (ellipsis `...`).

## 4. Простой пример: Макросы и Инфраструктура

Реализация безопасного обогащения на базе [Паттерна 06](06_error_context.md).

```c
#include <stdio.h>
#include <stdarg.h>
#include <stdlib.h>

typedef enum { ERR_OK = 0, ERR_IO, ERR_NO_MEM, ERR_PARSE } err_t;

typedef struct {
    err_t code;
    char message[256]; // Фиксированный буфер: защита от OOM
} error_state_t;

typedef struct {
    error_state_t err;
} lib_ctx_t;

// Базовая функция форматирования (вызывается через макрос)
void lib_set_error_fmt(lib_ctx_t *ctx, err_t code, const char *file, int line, 
                       const char *fmt, ...) {
    if (!ctx) return;
    ctx->err.code = code;
    
    // 1. Сначала пишем префикс (файл и строка)
    int n = snprintf(ctx->err.message, sizeof(ctx->err.message), "[%s:%d] ", file, line);
    if (n < 0) n = 0;
    
    // 2. Затем дописываем само сообщение пользователя
    va_list args;
    va_start(args, fmt);
    vsnprintf(ctx->err.message + n, sizeof(ctx->err.message) - (size_t)n, fmt, args);
    va_end(args);
}

// Удобный макрос для использования в коде
#define WRAP_ERR(ctx, err, fmt, ...) \
    lib_set_error_fmt(ctx, err, __FILE__, __LINE__, fmt, ##__VA_ARGS__)
```

## 5. Развёрнутый пример: Загрузка конфигурации

Покажем, как ошибка `fopen` (POSIX) превращается в осмысленное сообщение на уровне приложения.

```c
#include <errno.h>
#include <string.h>

// Доменная функция
__attribute__((warn_unused_result))
err_t config_load(lib_ctx_t *ctx, const char *path) {
    if (!ctx || !path) {
        WRAP_ERR(ctx, ERR_INVALID_ARG, "NULL argument provided");
        return ERR_INVALID_ARG;
    }

    FILE *f = fopen(path, "r");
    if (!f) {
        // ОБОГАЩЕНИЕ: Мы берем низкоуровневую ошибку и добавляем доменный контекст.
        // Используем strerror(errno) для получения системного описания.
        WRAP_ERR(ctx, ERR_IO, "Failed to open config file '%s' (sys: %s)", 
                 path, strerror(errno));
        return ERR_IO;
    }

    // ... чтение и парсинг ...
    
    char line[128];
    int line_num = 0;
    while (fgets(line, sizeof(line), f)) {
        line_num++;
        if (/* ошибка парсинга */) {
            // ОБОГАЩЕНИЕ: Добавляем номер строки!
            WRAP_ERR(ctx, ERR_PARSE, "Syntax error in '%s' at line %d", path, line_num);
            fclose(f);
            return ERR_PARSE;
        }
    }

    fclose(f);
    return ERR_OK;
}

// Использование на верхнем уровне
int main(void) {
    lib_ctx_t ctx = {0};
    
    err_t err = config_load(&ctx, "/etc/my_app/missing.conf");
    if (err != ERR_OK) {
        // Вывод: [/path/to/config.c:42] Failed to open config file '/etc/my_app/missing.conf' (sys: No such file or directory)
        fprintf(stderr, "Startup failed: %s\n", ctx.err.message);
        return EXIT_FAILURE;
    }
    return EXIT_SUCCESS;
}
```

## 6. Взаимодействие с другими паттернами

### 6.1. Синергия с Паттерном 06 (Контекст ошибок)

[Паттерн 06](06_error_context.md) предоставляет `lib_ctx_t` и `error_state_t`. Паттерн 14 предоставляет макросы `WRAP_ERR` и правила их использования. Они неразделимы в современных C-фреймворках.

### 6.2. Альтернатива `setjmp/longjmp` ([Паттерн 11](11_setjmp_longjmp.md))

В некоторых старых кодовых базах для сбора контекста ошибки использовали `longjmp` с глобальным буфером. Это антипаттерн. `WRAP_ERR` + `return err_t` делает то же самое (сохраняет контекст для верхнего уровня), но **безопасно**, не ломая стек и не требуя `volatile`.

### 6.3. Проблема "Перезаписи контекста" (Error Swallowing)

Если функция `A` вызывает `B`, и `B` уже записала ошибку в `ctx`, а `A` вызывает `WRAP_ERR`, сообщение из `B` будет **перезаписано**.

- *Решение:* В сложных системах используют "цепочки ошибок" (Error Chaining), где `error_state_t` содержит массив или связный список последних N ошибок. Но для 95% задач достаточно простого перезаписывания, так как верхнеуровневое сообщение обычно включает в себя суть нижнеуровневого (как в примере с `strerror(errno)`).

## 7. Практические рекомендации (Best Practices)

1. **Никогда не используйте `malloc` в `WRAP_ERR`.** Только `snprintf` / `vsnprintf` в статические или стековые буферы.
2. **Включайте `__FILE__` и `__LINE__` в макрос.** Это бесплатно на этапе компиляции, но критически ускоряет отладку в продакшене.
3. **Будьте осторожны с `strerror`.** Если вы используете `strerror(errno)` внутри `WRAP_ERR`, помните о её потокобезопасности (см. [Паттерн 02](02_sentinel_errno.md)). В многопоточных приложениях лучше передавать уже сохраненный `saved_errno` или использовать `strerror_r`.
4. **Не форматируйте в hot-path.** Если функция вызывается миллионы раз в секунду, и ошибка является *исключением*, `snprintf` может стать узким местом. В таких случаях используйте ленивое форматирование (сохранять только `code` и аргументы, а строку формировать только при явном вызове `lib_last_error_str()`).
5. **Согласованность макросов.** Введите в проекте единый макрос (например, `LOG_ERR_AND_WRAP`), который не только обогащает контекст, но и, опционально, пишет в `syslog`/`stderr`, если включен debug-режим.
