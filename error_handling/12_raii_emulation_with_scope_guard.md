# Паттерн обработки ошибок: Эмуляция RAII через Scope Guards

- Уверенное владение C: указатели, области видимости, время жизни объектов.
- Понимание [Паттерна 10: Goto-цепочки для централизованной очистки](10_goto_cleanup.md) и проблематики утечек ресурсов.
- Понимание контракта out-параметров из [Паттерна 01: Return-код + out-параметры](01_return_code_out_params.md).
- Знакомство с концепцией RAII из других языков (C++, Rust).
- Знакомство с [Каталогом паттернов](00_pattern_catalog.md).

objective:

- Описать паттерн Scope Guards как механизм детерминированного освобождения ресурсов при выходе из области видимости.
- Показать, как получить линейный код без `goto cleanup`, не жертвуя безопасностью владения.
- Сформулировать строгие инварианты инициализации, порядка очистки (LIFO) и обезвреживания guard'а (Disarm Pattern).
- Обозначить границы применимости: нестандартность расширения, MISRA, `longjmp`.

theory:
  В строгом ISO C нет деструкторов и нет RAII: захват и освобождение ресурса разделены во времени и связаны только соглашением разработчика. [Паттерн 10](10_goto_cleanup.md) устраняет утечки, но ценой нелинейного потока управления и меток в конце функции.

  GCC и Clang предоставляют расширение `__attribute__((cleanup(func)))`, привязывающее функцию-очиститель к времени жизни локальной переменной. Компилятор генерирует вызов этой функции при любом выходе переменной из области видимости: обычном достижении конца блока, `return`, `break`, `continue` или выходе из исключения области видимости цикла.

  Ключевой принцип: __ресурс освобождается там, где он объявлен, а не там, где заканчивается функция__. Это делает код линейным, а количество точек выхода перестает влиять на сложность очистки.

  Важное ограничение: `cleanup` — это расширение компилятора, а не возможность ISO C (в том числе C23). Следовательно, данный паттерн является осознанным архитектурным выбором проекта, а не универсальной заменой `goto cleanup`.

## 1. Описание и строгий контракт

### 1.1. Механика атрибута

Атрибут применяется к __переменной автоматического storage duration__. Функция-очиститель вызывается с аргументом — адресом этой переменной.

Если переменная объявлена как `T var`, очиститель обязан иметь сигнатуру `void cleanup_fn(T *arg)`.

```c
/* Переменная типа int => аргумент очистителя int * */
static void close_fd_guard(int *fd)
{
    if (*fd >= 0) {
        (void)close(*fd);
        *fd = -1;   /* обезвреживание: повторное закрытие исключено */
    }
}

int fd __attribute__((cleanup(close_fd_guard))) = -1;
```

__Критическое замечание о типах.__ Для указательных переменных нельзя бездумно использовать один универсальный очиститель `void fn(void *)` для всех типов: тип указателя на функцию должен точно соответствовать ожидаемому. Для `void *buf` корректным аргументом является `void **`, а не `void *`. Идиоматичное решение — либо точный тип очистителя, либо очиститель, принимающий `void *` и применяемый __только__ к переменным типа `void *`.

### 1.2. Жесткие инварианты

1. __Инициализация sentinel-значением.__ Guard'ированная переменная обязана быть инициализирована в момент объявления (`NULL`, `-1`, состояние «не захвачена»). Очиститель не знает, был ли ресурс успешно получен, и полагается исключительно на sentinel.
2. __Порядок LIFO по объявлениям.__ Очистители вызываются в порядке, __обратном порядку объявления переменных__ в блоке. Порядок объявлений поэтому должен отражать порядок зависимостей между ресурсами.
3. __Disarm Pattern (обезвреживание при передаче владения).__ Если ресурс передаётся вызывающему коду через out-параметр, локальная переменная обязана быть приведена к sentinel-значению (`NULL`) в том же логическом блоке, где выполнен экспорт владения. Иначе guard освободит ресурс, принадлежащий клиенту.
4. __Отсутствие аллокаций в очистителе.__ Очиститель выполняет только освобождение: никаких `malloc`, `printf` с форматированием, обращений к библиотеке обратно.

## 2. Области применения

### 2.1. Где паттерн уместен

- __Современные Linux user-space приложения:__ `systemd`, `networkd`, `udev`, CLI-утилиты с активной инициализацией.
- __Сетевые демоны:__ функции с десятком ранних выходов по таймаутам, разрывам соединения и ошибкам парсинга.
- __Внутренний код библиотек,__ целенаправленно ориентированных на GCC/Clang.

### 2.2. Где паттерн неприменим

- __Freestanding и жёсткое embedded:__ компилятор целевой платформы может не поддерживать расширение.
- __Кроссплатформенные библиотеки с требованием строгого ISO C:__ MSVC не реализует `__attribute__((cleanup))`.
- __Safety-critical процессы:__ неявный вызов очистителя требует отдельного обоснования в рамках процесса верификации, аналогично отступлению от MISRA C:2012 Rule 15.1 для `goto`.
- __Код, использующий `longjmp`:__ см. раздел 7.3.

## 3. Плюсы и минусы

### 3.1. Плюсы

- __Линейность чтения.__ Код читается сверху вниз; не нужно перемещаться к метке `cleanup` в конце функции.
- __Устойчивость к рефакторингу.__ Добавление нового `return` не требует добавления новой ветки очистки.
- __Локализация ответственности.__ Объявление ресурса и политика его освобождения находятся рядом.
- __Нулевой runtime-overhead сверх необходимой очистки.__ Вызов генерируется компилятором на путях выхода; диспетчеризации во время выполнения нет.

### 3.2. Минусы и риски

- __Привязка к компилятору.__ Переносимость теряется; в project-порт необходимо либо `goto cleanup`, либо условная компиляция.
- __Неявность управления потоком.__ Для разработчика, не знакомого с идиомой, отсутствие `free` в теле функции выглядит как утечка.
- __Хрупкость передачи владения.__ Забытое `buf = NULL` после экспорта ресурса приводит к `double free` / `use-after-free`.
- __Ошибка в сигнатуре очистителя.__ Приводит к несовместимости типов указателей на функции и к чтению памяти по неверному типу.

## 4. Эргономика: DRY-макросы

Писать полное имя атрибута в каждой строке избыточно. В индустрии приняты короткие обёртки:

```c
#if defined(__GNUC__) || defined(__clang__)
#  define _cleanup_(fn) __attribute__((cleanup(fn)))
#  define _NODISCARD    __attribute__((warn_unused_result))
#else
#  define _cleanup_(fn)
#  define _NODISCARD
#endif
```

Безопасные очистители с __точными типами аргументов__:

```c
#include <stdio.h>
#include <unistd.h>

static void fd_guard(int *fd)
{
    if (*fd >= 0) {
        (void)close(*fd);
        *fd = -1;
    }
}

static void file_guard(FILE **f)
{
    if (*f != NULL) {
        (void)fclose(*f);
        *f = NULL;
    }
}

/* Применяется только к переменным типа void * */
static void mem_guard(void **p)
{
    free(*p);
    *p = NULL;
}

#define _cleanup_fd_   _cleanup_(fd_guard)
#define _cleanup_file_ _cleanup_(file_guard)
#define _cleanup_mem_  _cleanup_(mem_guard)
```

__Важно о fallback-ветке.__ Если проект поддерживает компилятор без `cleanup`, пустое определение `_cleanup_` превращает код в __текучий__, а не в переносимый. Для таких платформ требуется отдельная реализация на `goto cleanup` ([Паттерн 10](10_goto_cleanup.md)), а не молчаливое отключение атрибута.

## 5. Развёрнутый пример: загрузка блока без `goto`

```c
#define _POSIX_C_SOURCE 200809L

#include <stdio.h>
#include <stdlib.h>
#include <string.h>

/* Макросы и очистители — из раздела 4. */

enum { BLOCK_CAP = 4096 };

typedef enum {
    ERR_OK = 0,
    ERR_INVALID_ARG,
    ERR_IO,
    ERR_NO_MEM,
    ERR_TOO_LARGE
} err_t;

_NODISCARD
err_t load_block(const char *path, void **out_buf, size_t *out_len)
{
    /* 1. Объявляем ресурсы в порядке зависимостей. LIFO при выходе обратен. */
    _cleanup_file_ FILE *f = NULL;
    _cleanup_mem_  void *buf = NULL;

    /* 2. Детерминизм out-параметров. */
    if (out_buf != NULL) { *out_buf = NULL; }
    if (out_len != NULL) { *out_len = 0; }

    if (path == NULL || out_buf == NULL || out_len == NULL) {
        return ERR_INVALID_ARG;   /* владения ещё нет */
    }

    /* 3. Ранние выходы: очистители сработают автоматически. */
    f = fopen(path, "rb");
    if (f == NULL) {
        return ERR_IO;
    }

    buf = malloc((size_t)BLOCK_CAP + 1u);
    if (buf == NULL) {
        return ERR_NO_MEM;        /* f будет закрыт его guard'ом */
    }

    size_t n = fread(buf, 1u, (size_t)BLOCK_CAP, f);

    if (ferror(f)) {
        return ERR_IO;
    }
    if (n == (size_t)BLOCK_CAP && fgetc(f) != EOF) {
        return ERR_TOO_LARGE;
    }

    /* 4. Экспорт владения. */
    *out_buf = buf;
    *out_len = n;

    /* 5. Disarm Pattern: отключаем очиститель переданного ресурса. */
    buf = NULL;

    return ERR_OK;
    /* f закрывается file_guard'ом; buf == NULL => mem_guard безопасен. */
}
```

### 5.1. Анализ путей завершения

| Путь | `f` | `buf` | Действия guard'ов | Результат |
| --- | --- | --- | --- | --- |
| Неверный аргумент | `NULL` | `NULL` | два холостых вызова | `ERR_INVALID_ARG` |
| `fopen` неудачен | `NULL` | `NULL` | два холостых вызова | `ERR_IO` |
| `malloc` неудачен | открыт | `NULL` | `free(NULL)`; `fclose(f)` | `ERR_NO_MEM` |
| Ошибка чтения | открыт | выделен | `free(buf)`; `fclose(f)` | `ERR_IO` |
| Успех | открыт | `NULL` (передан) | холостой `free`; `fclose(f)` | `ERR_OK`, владение у клиента |

Ни один ресурс не освобождается дважды. Ни один захваченный ресурс не остаётся неотпущенным.

## 6. Взаимодействие с другими паттернами

### 6.1. Противопоставление Паттерну 10 (Goto-cleanup)

| Критерий | [Паттерн 10](10_goto_cleanup.md) | Паттерн 12 (Scope Guards) |
| --- | --- | --- |
| Статус | Строгий ISO C | Расширение GCC/Clang |
| Управление | Явное, в конце функции | Неявное, привязано к переменной |
| Порядок очистки | Порядок текста в блоке `cleanup` | Обратный порядку объявлений |
| Устойчивость к новым `return` | Требует дисциплины | Автоматическая |
| Переносимость | Любая платформа | GCC/Clang |

__Архитектурное правило:__ ядро ОС и переносимые библиотеки — `goto cleanup`; Linux user-space с фиксированным toolchain — Scope Guards. Инварианты владения при этом __идентичны__ в обоих случаях.

### 6.2. Синергия с Паттерном 01 (`err_t`)

Scope Guards освобождают ресурсы, но __не отменяют проверку статуса__. Функции, возвращающие `err_t`, по-прежнему требуют принудительной проверки — см. [Паттерн 17](17_compiler_enforced_return_checking.md). Автоматическая очистка и явная обработка ошибки являются ортогональными обязанностями.

### 6.3. Синергия с маркерами потока (Паттерн 08)

В примере выше `fread`/`fgetc` работают в связке с `ferror()`: достижение конца потока не тождественно ошибке. Подробнее — [Паттерн 08: Маркеры состояния и конца потока](08_state_stream_marker.md). Guard отвечает только за закрытие потока, но не за семантику прочитанных данных.

## 7. Критические риски

### 7.1. Забытое обезвреживание (Disarm)

```c
/* АНТИПАТТЕРН */
*out_buf = buf;
return ERR_OK;   /* mem_guard освободит buf => use-after-free у клиента */

/* ПРАВИЛЬНО */
*out_buf = buf;
buf = NULL;      /* guard обезврежен */
return ERR_OK;
```

Обнуление локального указателя — это единственный способ сообщить собственному guard'у о смене владельца. В C++ эту роль выполняет `std::move` / `release()`; в C — sentinel-присваивание.

### 7.2. Порядок объявлений и зависимости

Поскольку очистители вызываются в порядке, обратном объявлениям, __зависимый ресурс обязан быть объявлен позже того, от которого он зависит__. Объявление аллокатора после объекта, живущего в его памяти, приведёт к освобождению контекста раньше объекта.

### 7.3. Несовместимость с `longjmp`

Расширение `cleanup` не является заменой деструкторам при нелокальных переходах: при выходе через `longjmp` вызов функций очистки __не гарантируется__ (в GCC такие очистители не выполняются). Смешивание guard'ов с [Паттерном 11](11_setjmp_longjmp.md) создаёт иллюзию безопасности и приводит к реальным утечкам. Для путей, использующих `setjmp`/`longjmp`, требуется явная очистка.

### 7.4. Вторичные ошибки освобождения

Очиститель не должен менять возвращаемый статус: ошибка `fclose` на пути обработки первичной ошибки является вторичной. Если закрытие значимо (запись данных), его следует проверить __до__ передачи владения и до выхода из области видимости, как описано в [Паттерне 10](10_goto_cleanup.md).

## 8. Практические рекомендации

1. __Всегда инициализируйте guard'ированную переменную.__ `int fd _cleanup_fd_ = -1;`. Неинициализированная переменная приведёт к попытке закрыть мусор из стека.
2. __Соблюдайте точность типов очистителя.__ `int *` для `int`, `FILE **` для `FILE *`, `void **` для `void *`. Не используйте `void *` как универсальный аргумент.
3. __Централизуйте макросы.__ `_cleanup_`, `_cleanup_fd_`, `_cleanup_mem_` должны жить в одном служебном заголовке, а не копироваться по модулям.
4. __Не делайте cleanup «умным».__ Никаких аллокаций, логгеров с форматированием и повторных обращений в библиотеку внутри очистителя.
5. __Не отключайте атрибут молча.__ В fallback-ветке для компилятора без поддержки требуется альтернативная реализация, иначе макрос превращает безопасный код в текущий.
6. __Документируйте передачу владения.__ Каждая функция, экспортирующая ресурс наружу, обязана содержать явный `ptr = NULL` с комментарием о причине.
