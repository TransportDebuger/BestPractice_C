objective:

- Описать паттерн "контекст ошибок" для C-библиотек как замену глобальному `errno`.
- Сформулировать строгие инварианты управления состоянием ошибки (очистка, обновление, безопасность памяти).
- Разобрать критические риски: состояния гонки (race conditions), устаревание ошибки и безопасность памяти.
- Привести пример безопасной реализации и интеграции с системными вызовами.

theory:
  В отличие от `errno`, который представляет собой глобальное (или thread-local) состояние, паттерн "контекст ошибок" привязывает состояние ошибок к структуре контекста библиотеки (например, `lib_ctx_t`), которую создаёт и использует вызывающая сторона.\
  Контекст ошибок обычно содержит код ошибки и строковое сообщение. Такой подход особенно полезен для библиотек, где может существовать несколько независимых экземпляров (несколько соединений с БД, несколько сетевых клиентов), требуется строгая потокобезопасность без опоры на глобальные переменные, и нужно хранить расширенную диагностику.\
  Ключевой принцип: контекст ошибки — это "снимок" последнего сбоя на данном экземпляре. Он требует строгой дисциплины обновления, чтобы не вводить пользователя в заблуждение.

## 1. Описание и строгий контракт

### 1.1. Формальное описание и контракт

```c
typedef enum {
    ERR_OK = 0,
    ERR_LIB_INVALID_ARG,
    ERR_LIB_IO,
    ERR_LIB_INTERNAL
} err_t;

typedef struct {
    err_t code;
    char  message[128]; // Фиксированный буфер: защита от OOM при обработке ошибок
} error_state_t;

typedef struct {
    /* Поля состояния библиотеки */
    error_state_t err;
} lib_ctx_t;

// C23: [[nodiscard("Ignoring error code may lead to stale error state")]]
// GCC/Clang: __attribute__((warn_unused_result))
__attribute__((warn_unused_result))
err_t lib_do_something(lib_ctx_t *ctx, /* ... args ... */);

const error_state_t *lib_last_error(const lib_ctx_t *ctx);
```

**Жесткие контракты и инварианты:**

1. **Инвариант очистки (Clear-on-Entry).** Каждая публичная функция библиотеки **обязана** начинать выполнение с вызова `clear_error(ctx)`. Это гарантирует, что успешный вызов функции не оставит "устаревшую" ошибку от предыдущих операций.
2. **Детерминизм сообщения.** Строковое сообщение должно быть валидной C-строкой (всегда завершаться `\0`). Использование `snprintf` вместо `strncpy` обязательно для предотвращения переполнения буфера.
3. **Потокобезопасность (Thread-Safety).** `lib_ctx_t` **не является потокобезопасным по умолчанию**. Один контекст = один поток выполнения. Если контекст используется из нескольких потоков, доступ к нему (и к `err`) должен защищаться мьютексом, либо библиотека должна использовать Thread-Local Storage (TLS).

### 1.2. Когда паттерн уместен

- Библиотека имеет состояние и поддерживает несколько независимых экземпляров (клиенты БД, HTTP-соединения).
- Необходимо предоставить расширенную диагностику (строки, коды подсистем), не засоряя сигнатуры функций.
- Требуется изоляция ошибок между потоками без использования глобального `errno`.

## 2. Плюсы и минусы

### 2.1. Плюсы

- **Контекстность и изоляция.** Ошибки привязаны к конкретному экземпляру. Нет проблем с затиранием `errno` или глобального состояния.
- **Расширяемость.** В `error_state_t` можно добавить поля (имя файла, ID запроса, код ОС) без изменения сигнатур функций.
- **Безопасность от OOM.** Использование фиксированных буферов (`char message[128]`) гарантирует, что обработчик ошибок не упадет с `Out Of Memory`, если система исчерпала память.

### 2.2. Минусы и риски

- **Проблема «Устаревшей ошибки» (Stale Error).** Если разработчик библиотеки забудет вызвать `clear_error` в начале функции, пользователь может прочитать ошибку от предыдущей успешной или неуспешной операции.
- **Сложность API.** Пользователь должен создавать, инициализировать и освобождать контекст.
- **Накладные расходы на память.** Каждый экземпляр контекста "весит" больше из-за встроенных буферов для строк.

## 3. Простой пример: Каркас библиотеки

```c
#include <stdlib.h>
#include <string.h>
#include <stdio.h>

typedef enum {
    ERR_OK = 0,
    ERR_LIB_INVALID_ARG,
    ERR_LIB_INTERNAL
} err_t;

typedef struct {
    err_t code;
    char  message[128]; 
} error_state_t;

struct mylib_ctx {
    error_state_t err;
    /* другие поля состояния */
};

// Строгий инвариант: очистка состояния
static void mylib_clear_error(mylib_ctx_t *ctx) {
    if (!ctx) return;
    ctx->err.code = ERR_OK;
    ctx->err.message[0] = '\0';
}

// Безопасная установка ошибки
static void mylib_set_error(mylib_ctx_t *ctx, err_t code, const char *msg) {
    if (!ctx) return;
    ctx->err.code = code;
    // snprintf безопасен: всегда ставит '\0' и не читает за пределами msg
    snprintf(ctx->err.message, sizeof(ctx->err.message), "%s", msg ? msg : "Unknown error");
}

mylib_ctx_t *mylib_create(void) {
    mylib_ctx_t *ctx = calloc(1, sizeof(*ctx)); // calloc обнуляет память
    return ctx;
}

void mylib_destroy(mylib_ctx_t *ctx) {
    free(ctx);
}

// Публичная функция с принудительной проверкой возврата (Паттерн 17)
__attribute__((warn_unused_result))
err_t mylib_do_operation(mylib_ctx_t *ctx, int param) {
    if (!ctx) return ERR_LIB_INVALID_ARG;
    
    // 1. ЖЕСТКИЙ ИНВАРИАНТ: Очищаем ошибку в первой строке
    mylib_clear_error(ctx); 
    
    if (param < 0) {
        mylib_set_error(ctx, ERR_LIB_INVALID_ARG, "param must be non-negative");
        return ERR_LIB_INVALID_ARG;
    }
    if (param == 0) {
        mylib_set_error(ctx, ERR_LIB_INTERNAL, "internal failure simulated");
        return ERR_LIB_INTERNAL;
    }
    return ERR_OK;
}

const error_state_t *mylib_last_error(const mylib_ctx_t *ctx) {
    if (!ctx) return NULL;
    return &ctx->err;
}
```

## 4. Интеграция с другими паттернами

### 4.1. Комбинация с `err_t` ([Паттерн 01](01_return_code_out_params.md))

Внешнее API использует `err_t` для управления потоком (ветвления `if/else`), а `error_state_t` — для диагностики (логирование, UI). Это идеальное разделение ответственности.

### 4.2. Безопасный маппинг `errno` ([Паттерн 02](02_sentinel_errno.md))

При обертывании POSIX-вызовов необходимо преобразовывать `errno` в строку. \
**Внимание:** стандартная `strerror(errno)` не является потокобезопасной в некоторых реализациях. В многопоточных библиотеках следует использовать `strerror_r` (POSIX) или явно документировать ограничения.

```c
#include <errno.h>
#include <string.h>

static void mylib_set_error_from_errno(mylib_ctx_t *ctx, err_t code, const char *prefix) {
    if (!ctx) return;
    char buf[256];
    
    // Вариант для POSIX (потокобезопасный):
    // strerror_r(errno, buf, sizeof(buf)); 
    
    // Вариант для чистого C11 (если библиотека однопоточная или errno не затирается):
    snprintf(buf, sizeof(buf), "%s: %s", prefix ? prefix : "System error", strerror(errno));
    mylib_set_error(ctx, code, buf);
}
```

### 4.3. Эволюция в Обогащение Контекста ([Паттерн 14](14_error_context_wrapping.md))

Если библиотеке нужно не просто хранить последнюю ошибку, но и "обрамлять" её контекстом при пробросе через слои абстракции (например, добавлять имя файла или номер строки), используется надстройка над этим паттерном — макросы `WRAP_ERR` с `vsnprintf`.

## 5. Критические риски и правила безопасности (Must Read)

### 5.1. Состояние гонки (Race Conditions)

Если вы передадите один `mylib_ctx_t` в два разных потока (например, в worker pool), и Поток А установит ошибку, а Поток Б вызовет `mylib_last_error`, Поток Б прочитает ошибку Потока А.

- **Решение:** Либо каждый поток создает свой контекст (рекомендуется), либо библиотека использует `_Thread_local` для хранения `error_state_t` внутри контекста, либо доступ защищается мьютексом (что убивает производительность).

### 5.2. Фиксированный буфер vs Динамическая память

Почему мы используем `char message[128]`, а не `char *message` с `malloc`?

- **Причина:** Обработчик ошибок **никогда не должен падать с OOM**. Если система исчерпала память (что и вызвало ошибку `ERR_NO_MEM`), вызов `malloc` внутри `set_error` вернет `NULL`, и мы потеряем информацию о первопричине сбоя. Фиксированный буфер решает эту проблему ценой небольшого перерасхода памяти.

### 5.3. Иллюзия успешного вызова

Если функция возвращает `ERR_OK`, но внутри нее забыли вызвать `mylib_clear_error`, а до этого была ошибка, `mylib_last_error` вернет старую ошибку.

- **Решение:** Автоматизация. Напишите макрос или используйте статический анализ, чтобы гарантировать вызов `clear_error` в прологе каждой публичной функции.

### 5.4. Переход в "Залипшее" состояние ([Паттерн 09](09_latched_error_state.md))

Если ошибка является фатальной (например, разрыв сетевого соединения), простого обновления `error_state_t` недостаточно. Объект должен перейти в состояние `FAILED`, и все последующие вызовы должны немедленно возвращать ошибку, не пытаясь выполнить работу. Контекст ошибок идеально ложится в архитектуру "Circuit Breaker" (Предохранитель).

---

## 6. Практические рекомендации (Best Practices)

1. **Принудительная проверка:** Помечайте функции, возвращающие `err_t`, атрибутом `__attribute__((warn_unused_result))` или `[[nodiscard]]` ([Паттерн 17](17_compiler_enforced_return_checking.md)). Игнорирование кода возврата в связке с контекстом ошибок ведет к чтению "мусорного" состояния.
2. **Очистка на входе:** `clear_error(ctx)` должна быть первой строкой кода в каждой публичной функции, сразу после проверки `ctx` на `NULL`.
3. **Документирование времени жизни (TTL):** Четко укажите в документации: "Ошибка очищается при следующем вызове любой функции библиотеки" или "Ошибка является залипающей (latched) до явного вызова clear".
4. **Избегайте `malloc` в путях обработки ошибок:** Используйте стековые буферы фиксированного размера (`char buf[N]`) и `snprintf`.
