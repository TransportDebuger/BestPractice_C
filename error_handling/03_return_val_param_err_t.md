# Паттерн обработки ошибок: Return полезного значения + статус через аргумент

title: "Паттерн обработки ошибок: Return полезного значения + статус через аргумент"\
date: "2026-07-01"\
version: "v1.0"\
standards: "C11 (базовый); GCC/Clang extensions (warn_unused_result); C23 ([[nodiscard]])"\
prerequisites:

- Базовое владение C (функции, указатели, перечисления).
- Понимание паттерна [Паттерн 01: Return-код + out-параметры](01_return_code_out_params.md).
- Знакомство с [Каталогом паттернов](00_pattern_catalog.md).
  
objective:

- Описать паттерн возврата полезного значения через `return` с передачей статуса ошибки через аргумент-указатель.
- Сформулировать строгие инварианты контракта (детерминизм return-значения при ошибке, опциональность `NULL`).
- Показать преимущества (читаемость, гибкость) и риски (игнорирование ошибки, двухканальность).
- Определить нишу паттерна в архитектуре C-библиотек.

theory:
  Паттерн предполагает, что функция возвращает основной результат через оператор `return`, а код ошибки передает через дополнительный параметр-указатель (обычно `err_t *err`).
  Этот подход занимает промежуточное положение между классическим [Паттерном 01](01_return_code_out_params.md) (`err_t` + out-параметры) и функциональными структурами [Паттерна 04](04_result_struct.md) (`Result` / `Tagged Union`).
  Ключевая философская установка: «Результат — это главное, ошибка — это дополнение». Если функция логически является «генератором значения» (парсер, математическая операция, поиск), то помещение значения в `return` делает код вызывающей стороны более выразительным. Возможность передать `NULL` вместо указателя на статус позволяет гибко управлять уровнем детализации.

---

## 1. Описание и строгий контракт

### 1.1. Формальное описание

```c
typedef enum {
    ERR_OK = 0,
    ERR_INVALID_ARG,
    ERR_NOT_FOUND,
    ERR_DIVIDE_BY_ZERO
} err_t;

// Возвращает полезное значение, статус пишет в err
int safe_divide(int a, int b, err_t *err);

// Возвращает указатель на объект, статус пишет в err
user_t *user_db_find(user_db_t *db, int user_id, err_t *err);
```

### 1.2. Жесткий контракт (Инварианты)

1. **Детерминизм return-значения (Safe Default).** При `*err != ERR_OK` возвращаемое значение **обязано** быть приведено к безопасному "пустому" состоянию (обычно `0`, `NULL` или `-1`). Возвращать мусор из стека или частичные данные недопустимо. Вызывающий код может по ошибке проверить `return` до проверки `err`, и это не должно приводить к UB.
2. **Опциональность статуса (NULL-tolerance).** Вызывающий код имеет право передать `NULL` вместо указателя `err`, если ему не нужна детализация ошибки (только факт успеха/неуспеха по return-значению). Функция **обязана** корректно обрабатывать `err == NULL` (не падать с SIGSEGV).
3. **Инициализация статуса.** При успешном завершении функция обязана записать `ERR_OK` в `*err` (если `err != NULL`).

---

## 2. Плюсы и минусы

### 2.1. Плюсы

- **Выразительность и читаемость.** Код `int val = get_val(ctx, &err);` читается естественнее, чем `err_t err = get_val(ctx, &val);`, особенно для математических операций и парсеров.
- **Гибкость детализации.** Можно передать `NULL`, если ошибка не важна: `int val = get_val(ctx, NULL);`. Это позволяет не загромождать код проверками, если "неуспех" означает просто "использовать дефолтное значение".
- **Отсутствие копирования.** В отличие от [Паттерна 04](04_result_struct.md) (`Result`-структур), здесь нет накладных расходов на копирование `struct` по значению.

### 2.2. Минусы и риски

- **Двухканальность информации.** Статус "размазан" по двум каналам (`return` и `out-arg`). Это требует четкой документации и дисциплины: вызывающий код должен знать, какое return-значение соответствует ошибке (например, `NULL` для указателей, `0` для целых).
- **Риск игнорирования ошибки.** Указатель `err` можно не проверить, если return-значение кажется валидным. Компилятор не может принудительно проверить указатель на `err` так же легко, как `[[nodiscard]]` для `err_t` (см. [Паттерн 17](17_compiler_enforced_return_checking.md)).
- **Ограниченность для сложных данных.** Паттерн плохо подходит, если нужно вернуть несколько разнородных значений (например, строку и её длину). Для этого лучше использовать [Паттерн 01](01_return_code_out_params.md).

## 3. Простой пример: Математическая операция

```c
#include <stddef.h>

typedef enum {
    ERR_OK = 0,
    ERR_INVALID_ARG,
    ERR_DIVIDE_BY_ZERO
} err_t;

int safe_divide(int a, int b, err_t *err) {
    // 1. Инициализация статуса (если указатель не NULL)
    if (err) *err = ERR_OK;

    // 2. Проверка предусловий
    if (b == 0) {
        if (err) *err = ERR_DIVIDE_BY_ZERO;
        return 0; // Детерминизм: при ошибке возвращаем Safe Default (0)
    }

    // 3. Успех
    return a / b;
}

// Использование:
// Вариант А: С детализацией
err_t e;
int res = safe_divide(10, 0, &e);
if (e != ERR_OK) { /* обработка */ }

// Вариант Б: Без детализации (NULL-tolerant)
int res2 = safe_divide(10, 2, NULL); 
```

## 4. Развёрнутый пример: Поиск в коллекции

```c
#include <stddef.h>

typedef struct { int id; const char *name; } user_t;
typedef struct user_db user_db_t;

// Возвращает указатель на пользователя или NULL
user_t *user_db_find(user_db_t *db, int user_id, err_t *err) {
    if (err) *err = ERR_OK;

    if (!db) {
        if (err) *err = ERR_INVALID_ARG;
        return NULL; // Safe Default для указателя
    }

    // ... логика поиска ...
    user_t *found = /* ... internal search ... */;

    if (!found) {
        if (err) *err = ERR_NOT_FOUND;
        return NULL;
    }

    return found;
}
```

## 5. Взаимодействие с другими паттернами

### 5.1. vs Паттерн 01 (`err_t` + out-параметры)

- **[Паттерн 01](01_return_code_out_params.md)** (`err_t func(..., T *out)`) лучше, когда нужно вернуть несколько значений, сложную структуру, или когда ошибка является *основным* событием (например, загрузка файла).
- **Паттерн 03** (`T func(..., err_t *err)`) лучше для скалярных типов (`int`, `double`) и указателей, где функция логически является "генератором значения" (парсер, поиск, вычисление).

### 5.2. vs Паттерн 04 (`Result` / `Optional`)

- **[Паттерн 04](04_result_struct.md)** упаковывает всё в одну структуру, что позволяет применять `[[nodiscard]]` и защищает от потери ошибки. Но требует копирования.
- **Паттерн 03** быстрее (нет копирования), но менее безопасен на уровне компилятора (легко забыть проверить `err`).

---

### 6. Практические рекомендации (Best Practices)

1. **Документирование "Safe Default".** В комментарии к функции явно укажите, какое значение возвращается при ошибке (например, `@return 0 on error, actual value on success`).
2. **Всегда поддерживайте `NULL`.** Реализация должна содержать `if (err) *err = ...`. Это позволяет вызывающему коду использовать функцию в однострочных выражениях без создания временных переменных для статуса.
3. **Избегайте для сложных структур.** Если `T` — это большая структура, возвращайте её по указателю (как в примере с `user_t *`), а не по значению, чтобы избежать накладных расходов.
4. **Комбинируйте с контекстом ошибок.** Если детализации через `err_t` не хватает, используйте этот паттерн в связке с [Паттерном 06](06_error_context.md) (Контекст ошибок): `err_t` возвращает быстрый код, а `lib_last_error(ctx)` хранит строковое сообщение.
