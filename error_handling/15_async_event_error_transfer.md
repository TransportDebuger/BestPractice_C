- Описать механику передачи ошибок в асинхронных и событийно-ориентированных системах.
- Сформулировать строгие контракты владения (ownership) и времени жизни контекста запроса.
- Разобрать критические риски: гонки при отмене (cancellation), thread affinity и утечки контекста.
- Показать индустриальный стандарт (единый `status` код) на примере современных фреймворков.

theory:
  В синхронном C стек вызовов служит каналом для возврата `err_t` ([Паттерн 01](01_return_code_out_params.md)) или `errno` ([Паттерн 02](02_sentinel_errno.md)). В асинхронном C (сетевые демоны, драйверы, `io_uring`) функция инициирует операцию и возвращает управление *немедленно*. Ошибка возникает в другом потоке (I/O thread) или в будущем.\
  Следовательно, ошибка не может быть возвращена через `return`. Она должна быть **упакована в событие завершения** (completion event) или передана в **callback завершения**.\
  Ключевой философский сдвиг: **Ошибка в асинхронном коде — это не исключительная ситуация, а просто переход конечного автомата (FSM) в состояние `FAILED` или `TEARDOWN`**. Обработка ошибки сводится к корректной очистке ресурсов и уведомлению вышестоящего уровня.

## 1. Описание и строгий контракт

### 1.1. Индустриальный стандарт: Единый `status`

В современных высокопроизводительных фреймворках (libuv, io_uring) отказываются от разделения `result` и `error_code`. Вместо этого используется единое поле `status` (или `res`):

- `status >= 0`: Успех (количество обработанных байт, дескриптор и т.д.).
- `status < 0`: Ошибка (значение равно `-errno`, например, `-ECONNRESET`, `-ENOMEM`).

```c
#include <stdlib.h>
#include <sys/types.h>

// Контекст запроса (должен жить до момента вызова callback!)
typedef struct io_req {
    int fd;
    void *buf;
    size_t len;
    
    // Callback завершения
    void (*completion_cb)(struct io_req *req, int status);
    
    // Внутренние поля для движка
    void *engine_private; 
} io_req_t;

// Инициирование асинхронного чтения
int async_read_submit(io_req_t *req);
```

### 1.2. Жесткие контракты и инварианты

1. **Инвариант времени жизни (Lifetime Rule).** Структура `io_req_t` **обязана** оставаться валидной в памяти до тех пор, пока не будет вызван `completion_cb`. Освобождать `req` внутри функции `async_read_submit` или сразу после неё — катастрофическая ошибка (Use-After-Free).
2. **Инвариант однократности вызова (Exactly-Once).** Движок гарантирует, что `completion_cb` будет вызван **ровно один раз** для каждого успешно сабмиченного запроса, независимо от того, завершился он успехом, ошибкой или был отменен.
3. **Инвариант контекста потока (Thread Affinity).** `completion_cb` обычно вызывается в потоке цикла событий (event loop). Внутри него **запрещено** выполнять блокирующие операции (синхронный I/O, `malloc` больших объемов, `sleep`).

## 2. Области применения

Паттерн является безальтернативным стандартом для:

- **Высоконагруженных сетевых серверов:** Nginx, Node.js (libuv), Envoy.
- **Современных интерфейсов ввода-вывода:** Linux `io_uring`, POSIX AIO.
- **Драйверов устройств и embedded-систем:** Обработка прерываний (IRQ) и DMA-трансферов.
- **GUI-фреймворков:** Асинхронная загрузка ресурсов без блокировки главного потока.

## 3. Плюсы и минусы

### 3.1. Плюсы

- **Масштабируемость.** Позволяет обрабатывать десятки тысяч одновременных операций на одном потоке (нет накладных расходов на создание потоков/стеков).
- **Естественность для FSM.** Ошибки (обрыв сети, таймауты) органично вписываются в модель конечных автоматов как переходы в состояния очистки.
- **Отсутствие неявного потока управления.** В отличие от `setjmp/longjmp` ([Паттерн 11](11_setjmp_longjmp.md)) или исключений, асинхронный код всегда выполняется явными шагами (step-by-step).

### 3.2. Минусы и риски

- **Сложность отладки.** Стек вызовов в момент ошибки не содержит пути от точки инициации до точки завершения. Трассировка требует явного логирования состояний FSM.
- **Риск гонок при отмене (Cancellation Races).** Если таймаут сработал, но I/O операция уже завершалась в ядре, кто освобождает память?
- **Громоздкость кода.** Написание сложных сценариев (например, "прочитать 3 файла и объединить") требует ручного написания state machine или использования сложных макросов/корутин.

## 4. Простой пример: Callback завершения

```c
#include <stdio.h>
#include <stdlib.h>
#include <errno.h>

// Пользовательский callback
void on_data_read(io_req_t *req, int status) {
    if (status < 0) {
        // Ошибка! status содержит -errno (например, -EIO, -ECONNRESET)
        fprintf(stderr, "Async read failed: %s\n", strerror(-status));
    } else {
        // Успех: status == количество прочитанных байт
        printf("Successfully read %d bytes\n", status);
        // ... обработка буфера req->buf ...
    }
    
    // ПРАВИЛО ВЛАДЕНИЯ: Тот, кто аллоцировал req, тот его и освобождает 
    // ПОСЛЕ завершения callback.
    free(req->buf);
    free(req);
}

void start_operation(int fd) {
    io_req_t *req = calloc(1, sizeof(*req));
    req->fd = fd;
    req->buf = malloc(4096);
    req->completion_cb = on_data_read;
    
    // Передаем владение контекстом в асинхронный движок
    if (async_read_submit(req) < 0) {
        // Ошибка инициации (синхронная, например, EINVAL)
        // Движок НЕ вызовет callback, если сабмит не прошел.
        // Мы обязаны очистить память сами!
        free(req->buf);
        free(req);
    }
}
```

## 5. Развёрнутый пример: Гонка отмены и Time-To-Live

Самая сложная проблема асинхронных ошибок — **отмена (cancellation)**. Что делать, если пользователь устал ждать и хочет закрыть соединение, но операция `read` уже ушла в ядро?

### 5.1. Паттерн "Токена отмены" (Cancellation Token)

Чтобы избежать Use-After-Free, мы используем атомарный флаг или счетчик ссылок, чтобы синхронизировать намерение отмены и фактическое завершение I/O.

```c
#include <stdatomic.h>

typedef enum {
    REQ_STATE_PENDING,
    REQ_STATE_CANCELLED,
    REQ_STATE_COMPLETED
} req_state_t;

struct io_req {
    // ... поля ...
    _Atomic req_state_t state;
    void (*completion_cb)(struct io_req *req, int status);
};

// Внутренняя функция движка (вызывается из I/O потока)
static void engine_complete(io_req_t *req, int status) {
    req_state_t expected = REQ_STATE_PENDING;
    
    // Пытаемся атомарно перевести в COMPLETED. 
    // Если уже CANCELLED, значит пользователь уже освободил (или освободит) память.
    if (atomic_compare_exchange_strong(&req->state, &expected, REQ_STATE_COMPLETED)) {
        // Мы выиграли гонку. Вызываем callback.
        req->completion_cb(req, status);
    } else {
        // Пользователь уже отменил запрос. 
        // Движок просто проглатывает ошибку/результат и не трогает память.
        // (Освобождение памяти берет на себя поток отмены).
    }
}

// Функция отмены (вызывается из потока приложения)
void async_read_cancel(io_req_t *req) {
    req_state_t expected = REQ_STATE_PENDING;
    if (atomic_compare_exchange_strong(&req->state, &expected, REQ_STATE_CANCELLED)) {
        // Мы выиграли гонку. I/O еще не завершилось.
        // Отменяем в движке и освобождаем память.
        engine_cancel_internal(req);
        free(req->buf);
        free(req);
    }
    // Если exchange не удался, значит I/O уже завершилось (или завершается).
    // Мы ничего не делаем, ждем вызова completion_cb.
}
```

## 6. Критические риски (Must Read)

### 6.1. Use-After-Free при таймаутах

**Сценарий катастрофы:** Приложение ставит таймер на 5 секунд. Таймер срабатывает, приложение считает, что сеть "умерла", и вызывает `free(req)`. Но в этот же момент ядро ОС завершает `read` и вызывает `completion_cb` с `status = -ECONNRESET`. Движок обращается к уже освобожденной памяти -> **Segmentation Fault**.
**Решение:** Использовать атомарные состояния (как в разделе 5.1) или счетчики ссылок (refcounting), чтобы гарантировать, что память освободится только тогда, когда и таймер, и I/O движок закончили с ней работать.

### 6.2. Блокировка Event Loop

Если в `completion_cb` (который работает в потоке `epoll_wait` / `io_uring_enter`) вы вызовете `fprintf`, `malloc` (с блокировкой аллокатора) или синхронный `read`, вы **остановите весь сервер**. Ошибки в асинхронном коде должны обрабатываться путем изменения состояния FSM и постановки задач в очередь воркеров, а не прямым выполнением.

### 6.3. Потеря `errno` и контекста

В асинхронных callback `errno` ([Паттерн 02](02_sentinel_errno.md)) **не имеет смысла**, так как callback вызывается в другом потоке и в другое время. Движок обязан сам перехватить `errno` сразу после системного вызова и упаковать его в `status` (со знаком минус).
Аналогично, если вы используете контекст ошибок ([Паттерн 06](06_error_context.md)), вы не можете просто вызвать `lib_set_error` из I/O потока, если `lib_ctx_t` не потокобезопасен. Ошибку нужно положить в `io_req_t` и передать в поток приложения.

## 7. Взаимодействие с другими паттернами

### 7.1. Синергия с Паттерном 09 (Latched State)

Если асинхронное соединение получает фатальную ошибку (например, `-EPIPE`), оно должно перейти в [Latched State (Паттерн 09)](09_latched_error_state.md). Все последующие сабмиты на этот `fd` должны немедленно возвращать ошибку через callback, не обращаясь к ядру.

### 7.2. Синергия с Паттерном 10 (Goto-cleanup)

Внутри самого callback-а, если происходит сложная обработка результата (например, парсинг прочитанных данных), мы возвращаемся к синхронной модели и используем `err_t` + `goto-cleanup` для локальных ресурсов.

## 8. Практические рекомендации (Best Practices)

1. **Используйте единый `status`.** Возврат `ssize_t result` и `int error` отдельно — это наследие синхронного POSIX. В асинхронном C используйте `int status`, где `< 0` означает `-errno`. Это упрощает FSM.
2. **Жесткий контракт владения.** Документируйте правило: *"Память `req` освобождается вызывающим кодом строго внутри `completion_cb` или после синхронной ошибки сабмита"*.
3. **Атомарная отмена.** Если ваш API поддерживает отмену, используйте `_Atomic` флаги состояния для предотвращения гонок между таймаутом и I/O завершением.
4. **Логирование состояний.** Поскольку стек вызовов бесполезен, внедрите макрос `REQ_LOG(req, "Transition to FAILED state: %d", status)`, который будет писать ID запроса и его FSM-переходы. Это единственный способ отлаживать асинхронный код.
5. **Fail-Fast в callback.** Если в `completion_cb` обнаруживается нарушение инвариантов (например, `req` уже был освобожден), используйте [Паттерн 13 (Fail-Fast)](13_fail_fast_assert.md) и вызывайте `abort()`. Тихая деградация в event loop недопустима.
