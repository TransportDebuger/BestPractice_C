# Паттерн 08: Маркеры состояния и конца потока (State/EOF Markers)

- Описать паттерн использования специальных значений как маркеров естественного завершения, а не ошибок.
- Жестко разграничить семантику Паттерна 08 (норма) и Паттерна 02 (сбой).

- Сформулировать строгие правила проверки состояния после достижения маркера.

theory:
  В языке C многие операции по своей природе являются итеративными или потоковыми (чтение файла, обход дерева, получение сообщений из очереди). Рано или поздно источник данных исчерпывается.\
  Паттерн «Маркеры состояния» предполагает использование специального значения (маркера), которое сигнализирует не о сбое, а о том, что операция выполнена успешно, но продолжать нечего (конец файла, конец списка, очередь пуста).\
  Ключевой принцип: **Достижение маркера не должно рассматриваться как ошибка**. Это штатный сценарий, который управляет потоком выполнения (например, завершает цикл `while`), в то время как истинные ошибки среды (сбой диска, обрыв сети) должны обрабатываться отдельно, как описано в [Паттерне 02](02_sentinel_errno.md).

## 1. Описание и строгий контракт

### 1.1. Формальное описание

Функция возвращает значение, которое формально находится за пределами множества корректных полезных данных, но при этом не устанавливает индикаторы фатальных ошибок.

```c
// I/O маркер
int c = fgetc(FILE *stream); // Возвращает EOF при естественном конце

// Итераторный маркер
node_t *current = list_get_next(list); // Возвращает NULL при достижении конца

// Маркер конечного автомата (FSM)
fsm_state_t state = fsm_step(fsm); // Возвращает STATE_DONE при завершении
```

### 1.2. Жесткий контракт (Инварианты)

1. **Инвариант недвусмысленности.** Маркер должен быть строго отделен от валидных данных. Классический пример: `fgetc` возвращает `int`, а не `char`, именно для того, чтобы значение `EOF` (обычно `-1`) не конфликтовало с валидным байтом `0xFF` (255).
2. **Инвариант ортогональности ошибке.** Достижение маркера (например, `EOF`) не должно оставлять поток или объект в состоянии `ferror()`. Состояние «успешно достигнут конец» и «произошла ошибка чтения» должны быть ортогональны.
3. **Инвариант обязательной проверки.** Возвращаемое значение, являющееся маркером, **обязано** проверяться вызывающим кодом. Игнорирование маркера приводит к бесконечным циклам или обработке мусорных данных.

## 2. Области применения

Паттерн является де-факто стандартом для:

- **Потокового ввода-вывода:** `fgetc`, `fgets`, `read` (возврат `0` как маркер EOF).
- **Итераторов и обхода структур данных:** возврат `NULL` при исчерпании элементов связного списка, хеш-таблицы или массива.
- **Конечных автоматов (FSM):** возврат специального состояния (например, `FSM_STATE_TERMINATED`), указывающего на успешное завершение машины состояний.
- **Очердей сообщений:** возврат специального кода (например, `QUEUE_EMPTY`), означающего, что сообщений пока нет, но это не является сбоем системы.

## 3. Плюсы и минусы

### 3.1. Плюсы

- **Естественное управление потоком.** Позволяет элегантно завершать циклы (`while ((c = fgetc(f)) != EOF)`), не загромождая код обработчиками исключительных ситуаций.
- **Отсутствие «ложных тревог».** Система мониторинга или логирования не будет спамить алертами о «ошибках», когда файл просто закончился.
- **Высокая производительность.** Проверка маркера (например, сравнение с `NULL` или `EOF`) обычно сводится к одной инструкции процессора, в отличие от проверки флагов ошибок.

### 3.2. Минусы и риски

- **Классическая ловушка смешивания.** Самая частая ошибка в C: разработчик видит `EOF` и считает, что файл прочитан, игнорируя тот факт, что `EOF` мог быть достигнут из-за аппаратной ошибки чтения (в этом случае `ferror()` будет истинным).
- **Требует дисциплины типов.** Если маркер и валидные данные имеют один тип (например, попытка использовать `-1` как маркер для функции, возвращающей знаковый `int`, где `-1` может быть валидным результатом), это ведет к трудноуловимым багам.

### 4. Простой пример: Итератор связного списка

Здесь `NULL` выступает не как ошибка выделения памяти, а как штатный маркер конца коллекции.

```c
#include <stddef.h>

typedef struct node {
    int value;
    struct node *next;
} node_t;

// Возвращает маркер NULL при естественном завершении обхода
// Игнорирование может привести к разыменованию NULL или бесконечному циклу
__attribute__((warn_unused_result)) 
static inline node_t *list_next(node_t *current) {
    return current ? current->next : NULL;
}

void print_list(node_t *head) {
    // NULL здесь — это Паттерн 08 (конец данных), а не ошибка.
    for (node_t *curr = head; curr != NULL; curr = list_next(curr)) {
        printf("%d ", curr->value);
    }
    printf("\n");
}
```

## 5. Развёрнутый пример: Чтение файла и разделение EOF / Ошибки

Это самый важный пример, демонстрирующий взаимодействие Паттерна 08 и [Паттерна 02](02_sentinel_errno.md).

```c
#include <stdio.h>
#include <stdlib.h>

// Чтение и подсчет всех байт в файле
__attribute__((warn_unused_result))
int count_file_bytes(const char *path) {
    FILE *f = fopen(path, "rb");
    if (!f) {
        // Это Паттерн 02: реальная ошибка среды (файл не найден, нет прав)
        perror("fopen failed");
        return -1;
    }

    int count = 0;
    int c;

    // Цикл управляется маркером Паттерна 08 (EOF)
    while ((c = fgetc(f)) != EOF) {
        count++;
    }

    // КРИТИЧЕСКИ ВАЖНЫЙ ШАГ: Разделение семантики после выхода из цикла
    if (ferror(f)) {
        // Мы достигли конца не потому, что файл закончился, а потому что случилась ошибка.
        // Теперь это Паттерн 02.
        perror("Read error occurred before EOF");
        fclose(f);
        return -1;
    }

    // Если мы здесь, значит ferror(f) == 0, и мы достигли штатного EOF (Паттерн 08)
    fclose(f);
    return count;
}
```

**Анализ:** Если бы мы опустили проверку `ferror(f)`, функция вернула бы частичный `count` при сбое диска, и вызывающий код считал бы это успешным прочтением. Маркер `EOF` лишь говорит «чтение остановилось», а `ferror()` уточняет «почему».

## 6. Взаимодействие с другими паттернами

### 6.1. Мостик к Паттерну 02 (Sentinel + errno)

Маркер сам по себе нейтрален. Но как только мы выясняем, что маркер был достигнут из-за сбоя (через `ferror()`, `errno` или проверку сокета), мы мгновенно переключаемся на [Паттерн 02](02_sentinel_errno.md) для обработки этой ошибки.

### 6.2. Мостик к Паттерну 09 (Latched error state)

Если при попытке достичь маркера (например, прочитать следующий пакет из сети) происходит фатальная ошибка (разрыв соединения), объект (сокет) должен перейти в [Latched State (Паттерн 09)](09_latched_error_state.md). Все последующие попытки чтения должны сразу возвращать ошибку, а не маркер «пусто».

### 6.3. Эволюция в Паттерн 04 (Result / Tagged Union)

Трюки с типами (как `fgetc`, возвращающий `int` вместо `char`) — это плата за отсутствие алгебраических типов в классическом C. В современном C11 для возврата «либо данные, либо маркер конца» всё чаще используют [Паттерн 04 (Tagged Union)](04_result_struct.md), где маркер и ошибка разделены на уровне компилятора.

## 7. Практические рекомендации (Best Practices)

1. **Всегда проверяйте `ferror()` после `EOF`.** Это золотое правило POSIX I/O. `EOF` означает лишь «данных больше нет», но не гарантирует, что последние данные были прочитаны корректно.
2. **Соблюдайте корректность типов для маркеров.** Никогда не используйте маркер, который может быть легальным значением данных. Именно поэтому `fgetc` возвращает `int`, а не `char`.
3. **Используйте `[[nodiscard]]` или `warn_unused_result`.** Компилятор должен предупреждать, если вы вызываете функцию-итератор или функцию чтения и игнорируете её результат (см. [Паттерн 17](17_compiler_enforced_return_checking.md)). Игнорирование маркера конца потока — это почти всегда логическая ошибка.
4. **Документируйте маркер в контракте.** В комментарии к функции явно указывайте: `@return Указатель на следующий элемент или NULL, если список исчерпан (не является ошибкой)`.
