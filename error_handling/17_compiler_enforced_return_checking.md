theory:\
  Главный архитектурный недостаток C в контексте обработки ошибок — отсутствие скрытого потока управления (исключений). Если вызывающий код напишет `init_system();` вместо `err_t err = init_system();`, программа продолжит выполнение, даже если система не инициализирована.\
  Паттерн Compiler-Enforced Return Checking переносит контроль ошибок из плоскости «runtime-логики» и «человеческой дисциплины» в плоскость «статического анализа». Если функция помечена соответствующим атрибутом, компилятор выдаст предупреждение (или ошибку), если её результат не будет использован.\
  Ключевой философский принцип: __Если возвращаемое значение содержит статус ошибки или владеющий ресурс, его игнорирование должно быть запрещено на этапе компиляции.__

## 1. Описание и строгий контракт

### 1.1. Эволюция инструментов

В индустрии используется два основных инструмента, в зависимости от целевого стандарта:

1. __Расширение GCC/Clang (C11 и ранее):__

   ```c
   __attribute__((warn_unused_result))
   err_t init_system(void);
   ```

2. __Стандарт C23 (Современный подход):__

   ```c
   [[nodiscard("Ignoring init status leads to undefined behavior")]]
   err_t init_system(void);
   ```

### 1.2. Макрос кросс-компиляции (Best Practice)

Для библиотек, которые должны собираться как на старых, так и на новых компиляторах, используется макрос-адаптер:

```c
#if defined(__STDC_VERSION__) && __STDC_VERSION__ >= 202311L
    // C23 и новее
    #define NODISCARD [[nodiscard]]
    #define NODISCARD_MSG(msg) [[nodiscard(msg)]]
#elif defined(__GNUC__) || defined(__clang__)
    // GCC / Clang (C11)
    #define NODISCARD __attribute__((warn_unused_result))
    #define NODISCARD_MSG(msg) __attribute__((warn_unused_result))
#else
    // Fallback для других компиляторов (например, MSVC в режиме strict C)
    #define NODISCARD
    #define NODISCARD_MSG(msg)
#endif

// Использование:
NODISCARD_MSG("Resource leak if ignored")
void *alloc_buffer(size_t size);
```

### 1.3. Жесткие контракты

1. __Абсолютная обязательность.__ Если функция помечена `NODISCARD`, вызывающий код *обязан* присвоить результат переменной, передать его в другую функцию или явно обработать.
2. __Семантическая нагрузка.__ Атрибут применяется только к тем функциям, где игнорирование возврата ведет к утечкам памяти, некорректному состоянию или уязвимостям. Не стоит помечать им функции, где возврат — это просто «справочная» информация (например, `strlen`).

## 2. Области применения

Паттерн является обязательным для:

- __Функций аллокации памяти:__ `malloc`, `calloc`, кастомные аллокаторы. Игнорирование `NULL` ведет к SIGSEGV.
- __Функций инициализации ресурсов:__ `fopen`, `open`, `pthread_mutex_init`.
- __Функций, возвращающих `err_t` или `Result`:__ Любое API, построенное на [Паттерне 01](01_return_code_out_params.md), [Паттерне 04](04_result_struct.md) или [Паттерне 09](09_latched_error_state.md).
- __Функций, меняющих глобальное/контекстное состояние:__ Если функция не вернула успех, состояние могло не измениться, и вызывающий код должен знать об этом.

## 3. Плюсы и минусы

### 3.1. Плюсы

- __Нулевой runtime-overhead.__ Вся проверка происходит на этапе компиляции. В бинарнике нет ни одного лишнего байта или инструкции.
- __Защита от «человеческого фактора».__ Разработчик может забыть проверить `err_t` при рефакторинге. Компилятор не даст такому коду скомпилироваться (или хотя бы выдаст громкий warning).
- __Самодокументируемость.__ Наличие `[[nodiscard]]` в сигнатуре сразу говорит читателю: «Эта функция может упасть, и её статус критически важен».

### 3.2. Минусы

- __Шум при рефакторинге.__ Если вы изменили API и добавили `NODISCARD`, вам придется переписать все места вызова, где результат ранее игнорировался.
- __Проблема явного игнорирования.__ Иногда статус действительно не важен (например, при попытке очистки ресурса в деструкторе). В C23 механизм явного игнорирования стал сложнее (см. раздел 5).

## 4. Продвинутый уровень: `[[nodiscard]]` для типов (C23)

Одна из самых мощных фич C23 — возможность применять `[[nodiscard]]` не только к функциям, но и к __типам__ (`struct`, `union`, `enum`). Если функция возвращает тип, помеченный этим атрибутом, компилятор автоматически потребует проверить результат.

Это идеально решает проблему бойлерплейта для [Паттерна 04 (Result)](04_result_struct.md).

```c
// C23: Атрибут применяется к типу
typedef struct [[nodiscard("Ignoring Result may leak memory or cause UB")]] {
    bool is_ok;
    union { int val; err_t err; } data;
} result_int_t;

// Функция не требует явного атрибута, он наследуется от типа!
result_int_t parse_int(const char *s); 

void demo(void) {
    parse_int("42"); 
    // ОШИБКА КОМПИЛЯЦИИ: ignoring return value of function declared with 'nodiscard' attribute
}
```

__Преимущество:__ Вы защищаете от игнорирования *все* функции, возвращающие `result_int_t`, просто определив атрибут один раз в месте объявления типа.

## 5. Критическая ловушка: Приведение к `(void)` в C23 (Must Read)

Это самый важный нюанс, разделяющий C11 (GCC) и C23.

__В GCC/Clang (`warn_unused_result`):__
Если вы намеренно хотите игнорировать результат, вы приводили его к `void`:

```c
(void)close(fd); // Подавляет warn_unused_result
```

__В C23 (`[[nodiscard]]`):__\
Стандарт C23 явно указывает, что __приведение к `(void)` больше не отменяет `[[nodiscard]]`__.

```c
// C23
[[nodiscard]] err_t init_system(void);

(void)init_system(); 
// ВНИМАНИЕ: Компилятор ВСЁ РАВНО выдаст предупреждение/ошибку!
```

__Как правильно игнорировать `[[nodiscard]]` в C23?__\
Если вы абсолютно уверены, что ошибку можно безопасно проигнорировать (например, `free` или `fclose`), стандартизованный способ — присвоить результат в «мусорную» переменную:

```c
// Способ 1: Присваивание в dummy-переменную
err_t dummy = init_system(); 
(void)dummy; // Подавление warning за неиспользуемую переменную

// Способ 2: Использование макроса-обертки (если библиотека предоставляет API для игнорирования)
```

*Архитектурный вывод:* Если функция помечена `[[nodiscard]]`, язык C23 настоятельно рекомендует вам __не игнорировать её вообще__. Если игнорирование легально, возможно, функция не должна быть помечена этим атрибутом, либо должна возвращать `void`, а статус писать в out-параметр.

## 6. Взаимодействие с другими паттернами

### 6.1. Синергия с Паттерном 01 (`err_t`) и Паттерном 09 (Latched State)

Без `NODISCARD` вызов `safe_file_write(&sf, data, len);` без проверки `err_t` приведет к тихой деградации. С `NODISCARD` компилятор заставит разработчика написать `if (safe_file_write(...) != ERR_OK)`, что спасет от потери данных.

### 6.2. Синергия с Паттерном 04 (Result) и Паттерном 16 (`_Generic`)

Как показано в разделе 4, применение `[[nodiscard]]` к самим `Result`-структурам делает функциональный стиль в C безопасным. Утечка памяти из-за пропущенного `free(r.ptr)` становится невозможной, так как компилятор не даст проигнорировать сам `Result` (см. [Паттерн 16](16_type_safty_tagged_union.md)).

### 6.3. Совместимость с MISRA C

Паттерн 17 является программной реализацией __MISRA C:2012 Rule 17.7__ ("The value returned by a function having non-void return type shall be used"). Использование `warn_unused_result` или `[[nodiscard]]` позволяет автоматизировать соблюдение этого правила статическим анализатором.

## 7. Практические рекомендации (Best Practices)

1. __Помечайте все API, возвращающие статус.__ Любая функция, возвращающая `err_t`, `bool` (успех/неуспех) или владеющий указатель, должна быть помечена `NODISCARD`.
2. __Используйте макрос-адаптер.__ Не засоряйте код `#ifdef`. Создайте единый `NODISCARD` макрос в корневом заголовочном файле проекта.
3. __Применяйте к типам в C23.__ Если вы пишете библиотеку на C23, помечайте `[[nodiscard]]` структуры `Result` и `Optional`. Это избавит от необходимости повторять атрибут для каждой функции.
4. __Добавляйте причину (C23).__ Используйте `[[nodiscard("reason")]]`, чтобы объяснить *почему* результат нельзя игнорировать (например, `"Resource leak"` или `"State corruption"`). Это бесценно для junior-разработчиков.
5. __Не злоупотребляйте.__ Не помечайте функции, где возврат — это просто данные, а не статус (например, `int get_count(void);`). Игнорирование количества элементов не ведет к UB или утечкам.
