# Паттерн обработки ошибок: Compiler-Enforced Return Checking (Принудительная проверка возврата)

__Дата:__ "2026-10-28"\
__Версия:__ "v1.0"\
__Стандарты:__ "C23 (ISO/IEC 9899:2024, атрибут [[nodiscard]]); GCC/Clang Extensions (__attribute__((warn_unused_result))); MSVC SAL Annotations (_Check_return_)"\
__Предварительные требования__:

- Понимание того, как компилятор C обрабатывает возвращаемые значения и предупреждения (warnings).
- Знакомство с [Каталогом паттернов](00_pattern_catalog.md).
- Знакомство с паттернами контракта возврата: [Паттерн 01](01_return_code_out_params.md), [Паттерн 02](02_sentinel_errno.md), [Паттерн 03](03_return_val_param_err_t.md), [Паттерн 04](04_result_struct.md), [Паттерн 05](05_bool_success.md), [Паттерн 08](08_state_stream_marker.md).
- Знакомство с [Паттерном 09: Latched error state](09_latched_error_state.md) как аддитивной надстройкой над контрактом возврата.
- Знакомство с [Паттерном 16: Типобезопасные Tagged Unions через `_Generic`](16_type_safty_tagged_union.md) для понимания синергии с полиморфными Result-типами.
- Базовое понимание различий между стандартами C11 и C23.

__Цель:__

- Описать механизмы принудительной проверки возвращаемых значений на уровне компилятора.
- Показать эволюцию от GCC-расширений к стандартизированному C23 `[[nodiscard]]`.
- Продемонстрировать применение атрибута не только к функциям, но и к типам (struct/enum).
- Разобрать критическую ловушку приведения к `(void)` в C23 и способы явного игнорирования.

__Теория:__\
  Главный архитектурный недостаток языка C в контексте надежности — отсутствие скрытого потока управления (встроенного механизма исключений) и историческая толерантность компилятора к неиспользуемым данным.

  На уровне ABI и машинного кода, когда функция возвращает значение, оно просто помещается в регистр процессора (например, `RAX` в x86_64) или передается через стек. Вызывающий код имеет полное право проигнорировать этот регистр и продолжить выполнение. Если вместо `err_t err = init_system();` написать просто `init_system();`, компилятор молча сгенерирует код, который очистит стек (если необходимо) и перейдет к следующей инструкции, даже если в `RAX` лежит критическая ошибка инициализации.

  Это порождает три фундаментальные проблемы:

  1. Нарушение инвариантов: Программа продолжает работу в неопределенном состоянии (UB).
  2. Маскирование первопричины: Ошибка проявит себя гораздо позже (через Segmentation Fault или повреждение памяти), что делает отладку крайне сложной.
  3. Уязвимости безопасности: Пропуск проверки статуса аутентификации или выделения памяти — классическая точка входа для эксплоитов.

  Паттерн Compiler-Enforced Return Checking переносит контроль ошибок из плоскости runtime-логики и человеческой дисциплины (code review) в плоскость статического анализа на этапе сборки. Атрибуты семейства `nodiscard` меняют правила игры: они делают неиспользование возвращаемого значения синтаксической ошибкой (или критическим предупреждением).

  Ключевой философский принцип: Если возвращаемое значение содержит статус ошибки, результат валидации или владеющий ресурс (указатель, дескриптор), его игнорирование должно быть пресечено компилятором. Безопасность API должна быть гарантирована конструктивно, а не инструктивно.

## 1. Описание и строгий контракт

### 1.1. Эволюция инструментов

В индустрии используется три основных инструмента, в зависимости от целевого стандарта и компилятора:

1. __Расширение GCC/Clang (работает во всех режимах, предпочтительно для C99/C11/C17):__

    Привязывает проверку к конкретным компиляторам. Принудительно вызывает предупреждение `-Wunused-result`.
    В C23 формально заменен стандартизованным атрибутом `[[nodiscard]]`, но остается работоспособным.

   ```c
   __attribute__((warn_unused_result))
   err_t init_system(void);
   ```

2. __SAL-аннотации MSVC (нативный Windows):__
   Source-code Annotation Language от Microsoft. Работает только для функций (не для типов), требует подключения `<sal.h>`.

   ```c
   #include <sal.h>
   
   _Check_return_
   err_t init_system(void);
   ```

   _Примечание: `clang-cl` (Clang в режиме совместимости с MSVC) предпочитает использовать `__attribute__((warn_unused_result))` вместо SAL-аннотаций._

3. __Стандарт C23 (Современный переносимый подход):__
   Унифицированный синтаксис, поддерживаемый всеми C23-совместимыми компиляторами (GCC 14+, Clang 18+, MSVC 19.35+).

   ```c
   [[nodiscard]]
   err_t init_system(void);
   ```

   _Примечание: Некоторые современные компиляторы (например, Clang) в режиме C23 также поддерживают расширение со строковым литералом `[[nodiscard("Reason")]]` для вывода кастомного сообщения в лог сборки. Однако стандарт C23 формально не включает строковый аргумент, в отличие от C++17/20._

### 1.2. Критерии применимости и архитектурные инварианты

Атрибут `NODISCARD` является инструментом статической верификации контракта API. Его использование должно быть строго ограничено функциями и типами данных, для которых нарушение контракта эквивалентно логической ошибке, UB или компрометации безопасности.

Принудительная проверка возврата строго обязательна в следующих четырех архитектурных сценариях:

#### Функции владения ресурсами (Resource Acquisition / Transfer)

Любая функция, которая выделяет, открывает или передает владение ресурсом (динамическая память, дескрипторы файлов, сокеты, мьютексы), должна быть помечена `NODISCARD`. Игнорирование возврата гарантирует утечку ресурса или вечную блокировку.

__Паттерн 01 (err_t + out-параметры):__

```c
// Ресурс передается через out-параметр, статус через return
NODISCARD
err_t open_channel(const char *uri, channel_t **out_ch);

// Использование:
channel_t *ch = NULL;
err_t err = open_channel("tcp://localhost:8080", &ch);
if (err != ERR_OK) {
    // Обработка ошибки
    return err;
}
// ch валиден, владение передано вызывающему коду
```

__Паттерн 02 (Sentinel + errno):__

```c
// Ресурс возвращается напрямую, NULL при ошибке
NODISCARD
FILE *open_data_file(const char *path);

// Использование:
FILE *f = open_data_file("config.txt");
if (!f) {
    // errno установлен, обработка ошибки
    return ERR_IO;
}
// f валиден, владение передано
```

#### Функции мутации состояния со статусным ответом (State Mutation)

Если функция изменяет состояние системы, но может завершиться сбоем, ее результат определяет, находится ли система в валидном состоянии. Пропуск проверки приводит к продолжению работы приложения в поврежденном/неопределенном окружении.

__Паттерн 01 (err_t + out-параметры):__

```c
// Изменяет состояние flash-памяти, возвращает статус
NODISCARD
sys_err_t flash_write_page(uint32_t addr, const uint8_t *data);

// Использование:
sys_err_t err = flash_write_page(0x1000, buffer);
if (err != SYS_OK) {
    // Состояние системы неизвестно, требуется восстановление
    recovery_procedure();
}
```

__Паттерн 04 (Result / Tagged Union):__

```c
struct result_int_impl {
    bool is_ok;
    union { int val; err_t err; } data;
};
typedef struct result_int_impl result_int_t;

// Возвращает результат операции + статус
NODISCARD
result_int_t parse_and_update_config(const char *line);

// Использование:
result_int_t res = parse_and_update_config("timeout=30");
if (!res.is_ok) {
    return res.data.err;
}
// Конфиг гарантированно обновлен, мутация успешна
```

#### Чистые функции и функции валидации (Pure Functions & Validation)

Для функций, не имеющих побочных эффектов (side-effects), вызов без использования результата полностью бессмысленен и является логической ошибкой разработчика. Сюда относятся предикаты верификации и парсеры.

__Паттерн 05 (bool + out-параметры):__

```c
// Предикат валидации, причина не важна
NODISCARD
bool is_token_valid(const char *token);

// Использование:
if (!is_token_valid(user_token)) {
    return ERR_AUTH_FAILED;
}
// Токен валиден, продолжаем работу
```

__Паттерн 04 (Result / Tagged Union):__

```c
struct result_int_impl {
    bool is_ok;
    union { int val; err_t err; } data;
};
typedef struct result_int_impl result_int_t;

// Парсер возвращает безопасную структуру Tagged Union
NODISCARD
result_int_t parse_and_update_config(const char *line);

// Использование:
result_int_t res = parse_and_update_config("timeout=30");
if (!res.is_ok) {
    return res.data.err;
}
// Успех, res.data.val содержит валидный int
```

__Паттерн 03 (Return value + err_t *):__

```c
// Возвращает значение, статус опционален
NODISCARD
int safe_divide(int a, int b, err_t *err);

// Использование:
err_t e;
int result = safe_divide(10, 0, &e);
if (e != ERR_OK) {
    // Деление на ноль, обработка
    return e;
}
// result содержит результат деления
```

#### Функции проверки границ и аутентификации (Security-Critical)

Пропуск проверки статуса авторизации, верификации криптографической подписи или выхода за границы буфера — классическая точка входа для эксплоитов.

__Паттерн 01 (err_t + out-параметры):__

```c
// Проверка криптографической подписи
NODISCARD
auth_status_t verify_signature(
    const uint8_t *payload, size_t len,
    const uint8_t *signature, size_t sig_len
);

// Использование:
if (verify_signature(payload, len, sig, sig_len) != AUTH_OK) {
    // Отказ в доступе
    return ERR_AUTH_FAILED;
}
// Подпись валидна, продолжаем обработку
```

__Паттерн 04 (Result / Tagged Union):__

```c
// Объявление типа для примера (возврат указателя с кодом ошибки)
struct result_ptr_impl {
    bool is_ok;
    union { void *ptr; err_t err; } data;
};
typedef struct result_ptr_impl result_ptr_t;

// Проверка границ буфера с возвратом безопасного значения
NODISCARD
result_ptr_t safe_buffer_read(buffer_t *buf, size_t offset);

// Использование:
result_ptr_t res = safe_buffer_read(buf, user_offset);
if (!res.is_ok) {
    return res.data.err; // Пресечена попытка Out-of-Bounds / Exploitation
}
// res.data.ptr безопасен для разыменования
```

#### Антипаттерн применения (Где `NODISCARD` запрещен)

__Информационные и вспомогательные возвраты:__ Запрещено помечать функции, где возвращаемое значение является лишь удобным побочным продуктом:

```c
// НЕ помечайте NODISCARD:
int sprintf(char *buf, const char *fmt, ...);  // возвращает количество байт
void *memcpy(void *dest, const void *src, size_t n);  // возвращает dest
int get_count(void);  // справочная информация
bool is_empty(void);  // геттер состояния
```

__Паттерн 08 (Маркеры состояния / EOF):__ Функции, возвращающие маркеры конца потока, __не должны__ помечаться `NODISCARD`, так как маркер — это норма, а не ошибка:

```c
// НЕ помечайте NODISCARD для маркеров:
int fgetc(FILE *stream);  // возвращает EOF при конце файла
node_t *list_get_next(list_t *list);  // возвращает NULL при конце списка

// Использование:
int c;
while ((c = fgetc(f)) != EOF) {  // EOF — это норма, не ошибка
    process_char(c);
}
// После цикла проверяем ferror(f) для разделения EOF и ошибки
```

Пометка таких функций `NODISCARD` засоряет код ложными предупреждениями и приводит к неоправданному использованию макросов подавления.

### 1.3. Применение атрибута к типам (C23)

Одна из самых мощных фич C23 — возможность применять `[[nodiscard]]` не только к функциям, но и к типам (`struct`, `union`, `enum`). Если функция возвращает тип, помеченный этим атрибутом, компилятор автоматически потребует проверить результат.

Это идеально решает проблему бойлерплейта для [Паттерна 04 (Result)](04_result_struct.md).

```c
// C23: Наиболее переносимый синтаксис. 
// Атрибут применяется к именованной структуре, а typedef создает псевдоним, 
// который корректно наследует атрибуты базового типа.
struct [[nodiscard]] result_int_impl {
    bool is_ok;
    union { int val; err_t err; } data;
};
typedef struct result_int_impl result_int_t;

// Функция не требует явного атрибута, он наследуется от типа!
result_int_t parse_int(const char *s); 

void demo(void) {
    parse_int("42"); 
    // ОШИБКА КОМПИЛЯЦИИ: ignoring return value of function declared with 'nodiscard' attribute
}
```

__Преимущество:__ Вы защищаете от игнорирования все функции, возвращающие `result_int_t`, просто определив атрибут один раз в месте объявления типа.

__Ограничение кроссплатформенности:__ Нативный MSVC (cl.exe) в режимах до C23 использует SAL-аннотации (`_Check_return_`), которые работают только для функций, но не для типов. Если ваша библиотека должна собираться на таком компиляторе, вы обязаны явно помечать атрибутом NODISCARD каждую функцию, возвращающую Result, а не полагаться на атрибуцию типа.

### 1.4. Макрос кросс-компиляции (Best Practice)

Для библиотек, обеспечивающих обратную совместимость со старыми стандартами и компиляторами, необходимо использовать макрос-адаптер. При этом важно учитывать различия в поддержке строкового аргумента:

- __Стандарт C23 (ISO/IEC 9899:2024, раздел 6.7.12.2)__ определяет атрибут `[[nodiscard]]` __без строкового аргумента__.
- __Clang__ поддерживает `[[nodiscard("message")]]` как __расширение__, даже в режиме C23.
- __GCC в режиме `-std=c23`__ выдаст ошибку компиляции при передаче строкового аргумента, так как строго следует стандарту.
- __Атрибут GCC `__attribute__((warn_unused_result))`__ не принимает параметров.

Пример готового файла:

```c
#ifndef COMPILER_ATTRS_H
#define COMPILER_ATTRS_H

/*
 * ============================================================================
 * КОМПИЛЯТОР-СПЕЦИФИЧНЫЕ АТРИБУТЫ ПРИНУДИТЕЛЬНОЙ ПРОВЕРКИ ВОЗВРАТА
 * ============================================================================
 */

/* Условное включение SAL-заголовка только для нативного MSVC */
#if defined(_MSC_VER) && !defined(__clang__)
    #include <sal.h>
#endif

/* ============================================================================
 * Макросы принудительной проверки возврата
 * ============================================================================ */
#if defined(__STDC_VERSION__) && __STDC_VERSION__ >= 202311L
    /* C23 и новее: стандартный атрибут ISO C */
    #define NODISCARD [[nodiscard]]
    
    /*
     * ВАЖНО: В стандарте C23 атрибут [[nodiscard]] НЕ принимает аргументов.
     * Только Clang поддерживает [[nodiscard("message")]] как расширение.
     * GCC в режиме -std=c23 выдаст ошибку компиляции при передаче строки.
     */
    #if defined(__clang__)
        #define NODISCARD_MSG(msg) [[nodiscard(msg)]]
    #else
        #define NODISCARD_MSG(msg) [[nodiscard]]
    #endif
    
#elif defined(__clang__) || defined(__GNUC__)
    /* Clang (включая clang-cl) или GCC в режимах до C23 */
    #define NODISCARD __attribute__((warn_unused_result))
    #define NODISCARD_MSG(msg) __attribute__((warn_unused_result))
    
#elif defined(_MSC_VER)
    /*
     * Нативный Microsoft Visual C++ (cl.exe) в режимах до C23
     * Ограничение: SAL работает только для функций, не для типов.
     */
    #define NODISCARD _Check_return_
    #define NODISCARD_MSG(msg) _Check_return_
    
#else
    /* Fallback для экзотических или устаревших компиляторов */
    #define NODISCARD
    #define NODISCARD_MSG(msg)
#endif

/* ============================================================================
 * МАКРОС ЯВНОГО ИГНОРИРОВАНИЯ РЕЗУЛЬТАТА
 * ============================================================================
 * Безопасно подавляет предупреждения nodiscard, гарантируя однократное
 * вычисление выражения и создание типизированной временной переменной.
 *
 * Использование:
 *   IGNORE_RESULT(fclose(f));
 *   IGNORE_RESULT(lib_cleanup(ctx));
 */
#if defined(__STDC_VERSION__) && __STDC_VERSION__ >= 202311L
    /* C23: стандартный typeof */
    #define IGNORE_RESULT(expr) \
        do { typeof(expr) _ignored_res_ = (expr); (void)_ignored_res_; } while(0)
#elif defined(__GNUC__) || defined(__clang__)
    /* GCC/Clang до C23: расширение __typeof__ */
    #define IGNORE_RESULT(expr) \
        do { __typeof__(expr) _ignored_res_ = (expr); (void)_ignored_res_; } while(0)
#else
    /*
     * Fallback для MSVC, экзотических или устаревших компиляторов
     * (Borland C, старые версии Tiny C, IAR/Keil без C99, и т.д.)
     *
     * ОГРАНИЧЕНИЕ: В этой ветке используется простой (void)-каст,
     * поскольку typeof недоступен. Это означает:
     *   - Для вызовов функций макрос работает корректно.
     *   - Для nodiscard-типов (структур с [[nodiscard]]) защита
     *     от предупреждений НЕ гарантируется на некоторых компиляторах.
     *   - Выражение вычисляется ровно один раз, побочные эффекты сохранены.
     */
    #define IGNORE_RESULT(expr) \
        do { (void)(expr); } while(0)
#endif

#endif /* COMPILER_ATTRS_H */
```

Как использовать в коде:

```c
#include "compiler_attrs.h"

/* Пример 1: Функция с сообщением (работает только в Clang) */
NODISCARD_MSG("Выделение памяти без проверки приведет к утечке")
void *alloc_buffer(size_t size);

/* Пример 2: Краткая форма (работает везде) */
NODISCARD
err_t init_system(void);
```

## 2. Плюсы и минусы

### 2.1. Плюсы

- __Нулевой runtime-overhead.__ Вся проверка происходит на этапе компиляции. В бинарнике нет ни одного лишнего байта или инструкции.
- __Защита от «человеческого фактора».__ Разработчик может забыть проверить `err_t` при рефакторинге. Компилятор не даст такому коду скомпилироваться (или хотя бы выдаст громкий warning).
- __Самодокументируемость.__ Наличие `[[nodiscard]]` в сигнатуре сразу говорит читателю: «Эта функция может упасть, и ее статус критически важен».

### 2.2. Минусы

- __Шум при рефакторинге.__ Если вы изменили API и добавили `NODISCARD`, вам придется переписать все места вызова, где результат ранее игнорировался.
- __Проблема явного игнорирования.__ Иногда статус действительно не важен (например, при попытке очистки ресурса в деструкторе). В C23 механизм явного игнорирования стал сложнее (см. раздел 3).

## 3. Подавление предупреждения `nodiscard`: механизмы и ловушки (Must Read)

Раздел рассматривает легитимные способы игнорирования результата, помеченного `NODISCARD`. Это необходимо в редких, но практически важных сценариях: попытка закрытия ресурса в деструкторе, best-effort очистка, fire-and-forget вызовы телеметрии. Непонимание механизмов подавления ведет либо к ложным предупреждениям, либо к UB.

### 3.1. Эволюция механизмов подавления: C11 vs C23

__C11 (GCC/Clang, `warn_unused_result`):__

Расширение компилятора не формализует способ подавления, но сложилась устойчивая идиома — явное приведение к `void`:

```c
__attribute__((warn_unused_result))
err_t close_resource(resource_t *r);

(void)close_resource(r);  // Подавляет предупреждение GCC/Clang
```

__C23 (`[[nodiscard]]`, ISO/IEC 9899:2024, раздел 6.7.12.2):__

Стандарт формализует семантику подавления. Цитата из спецификации:

> _"An implementation is encouraged to issue a diagnostic message if a nodiscard call is evaluated as a void expression __other than by an explicit cast to void__."_

Это означает, что __явный каст к `(void)` остается стандартным и рекомендуемым способом подавления__ предупреждения для вызовов функций. На практике GCC 14+ и Clang 18+ не выдают предупреждение при `(void)func()`.

```c
// C23
[[nodiscard]] err_t init_system(void);

// ПРАВИЛЬНО: Явный каст — стандартный способ подавления
(void)init_system();  // Компилятор НЕ выдаст предупреждение

// НЕПРАВИЛЬНО: Неявное отбрасывание
init_system();  // Компилятор ВЫДАСТ предупреждение
```

__Критический нюанс:__ Распространенное заблуждение, что в C23 `(void)` каст «больше не работает», __не соответствует действительности__. Стандарт явно разрешает его как механизм подавления. Проблема возникает в другом — при работе с `nodiscard`-типами (см. раздел 3.3).

### 3.2. Инфраструктурный макрос `IGNORE_RESULT`

Для самодокументируемости и единообразия кода в `compiler_attrs.h` (см. раздел 1.4) определен макрос `IGNORE_RESULT`, который:

1. __Гарантирует однократное вычисление выражения__ (избегая побочных эффектов при `IGNORE_RESULT(get_next_and_advance())`).
2. __Создает типизированную временную переменную__ через `typeof`/`__typeof__`, что удовлетворяет самым строгим интерпретациям `[[nodiscard]]`.
3. __Работает единообразно__ во всех поддерживаемых стандартах и компиляторах.

__Использование в коде:__

```c
#include "compiler_attrs.h"

void destroy_context(lib_ctx_t *ctx) {
    if (!ctx) return;
    
    // Best-effort очистка: ошибка закрытия не критична
    IGNORE_RESULT(flush_buffers(ctx));
    IGNORE_RESULT(close_socket(ctx->fd));
    
    free(ctx);
}
```

__Преимущества макроса перед прямым приведением к (void):__

- __Самодокументируемость:__ IGNORE_RESULT(x) явно декларирует намерение «я знаю, что игнорирую, и это легально».
- __Защита от двойного вычисления:__ макрос гарантирует, что выражение вычислится ровно один раз.
- __Единообразие:__ работает одинаково во всех компиляторах и стандартах.
- __Защита для nodiscard-типов:__ в ветках с typeof макрос корректно подавляет предупреждения даже для структур с атрибутом [[nodiscard]] (в отличие от (void)-каста, который на некоторых компиляторах может не сработать для типов).

__Ограничение MSVC и fallback-ветки:__ для нативного MSVC (до C23) и экзотических компиляторов без поддержки typeof макрос разворачивается в простой (void)(expr). В этом режиме защита nodiscard-типов не гарантируется — см. комментарии в [compiler_attrs.h](code_examples/compiler_attrs.h).

### 3.3. Особый случай: `nodiscard`-типы (структуры)

Макрос `IGNORE_RESULT` и явный `(void)` каст отлично работают для __вызовов функций__. Однако возникает специфический случай, когда `[[nodiscard]]` применен к __типу__ (фича C23, раздел 1.3), а не к функции:

```c
// C23: nodiscard применен к типу
struct [[nodiscard]] result_int_impl {
    bool is_ok;
    union { int val; err_t err; } data;
};
typedef struct result_int_impl result_int_t;

result_int_t parse_int(const char *s);
```

В этом случае некоторые компиляторы (особенно ранние реализации C23) могут выдавать предупреждения при попытке каста результата к `(void)`, поскольку атрибут «прилип» к типу, а не к конкретной функции.

__Решение — dummy-переменная:__

```c
// Способ 1: Явный каст (работает для большинства случаев)
(void)parse_int("42");

// Способ 2: Dummy-переменная (надежнее для nodiscard-типов)
result_int_t dummy = parse_int("42");
(void)dummy;  // Подавление warning за неиспользуемую переменную

// Способ 3: Через макрос IGNORE_RESULT (рекомендуется)
IGNORE_RESULT(parse_int("42"));
```

__Почему dummy-переменная надежнее:__ Компилятор видит, что результат присвоен в именованную переменную, а не отброшен как void-выражение. Это удовлетворяет даже самым строгим интерпретациям `[[nodiscard]]` для типов.

### 3.4. Таблица выбора механизма подавления

| Сценарий | Рекомендуемый механизм | Обоснование |
| :--- | :--- | :--- |
| Игнорирование вызова функции с `[[nodiscard]]` | `IGNORE_RESULT(func())` | Самодокументируемость, защита от двойного вычисления |
| Игнорирование вызова функции с `warn_unused_result` | `IGNORE_RESULT(func())` или `(void)func()` | Оба способа работают, макрос предпочтительнее |
| Игнорирование результата `nodiscard`-типа (C23) | `IGNORE_RESULT(func())` или dummy-переменная | Явный каст может не сработать в некоторых компиляторах |
| Best-effort очистка в деструкторе | `IGNORE_RESULT(cleanup())` | Семантически ясно, что игнорирование легально |
| Одинарное вычисление критично | `IGNORE_RESULT(expr)` | Макрос гарантирует однократное вычисление |

### 3.5. Архитектурный вывод

1. __`(void)` каст в C23 работает.__ Распространенное заблуждение о его «отмене» не соответствует стандарту. Стандарт явно разрешает явный каст как механизм подавления.
2. __Предпочитайте макрос `IGNORE_RESULT`.__ Он самодокументируем, защищает от двойного вычисления и работает единообразно во всех компиляторах.
3. __Для `nodiscard`-типов используйте dummy-переменную или `IGNORE_RESULT`.__ Явный `(void)` каст может не сработать в некоторых реализациях C23.
4. __Если игнорирование происходит часто — пересмотрите API.__ Если функция постоянно игнорируется, возможно, она не должна быть помечена `NODISCARD`, либо должна возвращать `void`, а статус передавать через out-параметр. `NODISCARD` — это сигнал о критичности результата, а не формальность.
5. __Запрещено использовать `IGNORE_RESULT` для маскировки багов.__ Если вы игнорируете результат аллокации памяти или проверки аутентификации — это не «подавление предупреждения», а уязвимость. Макрос — для легитимных случаев, а не для сокрытия ошибок.

## 4. Взаимодействие с другими паттернами

### 4.1. Синергия с Паттерном 01 (`err_t`) и Паттерном 09 (Latched State)

__С Паттерном 01 (базовый контракт):__
Без `NODISCARD` вызов `safe_file_write(&sf, data, len);` без проверки `err_t` приведет к тихой деградации. С `NODISCARD` компилятор заставит разработчика написать `if (safe_file_write(...) != ERR_OK)`, что спасет от потери данных.

__С Паттерном 09 (Latched State):__
Паттерн 09 переводит долгоживущий объект в состояние `FAILED` после фатальной ошибки (например, разрыв сокета или потеря связи с диском). Все последующие операции на таком объекте немедленно возвращают код ошибки, не обращаясь к ядру. Однако эта защита работает __только при условии__, что вызывающий код проверяет возвращаемый статус. `NODISCARD` гарантирует, что игнорирование такого статуса будет пресечено компилятором, превращая Latched State из декорации в работающий защитный механизм.

Подробное описание Latched State и его взаимодействия с контрактами возврата см. в [Паттерне 09](09_latched_error_state.md).

### 4.2. Синергия с Паттерном 04 (Result) и Паттерном 16 (_Generic)

Если Result-структура (Паттерн 04) содержит владеющий указатель, ее игнорирование ведет не просто к потере данных, а к утечке памяти. Применение [[nodiscard]] к типу (раздел 1.3) пресекает такую утечку на этапе компиляции, превращая runtime-проблему в compile-time ошибку. Подробное описание полиморфных макросов и их взаимодействия с атрибуцией типов см. в Паттерне 16. (см. [Паттерн 16](16_type_safty_tagged_union.md)).

### 4.3. Совместимость с MISRA C

Паттерн 17 является программной реализацией MISRA C:2012 Rule 17.7 ("The value returned by a function having non-void return type shall be used"). Использование `warn_unused_result` или `[[nodiscard]]` позволяет автоматизировать соблюдение этого правила статическим анализатором.

## 5. Практические рекомендации (Best Practices)

1. __Помечайте все API, возвращающие статус.__ Любая функция, возвращающая `err_t`, `bool` (успех/неуспех) или владеющий указатель, должна быть помечена `NODISCARD`.
2. __Используйте макрос-адаптер.__ Не засоряйте код `#ifdef`. Создайте единый `NODISCARD` макрос в корневом заголовочном файле проекта.
3. __Применяйте к типам в C23.__ Если вы пишете библиотеку на C23, помечайте `[[nodiscard]]` структуры `Result` и `Optional`. Это избавит от необходимости повторять атрибут для каждой функции.
4. __Добавляйте причину через макрос (Clang).__ Используйте `NODISCARD_MSG("reason")` вместо голого `[[nodiscard("reason")]]`, чтобы объяснить, почему результат нельзя игнорировать (например, `"Resource leak"` или `"State corruption"`). Это бесценно для junior-разработчиков. __Важно:__ Строковый аргумент поддерживается только Clang как расширение. В GCC и MSVC макрос `NODISCARD_MSG` раскроется в обычный `[[nodiscard]]` или `_Check_return_` без сообщения, но проверка возврата все равно будет работать.
5. __Не злоупотребляйте.__ Не помечайте функции, где возврат — это просто данные, а не статус (например, `int get_count(void);`). Игнорирование количества элементов не ведет к UB или утечкам.
