# Полный каталог паттернов обработки ошибок в C

title: "Полный каталог паттернов обработки ошибок в C"\
date: "2026-07-01"\
version: "v3.0 (Comprehensive & Standard-Aware)"\
baseline_standard: "C11 (ISO/IEC 9899:2011)"\
extended_standards: "C23 (ISO/IEC 9899:2024), POSIX.1-2017, GCC/Clang Extensions"\
objective:

- Предоставить исчерпывающую таксономию паттернов обработки ошибок в C.
- Четко разграничить семантику: ошибки среды, естественное завершение, баги программиста.
- Указать строгие требования к стандарту языка или компилятора для каждого паттерна.
- Задать архитектурный фундамент для проектирования API от embedded до высоконагруженных user-space систем.

theory:\
  В языке C отсутствует скрытый поток управления (нет исключений, нет RAII, нет деструкторов). Обработка ошибок — это всегда явное, детерминированное управление состоянием машины и ресурсами.\
  Выбор паттерна диктуется «стоимостью ошибки» (Cost of Failure), доменом и целевым стандартом. Низкоуровневый код использует POSIX-стиль, средний слой — явные коды (err_t) или структуры (Result), верхний — политики восстановления или аварийного останова (fail-fast).\
  Ключевой принцип C: «Ошибки не должны маскироваться под нормальные данные, а нормальное завершение не должно трактоваться как ошибка».

common_pitfalls:

  1. Эмуляция C++ исключений через setjmp/longjmp. В C это приводит к катастрофическим утечкам ресурсов, так как longjmp не вызывает функции очистки.
  2. Семантическое загрязнение: использование одного значения (например, -1 или NULL) и для ошибки среды, и для естественного конца потока (EOF).
  3. Игнорирование возвращаемых значений. Без механизмов принуждения (атрибутов компилятора) статус можно случайно проигнорировать.
  4. Смешивание паттернов в одном API. Возврат errno в одних функциях и err_t в других внутри одной библиотеки разрушает предсказуемость.

best_practices:

  1. Базовый стандарт: Проектировать API с учетом C11. Использовать C23 или расширения компиляторов только там, где они дают критическое преимущество (безопасность, эргономика).
  2. Принудительная проверка: Всегда помечать функции, возвращающие статус, атрибутами `warn_unused_result` или `[[nodiscard]]`.
  3. Явный выбор стратегии: Для модуля выбирается 1-2 основных паттерна.

## I. Паттерны возврата статуса и данных (Return & Data)

### 1. [Return-код (enum/int) + out-параметры](01_return_code_out_params.md)

**Требуемый стандарт:** C11 (базовый)\
**Идея.** Функция возвращает код ошибки (обычно `int` или `enum`), а полезные данные записывает через указатели-параметры.\
**Пример.** `err_t read_config(const char *path, config_t *out_cfg);`\
**Области применения.** Библиотеки и модульные API, где требуется явное и детализированное представление ошибок.\
**Плюсы.** Явный контракт; легко расширять набор ошибок через enum; удобно для маппинга системных ошибок.\
**Минусы.** Сигнатуры становятся громоздкими. Требует дисциплины или атрибутов компилятора для контроля проверки.\

### 2. [Специальное значение (sentinel) + errno (Ошибки среды)](02_sentinel_errno.md)

**Требуемый стандарт:** C11 + POSIX.1 (для `errno`)
**Идея.** Функция возвращает тип результата, но одно значение зарезервировано как признак *сбоя среды* (NULL, -1), а дополнительные сведения даются через `errno`.\
**Пример.** `fopen` (возвращает NULL), POSIX `read` (возвращает -1).\
**Области применения.** Обёртки вокруг стандартной библиотеки, POSIX-API, системный код.\
**Плюсы.** Стандарт де-факто для UNIX; не требует новых типов.\
**Минусы.** `errno` в POSIX — это макрос, раскрывающийся в `_Thread_local` переменную (решает проблему многопоточности, но требует проверки *сразу* после вызова). Sentinel должен быть формально вне множества корректных значений.

### 3. [Return полезного значения + статус через аргумент](03_return_val_param_err_t.md)

**Требуемый стандарт:** C11 (базовый)\
**Идея.** Функция возвращает полезное значение через `return`, а статус ошибки — через дополнительный параметр (указатель).\
**Пример.** `int calc(int x, int y, err_t *err);`\
**Области применения.** Функции, где ошибки редки, или где для читаемости удобно видеть результат как `return`.\
**Плюсы.** Позволяет передать `NULL` вместо указателя на статус, если вызывающему не нужна детализация.\
**Минусы.** Контракт менее прозрачен; легко проигнорировать статус.

### 4. [Struct Result / Tagged Union (Структура результата)](04_result_struct.md)

**Требуемый стандарт:** C11 (базовый)\
**Идея.** Функция возвращает структуру, содержащую тег (дискриминатор) и объединение (`union`) полезной нагрузки и кода ошибки.\
**Пример.**

```c
typedef struct {
    bool is_ok;
    union { int value; err_t err; } data;
} result_int_t;
```

**Области применения.** Парсеры, конвертеры, функциональные обертки.\
**Плюсы.** Вся информация упакована в одном типе; семантически четко разделены успех и ошибка.\
**Минусы.** Накладные расходы на копирование структуры; требует осмысленного дизайна времени жизни, если внутри union есть указатели.

### 5. [Простое булево «успех/неуспех»](05_bool_success.md)

**Требуемый стандарт:** C99/C11 (`<stdbool.h>`)\
**Идея.** Функция возвращает `bool` как флаг успеха, данные — через out-параметры.\
**Пример.** `bool parse_line(const char *line, entry_t *out_entry);`\
**Области применения.** Внутренние вспомогательные функции, фильтрация, простые проверки.\
**Плюсы.** Максимально простой и читаемый контракт.\
**Минусы.** Скрывает причину ошибки; при необходимости детализации придется ломать API.

## II. Паттерны состояния, контекста и потоков (State & Context)

### 6. [Глобальный/контекстный объект состояния ошибок](06_error_context.md)

**Требуемый стандарт:** C11 (базовый)\
**Идея.** Библиотека поддерживает объект контекста, в котором хранит состояние последней ошибки (код, сообщение, стек).\
**Пример.** `const error_state_t *lib_last_error(const lib_ctx_t *ctx);`\
**Области применения.** Сложные библиотеки (БД-клиенты, графические движки), где нужны контекстные ошибки и потокобезопасность.\
**Плюсы.** Ошибки привязаны к экземпляру контекста (нет проблем глобального `errno`); можно хранить богатый контекст.\
**Минусы.** Усложнение API (необходимость таскать контекст); требует строгого протокола чтения ошибки.

### 7. [Callback-обработчики ошибок](07_error_callback.md)

**Требуемый стандарт:** C11 (базовый)\
**Идея.** Пользователь регистрирует функцию-обработчик, которая вызывается при ошибках. Библиотека делегирует ей решение (логировать, завершить, повторить).\
**Пример.** `typedef err_action_t (*error_callback_t)(int code, void *user_data);`\
**Области применения.** Фреймворки, где пользователи должны настраивать политику обработки.\
**Плюсы.** Гибкость; разделение ответственности (библиотека детектирует, приложение реагирует).\
**Минусы.** Усложняет поток исполнения; callback не должен блокироваться или вызывать рекурсию.

### 8. [Маркеры состояния и конца потока (State/EOF Markers)](08_state_stream_marker.md)

**Требуемый стандарт:** C11 (базовый)\
**Идея.** Специальное значение используется не как ошибка, а как маркер *естественного завершения* или перехода состояния.\
**Примеры.** `EOF` в `fgetc` (конец файла); `NULL` при обходе связного списка.\
**Области применения.** Потоки ввода-вывода, итераторы, конечные автоматы.\
**Плюсы.** Позволяет элегантно завершать циклы без генерации «ложных» ошибок.\
**Минусы.** Требует строгого разделения: `EOF` (конец данных) не должен путаться с `ferror()` (ошибка чтения).\
*Семантическое отличие от Паттерна 2:* Паттерн 2 — «я не смог это сделать» (ошибка). Паттерн 8 — «я сделал, но данных больше нет» (норма).

### 9. [Latched error state (Залипающее состояние ошибки)](09_latched_error_state.md)

**Требуемый стандарт:** C11 (базовый)\
**Идея.** После определенного сбоя объект переводится в состояние «постоянной ошибки». Дальнейшие операции сразу возвращают ошибку.\
**Области применения.** Потоки (`FILE*`), сетевые сокеты, драйверы.\
**Плюсы.** Упрощает обработку: не нужно проверять ошибку после каждой записи в буфер.\
**Минусы.** Требует явного механизма сброса (reset) или пересоздания объекта.

## III. Паттерны управления потоком и ресурсами (Control Flow & Resources)

### 10. [Goto-цепочки для централизованной очистки (Cleanup)](10_goto_cleanup.md)

**Требуемый стандарт:** C11 (базовый)\
**Идея.** Использование `goto` и меток для детерминированного освобождения ресурсов в обратном порядке их захвата.\
**Области применения.** Любые функции, захватывающие более одного ресурса. Эталон для ядра Linux.\
**Плюсы.** Единственный математически строгий способ избежать дублирования кода очистки в базовом C.\
**Минусы.** Требует дисциплины: `goto` должен прыгать только вперед, к метке в конце функции.

### 11. [setjmp/longjmp (Нелокальные переходы)](11_setjmp_longjmp.md)

**Требуемый стандарт:** C11 (базовый)\
**Идея.** Сохранение контекста стека и «размотка» стека к точке сохранения при возникновении фатальной ошибки.\
**Области применения.** Парсеры с глубоким рекурсивным спуском (без захвата ресурсов), реализация сопрограмт (coroutines).\
**Плюсы.** Позволяет избежать передачи кода ошибки через множество уровней вложенности.\
**Минусы.** **Крайне опасно.** Не освобождает ресурсы. Может привести к UB, если между setjmp и longjmp менялись локальные не-volatile переменные. *Антипаттерн для штатных ошибок.*

### 12. [Эмуляция RAII через Scope Guards](12_raii_emulation_with_scope_guard.md)

**Требуемый стандарт:** **Расширение GCC/Clang** (`__attribute__((cleanup))`)\
**Идея.** Использование атрибута `cleanup` для автоматического вызова функции очистки при выходе переменной из области видимости (scope).\
**Пример.**

```c
void close_fd(int *fd) { if (*fd >= 0) close(*fd); }
int do_work() {
    int fd __attribute__((cleanup(close_fd))) = -1;
    fd = open("file", O_RDONLY);
    // ... код без goto ...
} // компилятор сам вызовет close_fd при выходе
```

**Области применения.** `systemd`, современные сетевые демоны, любой код, где `goto cleanup` становится слишком громоздким.\
**Плюсы.** Полностью устраняет необходимость в `goto`, делает код линейным, гарантирует отсутствие утечек при ранних возвратах.\
**Минусы.** Не является строгим ISO C (зависит от компилятора), но поддерживается GCC, Clang и Intel C.

## IV. Паттерны фатальных сбоев и инвариантов (Fail-Fast)

### 13. [Fail-Fast (инварианты, assert, аварийный выход)](13_fail_fast_assert.md)

#### 13.1. Defensive Programming (Ошибки программиста / Инварианты)

**Требуемый стандарт:** C11 (базовый, `<assert.h>`)\
**Идея.** Нарушение внутренних инвариантов означает баг в коде. Такие ошибки не лечатся, а приводят к немедленному падению в отладочной сборке.\
**Пример.** `assert(ptr != NULL);`\
**Области применения.** Внутренние проверки, API, где передача `NULL` является ошибкой вызывающего кода.\
**Плюсы.** Быстро выявляет логические ошибки на этапе тестирования.\
**Минусы.** В release-сборке `assert` вырезается (через `NDEBUG`). Для критичных проверок в production нужно использовать явные `if (!ptr) abort();`.

#### 13.2. Unrecoverable Environmental Errors (Невосстановимые средовые ошибки)

**Требуемый стандарт:** C11 (базовый, `<stdlib.h>`)\
**Идея.** Ситуации, когда продолжение работы невозможно или опасно (Out Of Memory, переполнение стека).\
**Пример.** `abort()`, `exit(EXIT_FAILURE)`, `panic()` в ядре.\
**Области применения.** Обработчики `malloc` в системах, не поддерживающих OOM; критические секции ядра.\
**Плюсы.** Гарантирует, что система не останется в неконсистентном состоянии.\
**Минусы.** Завершает весь процесс. Недопустимо для библиотек общего назначения (user-space).

## V. Продвинутые и современные архитектурные паттерны

### 14. [Error Context / Wrapping (Обогащение ошибки контекстом)](14_error_context_wrapping.md)

**Требуемый стандарт:** C11 (базовый)\
**Идея.** При пробросе ошибки с нижнего уровня на верхний, функция не просто возвращает `err_t`, но и добавляет контекст (какой файл, какой ID сессии).\
**Пример.** Макрос `LOG_ERR_AND_WRAP(ctx, ERR_IO, "Failed to open config %s", path);`\
**Области применения.** Средний и верхний уровни приложений, сложные распределенные системы.\
**Плюсы.** Решает проблему «потери контекста» при использовании простых кодов возврата.\
**Минусы.** Требует выделения памяти для хранения строк контекста или использования статических буферов.

### 15. [Асинхронная / Событийная передача ошибок](15_async_event_error_transfer.md)

**Требуемый стандарт:** C11 (базовый)\
**Идея.** Ошибки не возвращаются через `return`. Они доставляются асинхронно через структуры событий или callback-и завершения.\
**Пример.** `void on_read_complete(io_req_t *req, ssize_t result, int error_code);`\
**Области применения.** Высокопроизводительные сетевые серверы (`epoll`, `io_uring`, `libuv`), драйверы.\
**Плюсы.** Не блокирует поток выполнения, идеально ложится на модель конечных автоматов.\
**Минусы.** Крайне сложно для отладки; требует строгого контроля времени жизни контекста запроса.

### 16. [Типобезопасные Tagged Unions через `_Generic`](16_type_safty_tagged_union.md)

**Требуемый стандарт:** **C11** (ключевая фича стандарта)\
**Идея.** Использование `_Generic` для создания макросов `OK(val)` и `ERR(code)`, которые автоматически упаковывают значение в `union` нужного типа, обеспечивая строгую типобезопасность.\
**Пример.**

```c
#define OK(val) _Generic((val), \
    int: make_result_int(1, val, 0), \
    char*: make_result_str(1, val, NULL) \
)
```

**Области применения.** Современные C-библиотеки, парсеры, функциональные обертки.\
**Плюсы.** Строгая типобезопасность на уровне компилятора; отсутствие необходимости писать отдельную структуру для каждого типа данных.\
**Минусы.** Усложняет макросы; сообщения об ошибках компилятора при неправильном использовании могут быть трудны для чтения.

## VI. Паттерны контрактного программирования и принуждения (Enforcement)

### [17. Compiler-Enforced Return Checking (Принудительная проверка возврата)](17_compiler_enforced_return_checking.md)

**Требуемый стандарт:** **C23** (`[[nodiscard]]`) или **GCC/Clang Extensions** (`__attribute__((warn_unused_result))`)\
**Идея.** Использование атрибутов компилятора для генерации предупреждения или ошибки, если возвращаемое значение функции-статуса проигнорировано.\
**Пример.**

```c
// C23
[[nodiscard]] err_t init_system(void);
// GCC/Clang
__attribute__((warn_unused_result)) err_t init_system(void);
```

**Области применения.** Любые API, где игнорирование статуса ведет к неопределенному поведению или утечкам.\
**Плюсы.** Переводит обработку ошибок из плоскости «человеческой дисциплины» в плоскость «статического контроля».\
**Минусы.** Требует использования современных компиляторов или стандарта C23. При использовании `warn_unused_result` нужно явно приводить результат к `void`, если ошибка намеренно игнорируется.
